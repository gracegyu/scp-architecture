## 1. "Edge"가 무슨 뜻인가

클라우드 용어다. **데이터가 생기는 현장 가까이에서 도는 컴퓨팅**을 말하며 중앙 클라우드의 반대말이다.

치과에서 필요한 이유는 넷이다.

- 네트워크가 끊겨도 진료가 멈추면 안 된다
- 영상이 크다 — CT 한 건이 수백 MB~GB라 전부 올리면 비용·지연을 감당 못 한다
- 장비 SDK가 로컬에서만 동작한다 — USB·드라이버·전용 프로토콜
- PHI 주권 — 환자 데이터를 현지에 둬야 하는 규제

그래서 **local-first(로컬 우선)** 다. 로컬이 정상 동작의 기준이고 클라우드는 연결될 때 동기화하는 쪽이다.

⭐ **핵심은 Edge가 새 기능이 아니라 포지셔닝 전환이라는 것이다.**

- EzServer = "병원에 설치하는 서버 소프트웨어"(독립 제품)
- Edge = "클라우드 플랫폼의 현장 말단"(플랫폼의 일부)

같은 자리의 같은 역할인데 제품 구도에서의 의미가 다르다. SCP Cloud와 Edge가 한 쌍이 되는 그림이다.

## 2. vt-edge가 실제로 무엇인가

**플러그인을 설치해 기능을 붙이는 로컬 서버.** PocketBase를 참고 모델로 문서에 명시했다.

```

├─ 데이터 API                        ├─ ZIP 패키지 + manifest + SHA-256
├─ 플러그인 설치·실행·중지·제거       ├─ 자기 도메인 모델·업무 규칙 소유

└─ 관리 콘솔(React·바이너리에 내장)
```

## 3. 핵심 설계 결정 다섯

**(1) 기능 추가 = 플러그인 설치**
본체를 고쳐 전체를 재릴리즈하는 구조를 버렸다. 모든 설계의 출발점이다.

**(2) 플러그인은 별도 프로세스**
stdin/stdout 줄 단위 JSON으로만 대화한다. 하나가 죽어도 콘솔과 다른 기능은 산다.
- ⚠ 문서가 반복해 못 박는다 — **같은 OS 계정이라 보안 샌드박스가 아니다.** 장애 격리이지 보안 격리가 아니다

**(3) 플러그인에 DB를 주지 않는다**
연결 문자열도 파일 경로도 주지 않고 Base의 데이터 API를 거친다.
- ⭐ 요청에 적힌 `pluginId`를 **믿지 않고** 호스트가 발급한 실행 세션으로 데이터 영역을 결정한다. 자칭 신원을 신뢰하지 않는 설계

**(4) 암호화를 프로세스 밖으로 뺐다**
OpenBao(Vault 오픈소스 포크) Transit에 위임해 **Edge 프로세스가 키를 직접 들지 않는다.**

**(5) DDD 4계층 강제**
`domain → application → infrastructure` 의존 방향 고정. 도메인은 HTTP·파일시스템·프로세스를 모른다.
- "ezserver 용어는 커넥터의 변환 계층에 가둔다"는 문장까지 있다 — 레거시 어휘가 새 도메인에 스미는 것을 처음부터 막겠다는 뜻

## 4. 기술 스택과 저장소

### 의존성 (Cargo.toml)

- `axum` — HTTP 서버
- `rusqlite` (bundled · backup · hooks · limits) — **SQLite만.** PostgreSQL 드라이버 없음
- `tokio` · `serde` · `serde_json` · `zip` · `sha2` · `uuid` · `semver`
- `windows-sys`(Windows) · `libc`(Unix)
- ❌ `tonic`·`prost`·protobuf **없음** — gRPC 미사용

### SQLite 내구성 설정 (`src/base_data/sqlite.rs`)

```
PRAGMA foreign_keys=ON; journal_mode=WAL; synchronous=FULL;
busy_timeout = 500ms
```

⭐ **WAL + synchronous=FULL은 내구성 최대 설정이다.** 많은 제품이 성능 때문에 `NORMAL`로 두는데 `FULL`을 썼다. 전원이 끊겨도 커밋된 트랜잭션은 지켜진다.

백업 시 `PRAGMA integrity_check` + `pragma_foreign_key_check`를 돌린다 — 손상된 DB를 백업하지 않겠다는 뜻이다.

### 단일 실행 보장

- Windows — `Global` named mutex (로그인 세션 넘어 잠금)
- Linux — abstract Unix socket
- 다중 writer가 SQLite 손상 원인 1순위인데 OS 수준에서 막았다

## 5. API 표면 — 지금은 RPC 스타일이다

### Base 자체 관리 API

```
GET  /api/plugins
POST /api/login
     /api/admin/database · /api/admin/database/query
     /api/platform/backups · /api/platform/protection · /api/platform/settings
```

### 플러그인 업무 호출

```
POST /api/services/vatech.devices/call
     {"operation":"devices.register","data":{...}}
```

⚠ **리소스가 URL에 없고 메서드가 의미를 갖지 않는다. REST가 아니라 RPC다.**

프로토타입으로는 합리적이다 — 플러그인이 몇 개가 되든 디스패치 통로를 하나로 단순화한 것이다. 다만 "EzServer API를 RESTful하게 정리한다"는 목표와는 아직 만나지 않았다.

### 호스트↔플러그인 내부 파이프

```json
{"type":"invoke","request_id":"...","call":{"operation":"devices.list","data":{}}}
{"type":"data","request_id":"...","call_id":"...","request":{"operation":"list","collection":"devices"}}
{"type":"data_result","request_id":"...","result":{"Ok":[]}}
{"type":"result","request_id":"...","result":{"Ok":{"devices":[]}}}
```

여기는 RPC가 **맞다.** 외부 계약이 아니라 내부 전송이고 양방향이라 HTTP 의미론이 필요 없다.

## 6. 플러그인 계약 — IDL은 없다

`crates/plugin-sdk/src/lib.rs` **90줄**이 계약 전체다.

```rust
pub const MAX_FRAME: u64 = 256 * 1024;
#[serde(deny_unknown_fields)]          pub struct ServiceError
#[serde(rename_all = "camelCase", …)]  pub struct ServiceCall
#[serde(tag = "operation", …)]         pub enum DataRequest
#[serde(deny_unknown_fields)]          pub struct Record
#[serde(tag = "type", …)]              pub enum ServiceFrame
```

**계약이 없는 게 아니라 꽤 엄격하다.**

- `deny_unknown_fields` — 모르는 필드가 오면 거부. 오타·버전 불일치가 조용히 통과하지 않는다
- 태그드 유니온으로 프레임 종류가 타입으로 갈린다
- SDK 버전 정확히 고정 — `vt-edge-plugin-sdk = "=0.2.0"`
- 런타임 호환성은 `hostApiVersion: 2`로 별도 확인

**다만 언어 중립 IDL이 아니다.** 계약이 Rust 소스에 있으므로 **사실상 Rust 플러그인만 가능**하다. C++·C#으로 만들려면 90줄을 읽고 JSON 프레임을 손으로 맞춰야 한다.

## 7. REST vs RPC — vt-edge 관점 비교

> §5에서 본 HTTP 표면(RPC 스타일)과 §6의 플러그인 계약을 함께 놓고 판단하기 위한 절.

### 7.0 통신 구간은 셋이다 — 먼저 구분할 것

"RPC냐 REST냐"를 논하기 전에 **어느 구간 얘기인지**를 먼저 가려야 한다. 셋이 조건이 전혀 다르다.

```
① 클라이언트 ─────────────→ Edge Base        바깥  · 지금 RPC 스타일 · REST 권고
② Edge Base ──전용 파이프──→ 플러그인 프로세스   안   · RPC · 유지
③ 플러그인 ←──────────────→ 플러그인          경로 없음
```

| 구간 | 지금 | 권고 |
| --- | --- | --- |
| ① 클라이언트 ↔ Edge | RPC 스타일 (`POST /…/call` + `operation`) | **REST로** |
| ② 호스트 ↔ 플러그인 | RPC (stdin/stdout JSON 프레임) | **그대로 유지** |
| ③ 플러그인 ↔ 플러그인 | **없음** | 지금은 불필요 |

⚠ **"플러그인끼리 RPC"가 아니다.** ②는 **호스트와 플러그인 사이**이고, ③은 **아예 경로가 없다.**

**③이 없는 것은 설계 의도다.**

- `plugin-first-design.md` §8 — "**플러그인 간 의존성**"이 명시적 제외 범위
- 구조적으로도 막혀 있다 — 호스트가 **플러그인마다 별도 프로세스 하나와 전용 파이프**를 주고, 그 파이프는 호스트하고만 연결된다
- 데이터도 같다 — "다른 서비스 데이터는 그 서비스의 **공개 유스케이스를 통해** 사용한다. 타 서비스 테이블에 직접 JOIN하거나 수정하는 계약을 제공하지 않는다"
- ⭐ 런타임에서 **강제**한다 — "호스트는 **전용 파이프의 실행 세션에서 소유 서비스를 결정**한다. Data 요청에 **다른 pluginId나 SQL을 넣을 수 없다**." 플러그인이 자기를 뭐라고 주장하든 믿지 않고 **어느 파이프로 들어왔는지**로 판정한다

**③이 언제 문제가 되나** — 업무 기능이 늘면 "영상 수집 플러그인이 환자 플러그인의 데이터를 봐야 하는" 상황이 온다. 그때 선택지는 둘이다.

- **호스트 경유 중계** — 권한 판정 지점이 한 곳에 남는다. 문서의 "공개 유스케이스를 통해"가 이쪽을 전제한 것으로 읽힌다
- **직접 연결** — 빠르지만 격리가 무너지고 플러그인 간 의존성·버전 문제가 생긴다

→ 아직 구현이 없으므로 **Scott에게 확인할 항목**이다(`02-Scott-질문지.md`).

### 7.1 먼저 분리해야 할 세 가지

비교에 들어가기 전에 **이 선택과 무관한 것**을 떼어 놓는다. 자주 섞여서 논의가 흐려진다.

| 흔한 오해 | 사실 |
| --- | --- |
| "RPC로 가면 TLS 문제가 해결된다" | ❌ **전송 보안은 API 스타일과 직교한다.** gRPC도 HTTP/2 위에서 돌고 TLS에 인증서가 똑같이 필요하다 |
| "REST로 가면 호스트가 플러그인 업무를 알아야 한다" | ❌ **경로 접두어 위임으로 해결된다**(7.3) |
| "RPC = gRPC" | ❌ RPC는 개념, gRPC는 구현체. vt-edge는 **둘 다 아닌 자체 JSON RPC 스타일**(§12) |

### 7.2 vt-edge 맥락에서의 비교

일반론이 아니라 **이 제품의 제약** 기준이다.

| 기준 | REST | RPC (현재) | vt-edge에서 중요한가 |
| --- | --- | --- | --- |
| 플러그인 디스패치 | 경로 접두어로 위임 | 단일 `/call` | **둘 다 가능** — 7.3 |
| 로그·관측 | `GET /devices`로 분리 | 전부 `POST /…/call` | ⭐ **매우 중요** — 장애 시 무엇이 느린지 안 보인다 |
| 게이트웨이 정책 | 경로로 걸린다 | 걸 지점이 없다 | ⭐ **매우 중요** — GW가 경로 기반 |
| 감사 추적 | 리소스가 URL에 있다 | payload를 열어야 안다 | ⭐ 중요 — 규제 요구 |
| 동시성·멱등 | `If-Match`·`Idempotency-Key` 표준 | 매번 직접 설계 | 중요 — 의료 데이터 |
| 액션형 동작 | 서브리소스로 표현 | 자연스럽다 | 보통 |
| 도구·클라이언트 생성 | OpenAPI 생태계 | 빈약 | 중요 |
| 브라우저 직접 호출 | 가능 | 가능(JSON이라) · gRPC면 불가 | 콘솔이 React |

### 7.3 ⭐ "RPC를 고른 이유"는 REST를 막지 않는다

현재 RPC인 이유는 명확하다 — **호스트가 플러그인의 업무를 몰라야 하기 때문**이다. 경로 라우팅 테이블을 호스트가 관리하면 플러그인이 설치·제거될 때마다 호스트가 흔들린다.

**그런데 REST로도 똑같이 된다.** 접두어까지만 호스트가 알고 나머지는 **해석하지 않고 통째로 넘기면** 된다.

```
POST /api/services/vatech.devices/devices/ct-01/calibrate
     └──── 호스트가 아는 부분 ────┘└──── 플러그인이 소유 ────┘
```

호스트는 `vatech.devices`까지만 보고 그 뒤를 **불투명하게 전달**한다. 플러그인이 그 아래에서 자기 REST를 설계한다.

> **이건 GW가 이미 하는 방식이다.** GW는 서브도메인으로 target을 정하고 경로와 body는 verbatim 통과시킨다. 내용을 전혀 모르면서 라우팅한다.

→ **"플러그인 디스패치 단순화"는 RPC를 택할 근거가 되지 못한다.**

### 7.4 REST가 유리한 네 가지 (vt-edge 한정)

**(1) GW의 정책·게이팅이 경로 기반이다**

GW 정책 모델에 `allowed_endpoints`가 있고 gw/1.1에서 endpoint 세분화를 활성화하기로 돼 있다. 호환성 매트릭스도 `apis[].path`를 쓴다.
→ **RPC면 전부 `/call` 하나라 정책도 게이팅도 걸 지점이 없다.**
→ Edge가 GW의 device가 되는 그림이면 이 차이가 그대로 드러난다.

**(2) 감사 로그가 리소스 축을 전제한다**

GW `audit_log`는 `resource_type`/`resource_id`로 "이 리소스의 변경 이력"을 조회한다. 의료기기 규제가 요구하는 추적성이다.
→ RPC는 리소스 개념이 URL에 없어 이 축을 만들려면 payload를 열어야 한다.

**(3) 동시성·멱등이 표준으로 풀린다**

vt-edge는 이미 revision으로 충돌을 감지하는데, 지금은 **body에 revision을 넣고 409**를 쓴다.
→ REST면 `If-Match` + `412`가 표준이고 멱등은 `Idempotency-Key`다. **GW도 이미 `Idempotency-Key`를 쓴다.**
→ 표준을 쓰면 재발명하지 않고 클라이언트 라이브러리가 그냥 동작한다.

**(4) 장애 대응이 달라진다**

로그에 `POST /api/services/x/call`이 1만 줄 쌓이면 무엇이 느린지 모른다. 메트릭도 경로 단위로 안 나온다. 현장 장애에서 이 차이는 크다.

### 7.5 RPC가 진짜 맞는 자리 — 구간 ②

**호스트↔플러그인 내부 파이프**다(§5 하단·§7.0의 ②). 여기는 바꿀 이유가 없다.

- 외부 계약이 아니라 **내부 전송**이다
- 양방향이고 요청·응답이 섞여 흐른다 — `invoke` 처리 중에 `data` 요청이 역방향으로 온다
- HTTP 의미론이 필요 없다

반대로 **②를 REST로 바꾸면 얻는 게 없다.** 중간자가 없어 경로로 판단할 주체가 없고, 양방향 스트림을 HTTP에 억지로 맞춰야 한다.

### 7.6 권고 — 바깥(①)은 REST, 안(②)은 RPC

```
① 클라이언트 ──REST──> Edge Base ──경로 접두어로 위임──> 플러그인
                           └──② RPC(전용 파이프)──> 플러그인 프로세스
                           ③ 플러그인끼리 직접 경로는 없음
```

#### 왜 구간마다 다른가 — 조건이 다르다

| 조건 | ② 안 | ① 밖 |
| --- | --- | --- |
| 소비자를 통제할 수 있나 | **가능** — 우리가 만든 플러그인, 같이 배포된다 | **불가** — CleverOne·EzDent-i·브라우저가 각자 속도로 움직인다 |
| 계약이 깨지면 | 같은 릴리즈에서 양쪽을 고친다 | **한 번 깔리면 몇 년 간다** |
| 중간자가 있나 | **없다** — 전용 파이프 하나뿐 | **있다** — GW·프록시·감사·모니터링 |
| 적합한 방식 | RPC | **REST** |

⭐ **중간자 유무가 핵심이다.** 밖에는 GW·프록시·감사가 중간에 있고 **이들은 내용을 모른 채 판단해야 한다.**

- REST는 메서드와 경로에 의미가 있어 **body를 열지 않고도** 판단한다
- RPC는 전부 `POST /…/call`이라 **body를 열어야** 무엇을 하는지 안다

GW가 정확히 그런 중간자다 — body는 verbatim 통과시키면서 **경로로** 정책(`allowed_endpoints`)·호환성 게이팅(`apis[].path`)·감사(`resource_type`)를 건다. RPC면 그 셋이 전부 걸 지점을 잃는다.

그리고 소비자를 통제할 수 없으니 **밖은 표준을 써야 한다** — `If-Match`·`Idempotency-Key`·표준 상태코드. 직접 발명하면 클라이언트마다 다르게 구현하고 그걸 평생 지원하게 된다.

> 즉 **"둘을 섞자"가 아니라 "조건이 다르니 각자에게 맞는 걸 쓰자"** 는 얘기다.

- **클라이언트가 보는 면은 REST** — 리소스는 URL에, 의미는 메서드에, 동시성·멱등은 표준 헤더로
- **호스트는 `/api/services/{pluginId}/` 까지만 알고 뒤는 불투명 전달** — 플러그인 설치·제거에 호스트 불변
- **호스트↔플러그인 내부 파이프는 지금처럼 RPC**
- **액션형 동작은 서브리소스로** — `POST /devices/{id}/calibrate`. 전부 리소스로 욱여넣을 필요는 없다

두 방식을 섞는 게 아니라 **경계마다 맞는 모양**을 쓰는 것이다.

### 7.7 ⚠ 지금 정해야 하는 이유

프로토타입 단계에서 RPC는 **합리적인 선택이었다.** 플러그인 둘로 경계를 검증하는 데는 통로 하나가 간단하다.

문제는 **업무 플러그인이 늘어난 뒤에는 못 바꾼다**는 것이다. 플러그인이 다섯 개 되고 클라이언트가 붙기 시작하면 전환 비용이 급등한다.

> **지금은 플러그인 둘이고 클라이언트는 콘솔뿐이라 가장 싼 시점이다.**

### 7.8 gRPC는 어떤가

| 면 | 판단 | 이유 |
| --- | --- | --- |
| 클라이언트 면 | ❌ **부적합** | 브라우저에서 직접 못 쓴다(gRPC-Web 프록시 필요). 콘솔이 React다. LAN 클라이언트도 전부 바꿔야 한다 |
| 호스트↔플러그인 | ⭕ **후보** | `.proto` 코드 생성 · 양방향 스트리밍 기본 · **다른 언어 플러그인에 유리**(§6) |

→ 다언어 플러그인(C++ 장비 SDK 등)이 전제가 되면 내부 파이프의 다음 단계로 검토할 값어치가 있다. **지금 바꿀 이유는 없다** — 현재 stdin/stdout JSON은 의존성 0이고 디버깅이 쉽다.

## 8. 구간 ② 선택지 — 호스트↔플러그인 내부 통신

> §7이 ①번(클라이언트↔Edge)을 다뤘다면 이 절은 **②번(호스트↔플러그인)**의 기술 선택지다.
> ②는 **내부**라 나중에 바꿔도 된다 — 호스트와 플러그인이 같이 배포되기 때문이다. ①과 급한 정도가 다르다.

### 8.1 두 층으로 나눠서 봐야 한다

"RPC 대신 무엇"을 논할 때 자주 층이 섞인다. 먼저 가른다.

| 층 | 무엇을 정하나 | 보기 |
| --- | --- | --- |
| **전송(transport)** | 바이트를 어떻게 주고받나 | stdin/stdout · Unix socket · named pipe · 공유메모리 · 로컬 TCP |
| **프로토콜·계약** | 그 바이트를 어떻게 해석하나 | 자체 JSON · JSON-RPC 2.0 · tarpc · gRPC |

흔히 거론되는 이름들을 이 기준으로 재배치하면 이렇다.

- **IPC** — 전송 계층의 **총칭**이다. RPC의 대안이 아니라 **RPC가 올라타는 바닥**
- **IPC-RPC** — 기술 이름이 아니라 "IPC 위에서 도는 RPC"라는 서술
- **interprocess** — Rust 라이브러리이고 **전송만** 다룬다(named pipe·Unix socket). RPC가 아니다
- **JSON-RPC** — **프로토콜 스펙**이다. 전송은 무관
- **tarpc** — Rust 라이브러리로 **프로토콜 + 코드생성**. 전송은 갈아끼운다

→ `tarpc + interprocess`는 "프로토콜 + 전송" 조합이라 **짝이 맞는 제안**이다.

### 8.2 현재 조합과 그 제약

```
전송      stdin/stdout (자식 프로세스 파이프)
프레이밍  줄 단위 JSON · 자체 정의 {"type":"invoke","request_id":…}
계약      Rust serde 구조체 (plugin-sdk 90줄)
```

문서에 적힌 현재 제약은 이렇다.

> 프레임 최대 **256 KiB** · 호출당 DB 요청 최대 16개 · 응답 대기와 파이프 전송에 **4초** 제한
> 데이터 API는 작은 장비 목록용이며 컬렉션 100개·레코드 2 KiB, **직렬 호출** 등 제한이 있다

⭐ **핵심은 "직렬 호출"이다.** 단일 stdin/stdout 스트림이라 동시 요청을 못 한다 — 다중화를 직접 구현해야 하는데 아직 안 했다.

⚠ 그리고 **영상이 들어오면 256 KiB 프레임으로는 성립하지 않는다.** 다만 이건 전송을 바꿔 풀 문제가 아니다 — **바이트를 이 파이프로 보내면 안 된다.** 경로나 핸들만 주고받고 데이터는 파일시스템으로 가야 한다.

### 8.3 전송 층 선택지

| 방식 | 유리한 점 | 불리한 점 |
| --- | --- | --- |
| **stdin/stdout** (현재) | 의존성 0 · **프로세스 수명과 자동 연동**(죽으면 파이프가 닫힘) · 디버깅 쉬움 | 단일 스트림이라 **다중화 직접 구현** · 대용량 비효율 |
| **Unix socket / named pipe** (`interprocess`) | 전이중 · 다중 연결 · 백프레셔 | 소켓 파일 정리·고아 처리 · 권한 설정 |
| **공유메모리** | **대용량 제로카피** | 동기화 복잡 · 안전성 부담 |
| **로컬 TCP** | 도구가 많음 | 포트 관리 · 같은 PC의 다른 프로세스가 붙을 수 있음 |

### 8.4 프로토콜 층 선택지

| 방식 | 코드생성 | 언어중립 | 변화 적응 | 비고 |
| --- | --- | --- | --- | --- |
| 자체 JSON (현재) | ✕ | △ 수동 | ❌ `deny_unknown_fields` 탓(8.6) | 90줄, 단순 |
| **JSON-RPC 2.0** | ✕ | ⭕ 스펙 표준 | ⭕ | 전환 비용 가장 낮음 |
| **tarpc** | ⭕ Rust 매크로 | ❌ **Rust 전용** | ⭕ serde 정책에 달림 | Rust 확정이면 최고 |
| gRPC | ⭕ | ⭕ | ⭕⭕ unknown field 보존 | 다언어·스트리밍 |
| Cap'n Proto·FlatBuffers | ⭕ | ⭕ | ⭕ | 대용량 제로카피 |

> **Scott의 현재 설계는 JSON-RPC가 아니다** — `jsonrpc` 문자열이 코드·문서 어디에도 없고 필드명도 다르다. 상세 대조는 §13.

### 8.5 현재 방식 vs tarpc — 상세 비교

#### 계약을 표현하는 방법이 다르다

**지금 — 계약이 프레임 enum이고, 분기는 문자열 매칭이다.**

```rust
#[serde(tag = "type", rename_all = "snake_case", deny_unknown_fields)]
pub enum ServiceFrame {
    Invoke     { request_id: String, call: ServiceCall },
    Data       { request_id: String, call_id: String, request: DataRequest },
    DataResult { request_id: String, result: ServiceResult },
    Result     { request_id: String, result: ServiceResult },
}
```

```rust
loop {
    match read_line_json()? {
        ServiceFrame::Invoke { request_id, call } => {
            let result = match call.operation.as_str() {        // ← 문자열 매칭
                "devices.register" => register(call.data),
                "devices.list"     => list(),
                _ => Err(ServiceError::new("unknown_operation")),
            };
            write_line_json(ServiceFrame::Result { request_id, result })?;
        }
        ServiceFrame::DataResult { request_id, result } => {
            pending.remove(&request_id)?.send(result);          // ← 상관 직접 관리
        }
        _ => {}
    }
}
```

**tarpc — 계약이 trait이고, 분기가 사라진다.**

```rust
#[tarpc::service]                       // 호스트 → 플러그인
pub trait DeviceService {
    async fn register(device: NewDevice) -> Result<Device, ServiceError>;
    async fn list() -> Result<Vec<Device>, ServiceError>;
    async fn set_enabled(id: String, enabled: bool, revision: u64) -> Result<Device, ServiceError>;
}

#[tarpc::service]                       // 플러그인 → 호스트 (역방향)
pub trait DataApi {
    async fn get(collection: String, key: String) -> Result<Option<Record>, ServiceError>;
    async fn put(collection: String, key: String, value: Value, revision: Option<u64>) -> Result<Record, ServiceError>;
    async fn list(collection: String) -> Result<Vec<Record>, ServiceError>;
}
```

```rust
impl DeviceService for DeviceServer {
    async fn register(self, _: Context, device: NewDevice) -> Result<Device, ServiceError> {
        // 역방향 호출이 그냥 await — call_id 상관이 사라진다
        let existing = self.data.get(context::current(), "devices".into(), device.id.clone()).await??;
        if existing.is_some() { return Err(ServiceError::conflict("duplicate id")); }
        ...
    }
}
```

호스트 쪽은 `let devices = client.list(context::current()).await??;` 한 줄이다.

> 위 코드는 **개략**이다. tarpc 실제 시그니처·버전별 세부는 도입 시 확인이 필요하다.

#### 무엇이 사라지나

| 지금 직접 구현 | tarpc |
| --- | --- |
| `ServiceFrame` enum 4종 | trait 메서드 |
| `request_id` 발급·상관, `pending` 맵 | 라이브러리 |
| 응답 대기 4초 타임아웃 | `Context::deadline` |
| `operation` 문자열 매칭 + `unknown_operation` 분기 | **컴파일 타임 검사** |
| `call_id`로 역방향 호출 상관 | `await` 한 줄 |
| **"직렬 호출" 제약** | **다중화 기본** |
| 프레임 256 KiB 제한 | transport 설정 |

가장 큰 둘은 **다중화**와 **타입 안전**이다. 지금 `"devices.registar"` 같은 오타는 런타임에야 드러나는데 trait이면 빌드가 막는다.

#### 종합 비교

| 기준 | 현재 (자체 JSON 프레임) | tarpc |
| --- | --- | --- |
| 계약 표현 | JSON 프레임 enum | **Rust trait** |
| 오타·불일치 검출 | 런타임 | **컴파일 타임** |
| 동시 요청 | **직렬** | **다중화** |
| 역방향 호출 | `call_id` 상관 직접 | `await` |
| 타임아웃·에러 전파 | 직접 구현 | 라이브러리 |
| 양방향 전송 | **해결됨**(단일 스트림 + `type` 태그) | ⚠ **다시 설계 필요**(8.5 아래) |
| 의존성 | **0** | tarpc + transport + serde 포맷 |
| 프로세스 수명 연동 | **자동**(파이프가 닫힘) | 연결 관리 필요 |
| 다언어 | 어려움(가능은 함) | ❌ **불가** |
| 디버깅 | JSON을 눈으로 본다 | bincode면 불가 · JSON transport면 완화 |
| wire에 Rust 노출 | `{"Ok"/"Err"}` 있음 | 포맷에 따라 다름 |

#### ⚠ tarpc가 공짜가 아닌 부분 — 양방향

서비스가 **둘이고 방향이 반대**다.

```
DeviceService : 호스트 → 플러그인
DataApi       : 플러그인 → 호스트
```

tarpc는 보통 한 연결에 한 서비스다. 선택지는 둘이다.

- **연결 2개** — named pipe를 둘 열어 방향별로 쓴다. 단순하지만 수명주기 관리가 두 배
- **한 전송에 다중화** — 직접 얹어야 한다

현재는 단일 stdin/stdout에 `type` 태그로 네 종류를 섞어 흘려서 **이 문제를 이미 푼 상태**다. tarpc로 가면 여기를 다시 설계해야 한다.

#### ⭐ 오히려 개선되는 것

지금은 `call_id`로 "어느 invoke가 낸 data 요청인가"를 추적해 **데이터 소유권을 판정**한다.

tarpc + 연결 기반이면 **연결 자체가 세션**이 된다. "이 연결 = 이 플러그인"이 자명해져 소유권 판정이 더 단순하고 안전해진다. 문서가 강조하는 "자칭 `pluginId`를 믿지 않는다"가 **구조로 보장**된다.

### 8.6 ⚠ 더 급한 것 — 변화 적응

플러그인은 **추가·변경·업그레이드**가 계속 일어난다. 이 축에서 보면 현재 설계에 함정이 둘 있고, **전송·프로토콜 교체보다 이게 먼저다.**

#### 함정 1 — `deny_unknown_fields`

```rust
#[serde(deny_unknown_fields)]  pub struct ServiceError
#[serde(deny_unknown_fields)]  pub struct Record
```

모르는 필드가 오면 **거부**한다. 엄격해서 좋아 보이지만 진화에는 최악이다.

- 호스트가 새 필드 추가 → **구버전 플러그인이 거부**
- 플러그인이 새 필드 추가 → **구버전 호스트가 거부**
- 결국 **양쪽을 동시에 교체해야만** 동작한다

Protobuf가 모르는 필드를 보존·무시하는 이유가 이것이다(전진 호환).

> 참고 — 이건 **tarpc와 무관한 serde 설정 문제**다. tarpc로 가도 이 정책을 안 바꾸면 그대로 남는다.

#### 함정 2 — 정확히 일치 요구

> 첫 버전은 지원하는 `schemaVersion`, `hostApiVersion`, 플랫폼이 **정확히 맞아야** 설치할 수 있다

여기에 SDK 버전도 `=0.2.0`으로 핀돼 있다. **즉 진화를 허용하지 않고 "같이 올려라"로 푼 것**이다. 플러그인 둘이고 전부 우리가 만들 땐 성립하지만, 열 개가 되거나 벤더가 만들면 성립하지 않는다.

#### 그래서 전송·프로토콜보다 먼저 정할 셋

| # | 결정 | 효과 |
| --- | --- | --- |
| 1 | **unknown field 정책을 무시로 바꿀 것인가** | 지금 구조 그대로 **전진 호환** 확보. 가장 싸고 효과 크다 |
| 2 | **버전을 정확 일치 → capability 협상으로** | 부분 호환 가능. 호스트가 "이 플러그인은 X를 모른다"로 분기 |
| 3 | **플러그인이 자기 operation을 런타임에 선언** | 새 플러그인 추가 시 **콘솔 코드 0** |

⭐ **3번은 GW에서 쓴 방법과 같다** — device 카탈로그가 "무엇을 연동할 수 있나 + 무엇을 입력받아야 하나(`fields[]`)"를 내려줘 화면을 동적 렌더하게 한 것. vt-edge에는 그 장치가 아직 없다.

> 1번의 대가 — 오타가 조용히 통과한다. 절충은 **계약 필드는 엄격, 확장 영역은 관대**로 나누는 것이다.

### 8.7 권고와 우선순위

| 순위 | 할 일 | 왜 지금 |
| --- | --- | --- |
| **1** | ① 클라이언트 면을 REST로 (§7) | **나중엔 못 바꾼다** |
| **2** | unknown field · capability · operation 디스커버리 (8.6) | 설계 원칙이라 늦으면 전부 뜯는다 |
| **3** | ② tarpc 전환 | **Rust 전용이 확정된 뒤** |

**②를 3순위에 둔 이유**는 넷이다.

1. **전제가 미확정** — "Rust 전용"이 확정돼야 성립한다. 장비 SDK(C++) 가능성이 실재하고, tarpc는 그 층을 Rust에 **못 박는다**
2. **지금 아프지 않다** — 플러그인 둘. "직렬 호출" 제약이 실제 문제를 내고 있는지 미확인
3. **공짜 교체가 아니다** — 양방향 전송을 다시 설계해야 한다
4. ⭐ **②는 내부라 나중에 바꿔도 된다** — 호스트와 플러그인이 **같이 배포**되므로 SDK를 올리면 플러그인도 따라온다. 반면 ①은 외부라 나중에 못 바꾼다. **바꿀 수 없는 것부터 정하는 게 맞다**

그리고 2번이 3번보다 앞인 이유는 **그 셋을 tarpc가 해주지 않기 때문**이다. 변화 적응에는 그쪽이 훨씬 직접적이다.

> ②를 안 바꿔도 **문제는 없다.** 지금 구조는 의존성 0이고 프로세스 수명과 자동으로 엮인다. tarpc는 "더 나은 선택"이지 "고쳐야 할 결함"이 아니다.

## 9. LAN 구간 TLS와 사설 CA

> vt-edge 문서에는 아직 이 주제가 없다. 다만 **EzServer가 인증 심사에서 실제로 걸린 지점**이고, Edge는 클라이언트를 새로 배포하므로 **지금이 구조를 바꿀 수 있는 유일한 시점**이라 정리해 둔다.

### 9.1 문제 — 왜 LAN TLS가 어려운가

공인 CA(DigiCert·Let's Encrypt 등)는 **도메인 소유를 검증할 수 있을 때만** 발급한다. `192.168.1.50`이나 `edge.local` 같은 LAN 이름은 소유를 증명할 방법이 없어 **발급 자체가 거부**된다.

EzServer가 막힌 경로가 이것이다.

1. 공인 인증서를 못 받는다
2. → self-signed로 간다
3. → 클라이언트마다 그 인증서를 신뢰 저장소에 심어야 하는데 클리닉 IT가 못 한다
4. → **클라이언트가 검증을 끈다**
5. → 암호화는 하지만 **상대를 확인하지 않으므로** LAN 안에서 가로채기가 그대로 성립한다

⭐ **4번이 핵심이다.** 문제는 "인증서가 self-signed라서"가 아니라 **"검증을 끌 수밖에 없어서"** 다.

### 9.2 심사가 보는 것

규제는 "SSL을 써라"라고 하지 않는다. 묻는 것은 넷이다.

- 전송 구간을 보호하는가
- **상대를 인증하는가**
- 키와 인증서를 **누가 발급·회전·폐기하는가**
- 그 과정이 **통제되고 기록되는가**

`self-signed + 검증 끄기`는 두 번째부터 답이 없다. **통제가 없다는 것**이 문제이지 암호화 유무가 아니다. 유럽 시장(MDR·MDCG 2019-16)도 같은 결이다.

### 9.3 사설 CA란

**우리가 운영하는 인증 기관**이다. 외부 업체가 아니라 "공인 CA가 아니다"라는 뜻이다.

> self-signed와의 차이는 **"누가 보증하느냐"** 다. self-signed는 자기가 자기를 보증하니 검증할 게 없고, 사설 CA는 **공통의 발급자**가 있어 클라이언트가 **그 하나만** 신뢰하면 된다.

구성 요소는 넷이다.

| | 무엇 | 비고 |
| --- | --- | --- |
| 루트 키·인증서 | 최상위 신뢰 앵커 | **보관이 가장 중요** |
| 발급 절차 | CSR 제출 → 서명 → 인증서 반환 | 개인키가 Edge를 떠나지 않음 |
| 신뢰 배포 | 클라이언트가 루트를 신뢰 저장소에 가짐 | **설치 프로그램 몫** |
| 수명주기 | 갱신 · 폐기(CRL/OCSP) · 키 회전 | 심사 대상 |

### 9.4 세 가지 방안

| | ① 클리닉별 로컬 CA | ② AWS Private CA | ③ OpenBao를 AWS에 직접 구축 |
| --- | --- | --- | --- |
| CA 위치 | **각 Edge 안** | AWS 관리형 | **우리가 AWS에 세움** |
| 루트 키 보관 | 클리닉마다 | AWS HSM | **AWS KMS**(auto-unseal) |
| 클라이언트가 신뢰할 것 | **클리닉 수만큼** | 루트 하나 | 루트 하나 |
| 고정비 | 0 | **CA당 월 $400 수준** | 컴퓨트 + KMS 키(낮음) |
| 발급 비용 | 0 | 건당 과금 | 0 |
| 운영 부담 | 낮음(분산) | **거의 없음** | **구축 + 상시 운영** |
| 키 유출 반경 | **그 클리닉만** | 전체 | 전체 |
| 폐기·회전 통제 | **중앙 불가** | 중앙 | 중앙 |
| 심사 입증 | **어렵다**(CA가 N개) | **쉽다** | 가능하나 문서화 부담 |
| **완전 격리(C) 클리닉** | ⭕ **유일하게 동작** | ❌ 갱신 불가 | ❌ 갱신 불가 |
| 구현 도구 | **로컬 OpenBao**(이미 있음) | AWS 관리형 | **중앙 OpenBao**(별도 인스턴스) |

> ⭐ **축은 "OpenBao냐 AWS냐"가 아니라 "CA를 어디에 두느냐"다.** OpenBao는 ①의 구현체도 ③의 구현체도 될 수 있다. 도구를 OpenBao로 한다고 ①의 약점이 사라지지 않는다.
>
> ⚠ **그리고 이 셋이 최종 선택지가 아니다.** 오프라인 클리닉(9.5)을 넣으면 **9.6.1 하이브리드**가 답이 된다 — 중앙에 루트, Edge마다 중간 CA. 아래 셋은 그 결론에 이르기 위한 비교로 읽을 것.

#### ① 클리닉별 로컬 CA

Edge가 자기 CA를 들고 자기 서버 인증서를 발급한다. 클라이언트 설치 프로그램이 **그 클리닉 Edge에서 CA를 받아** 심는다.

**도구는 이미 있다.** `security/README.md`를 보면 OpenBao는 **Edge 머신에 로컬 설치**된다 — `edge-security up`이 OpenBao 2.6.2를 내려받아(SHA-256 고정) 백그라운드로 띄우고 봉인을 해제한다. Transit이 거기 얹혀 있으므로 **PKI는 엔진 하나 더 켜는 일**이고 새 컴포넌트가 필요 없다.

- ⭕ 가장 싸고 빠르다. 중앙 인프라가 없다
- ⭕ 키 유출 반경이 **그 클리닉으로 제한**된다
- ❌ **초기 신뢰 문제(TOFU)** — 설치 시점에 "지금 받은 이 CA가 진짜인가"를 검증할 방법이 없다. 그 순간 가로채면 그대로 뚫린다
- ❌ 클라이언트가 **여러 클리닉에 붙으면** CA가 여러 개가 된다
- ❌ **중앙에서 폐기·회전이 불가**하다. 심사에서 "N개 CA를 어떻게 통제하느냐"에 답하기 어렵다
- ❌ **auto-unseal을 KMS로 걸 수 없다** — 오프라인 동작이 전제이므로 unseal 수단이 **그 머신에** 있어야 한다. 머신을 장악하면 CA 키가 넘어간다
- ⚠⚠ **키 서비스 복구가 아직 안 된다** — `security/README.md`가 "다른 장비로의 전체 복구에는 OpenBao Raft 스냅샷, 원본 복구 지분, 설치 ID와 인증 재발급이 추가로 필요"하고 **"키 서비스까지 새 장비로 복원하는 자동화는 아직 미제공/미검증"**이라고 명시한다

⭐ **마지막 항목이 결정적이다.** 여기에 CA 키까지 얹으면 **Edge 장비 고장 = 그 클리닉 CA 소실 = 클라이언트 전부 재설치**가 된다. 중앙 CA라면 새 장비에 인증서만 다시 발급하면 끝이다.

덧붙여 OpenBao 구동이 아직 "**Windows 서비스 설치·자동 부팅 등록·프로세스 감독기가 아닌 개발 도구**"라고 적혀 있어, ①을 가려면 그 운영 형태부터 만들어야 한다.

#### ② AWS Private CA

AWS 관리형 CA. 루트 키를 AWS HSM이 보관하고 발급 이력은 CloudTrail에 남는다.

- ⭕ **"키를 사람이 들고 있지 않다"를 설명하기 가장 쉽다**
- ⭕ CRL·OCSP가 기본. 운영 부담이 거의 없다
- ⭕ GW가 이미 AWS에 있고 enroll이 AWS IoT를 쓰므로 **운영 경로가 같다**
- ❌ **고정비가 붙는다** — CA당 월 $400 수준
- 짧은 수명 모드는 더 싸지만 **자동 갱신이 전제**다. ⚠ Edge가 오프라인인 동안 만료되면 LAN이 죽으므로 수명을 넉넉히(예: 1년) 잡는 편이 안전하다

#### ③ OpenBao PKI를 AWS에 직접 구축

⚠ **①의 로컬 OpenBao와는 별개 인스턴스다.** 제품만 같고 위치·역할·unseal 방식이 다르다.

| | ① 로컬 OpenBao | ③ 중앙 OpenBao |
| --- | --- | --- |
| 위치 | Edge 머신마다 | AWS에 하나 |
| 쓰는 엔진 | Transit(+PKI 가능) | PKI |
| unseal | 그 머신에서 자동 | **AWS KMS** |
| 복구 | ⚠ 미제공/미검증 | 우리가 설계 |

```
ECS/EKS 또는 EC2 ─ OpenBao (PKI 엔진)
                    ├─ 스토리지: Raft 통합 또는 PostgreSQL/S3
                    └─ ⭐ auto-unseal: AWS KMS
```

OpenBao PKI는 사설 CA에 필요한 것을 다 갖고 있다 — 루트/중간 CA 발급, 역할 기반 발급 정책(허용 도메인·최대 수명·키 타입), CSR 서명, **CRL 자동 생성·OCSP 응답기 내장**, 폐기 API.

- ⭐ **`auto-unseal`을 AWS KMS로 거는 것이 핵심이다.** 그러면 **"루트 키를 사람이 들고 있지 않다"가 성립**해 ②의 가장 큰 장점을 상당 부분 가져온다. KMS 키 비용은 월 1달러 수준
- ⚠ auto-unseal 없이 운영하면 재기동마다 사람이 unseal 키를 넣어야 한다. **운영도 심사도 곤란하므로 선택이 아니라 필수**로 봐야 한다
- ⭕ **vt-edge가 이미 OpenBao를 쓴다**(Edge 로컬은 Transit 암호화, 중앙은 PKI). 역할은 달라도 같은 제품이라 운영 지식이 공유된다. 라이선스 0
- ❌ **백업·복구가 가용성보다 중요하다** — 루트 키를 잃으면 복구 불가다. 복구 연습까지 해 둬야 한다
- ❌ 심사에서 발급·갱신·폐기 절차를 **우리가 문서화하고 지켰음을 보여야** 한다

> **가용성 요구는 생각보다 낮다.** 인증서 발급은 enroll과 갱신 때만 일어나고 상시 트래픽이 아니다. CA가 몇 시간 내려가도 **이미 발급된 인증서는 유효**하므로 클리닉 서비스는 멈추지 않는다. 신규 설치만 지연된다.

### 9.5 ⚠ 오프라인 클리닉이라는 제약

⭐ **②와 ③은 "인터넷이 된다"를 전제한다. 그런데 vt-edge는 오프라인 동작을 설계 원칙으로 못 박아 놨다.**

| 근거 | 문장 |
| --- | --- |
| `docs/plugin-first-design.md` | "**인터넷 연결 없이도** 이미 설치한 플러그인은 실행할 수 있다" |
| `security/README.md` | "**인터넷이 끊겨도** 로컬 키 서비스가 정상 동작하면 읽기·쓰기가 가능합니다" |
| `ui/README.md` | "No CDN or runtime network download is needed" |

그리고 EzServer는 독립 제품이라 **외부 연결 없이 내부망으로만 쓰는 클리닉이 실제로 있다.** 중앙 CA는 그 전제와 충돌한다.

#### 9.5.1 "외부 연결 없음"을 셋으로 갈라야 한다

| | 실제 상황 | 중앙 CA가 되나 |
| --- | --- | --- |
| **A. inbound 차단 · outbound 가능** | 방화벽이 바깥에서 들어오는 것만 막음 | ⭕ **문제 없음** — Edge가 먼저 걸면 됨 |
| **B. 가끔 연결** | 평소 끊겨 있고 이따금 붙음 | ⭕ 갱신 여유를 크게 잡으면 됨 |
| **C. 완전 격리** | 진짜로 바깥과 끊김 | ❌ **깨진다** |

⭐ **현장에서 "외부 연결 없다"는 말의 대부분은 A다.** A는 중앙 CA에 아무 문제가 없다 — 발급도 갱신도 Edge가 먼저 걸면 된다.

**문제는 C뿐이고, C가 실제로 얼마나 있는지가 먼저 확인할 사실이다.**

#### 9.5.2 C에서 깨지는 것 — 발급보다 갱신이 치명적이다

| | 영향 |
| --- | --- |
| 발급 | 설치 때 **한 번**이라 USB로 CSR을 들고 나왔다 들어가는 것도 어떻게든 된다 |
| **갱신** | ⚠ **1년마다 반복된다.** 자동화가 안 되면 **1년마다 LAN이 죽고 C/S가 나간다** — 우리가 없애려던 바로 그것 |
| 폐기 확인(CRL·OCSP) | 받으러 갈 수 없다. **격리망의 구조적 한계**로 인정해야 한다 |

#### 9.5.3 ⭐ 반전 — 격리망에서는 ①이 유일하게 동작한다

9.4에서 ①을 약하다고 봤지만 **C 시나리오에서는 ①만 된다.** Edge가 자기가 발급하고 자기가 갱신하니 인터넷이 전혀 필요 없다.

→ **그래서 답은 ①/②/③ 중 하나를 고르는 것이 아니라 9.6의 하이브리드다.**

#### 9.5.4 TLS만의 문제가 아니다 — 제품 등급 질문이다

C 클리닉이면 이것들이 **전부** 안 된다.

- **자동 업데이트** — ⚠ 우리가 풀려던 핵심 문제인데 격리 클리닉은 여전히 C/S 출동이다
- **호환성 매트릭스 조회** — 무엇을 올려도 되는지 못 받아온다
- **GW device enroll** — 안 된다. "Edge가 GW의 device가 된다"는 그림이 성립하지 않는다
- **원격 백업** — `security/README.md`에 있는 기능인데 안 된다
- **CleverSpace 연동·동기화** — Edge의 존재 이유 중 하나인데 안 된다

⭐ **Edge의 포지셔닝이 "클라우드 플랫폼의 현장 말단"(§1)인데 C 클리닉은 클라우드에 안 붙는다.** EzServer는 독립 제품이라 가능했던 것이고, Edge로 가면서 그 고객을 어떻게 할지가 정해져야 한다.

| 선택 | 의미 |
| --- | --- |
| **오프라인 등급을 만든다** | 로컬 기능만 · 업데이트는 수동 · 명시적으로 축소된 제품 |
| **온라인을 요구한다** | C 고객을 받지 않거나 전환시킨다 |
| **A·B만 지원한다** | outbound만 열면 된다고 요구 — ⭐ **가장 현실적일 수 있다** |

### 9.6 ⭐ 어느 쪽을 고르든 먼저 정할 것 — 루트/중간 분리

```
루트 CA     오프라인 보관 · 장수명(10~20년) · 평소엔 쓰지 않음
  └─ 중간 CA   실제 발급 담당 · 수명 짧게 · 교체 가능
       └─ Edge 서버 인증서
```

**루트를 나중에 바꾸는 것은 거의 불가능하다.** 클라이언트에 심은 신뢰 앵커를 바꾸려면 **전 클라이언트를 다시 배포**해야 한다.

루트/중간을 나누면

- 클라이언트는 **루트만** 신뢰한다 — 한 번 심으면 끝
- **중간 CA는 교체 가능**하다 — ③으로 시작했다가 ②로 옮겨도 클라이언트는 그대로
- 중간 키가 유출돼도 **그 중간만 폐기**하면 된다

즉 **"②냐 ③이냐"를 지금 확정하지 않아도 되게 만드는 장치**다.

#### 9.6.1 ⭐⭐ 오프라인 대응형 — 중간 CA를 Edge에 둔다

9.5의 C 문제는 **이 분리를 한 단계 더 쓰면** 풀린다.

```
중앙 루트 CA (오프라인 보관 · 10~20년)
  └─ Edge별 중간 CA      ← 설치·온보딩 때 1회만 발급 · 수명 길게(5~10년)
       └─ 서버 인증서      ← Edge가 로컬에서 발급·갱신 · 인터넷 불필요
```

- 클라이언트는 **중앙 루트 하나만** 신뢰한다 — ①의 **TOFU 문제가 사라진다**
- 서버 인증서 **갱신이 로컬**이다 — 인터넷 불필요. **오프라인 설계 원칙을 지킨다**
- 온라인이 필요한 건 **설치 때 중간 CA 발급 1회**뿐이다

⭐⭐ **9.4에서 ①의 결정적 약점으로 지적한 것이 여기서 해소된다.** Edge 장비가 죽어도 **새 장비에 새 중간 CA를 발급하면 끝**이고, 중앙 루트가 살아 있으므로 **클라이언트는 그대로**다. 전부 재설치할 필요가 없다.

즉 **①의 오프라인 자립성 + ②③의 중앙 통제를 동시에 얻는다.** 루트/중간 분리가 "구현체 교체용 장치"가 아니라 **오프라인 대응의 핵심 메커니즘**이 된다.

**남는 위험과 완화**

- Edge가 중간 CA 키를 들고 있으므로 **머신을 장악하면 키가 넘어간다.** 다만 루트는 안전하고 **그 중간만 폐기**하면 되므로 반경이 제한된다
- X.509 **Name Constraints**로 그 중간 CA가 자기 이름 범위 밖을 발급하지 못하게 묶을 수 있다 — ⚠ 클라이언트별 지원이 고르지 않아 **검증이 필요하다**
- 격리망에서는 폐기를 전달할 길이 없다 — **한계로 인정**하고 중간 CA 수명으로 관리한다

### 9.7 진짜 큰 일은 신뢰 배포다

CA 운영보다 **클라이언트에 루트를 심는 일**이 실무의 대부분이다.

- **관리자 권한**이 필요하다 — 설치 시점에 한 번
- Chrome·Edge는 OS 저장소를 쓰므로 **같이 해결**된다
- ⚠ **Firefox는 자체 저장소**라 별도 처리가 필요하다
- 이미 깔린 클라이언트는 **업데이트 때** 심어야 한다

⭐ **그래서 Edge 출시가 유일한 기회다.** 클라이언트를 새로 배포하는 그 시점에 넣지 않으면 EzServer와 똑같이 "나중에 못 바꾸는" 상태가 된다.

### 9.8 권고와 결정 순서

**되돌릴 수 있는 것과 없는 것을 구분하는 게 핵심이다.**

| 순서 | 결정 | 되돌릴 수 있나 |
| --- | --- | --- |
| **1** | **클라이언트가 검증을 켤 수 있는가** | ❌ 클라이언트 재배포 시점에만 가능 |
| **2** | **완전 격리(C) 클리닉을 지원하는가** | ❌ 제품 등급 문제 — 9.5.4 |
| **3** | **루트/중간 분리 구조** | ❌ 루트 교체 = 전 클라이언트 재배포 |
| **4** | 중간 CA를 어디에 두는가 (중앙 / Edge) | △ C를 지원하면 Edge로 고정 |
| **5** | 루트 운영 구현체 (② / ③) | ⭕ **교체 가능** |

⚠ **1번이 전부다.** CA를 세워 놓고 클라이언트가 여전히 검증을 끄면 **아무것도 나아지지 않는다.** 돈만 쓴 것이 된다. 이건 인프라 작업이 아니라 **클라이언트 작업과 세트**다.

**2번이 나머지를 결정한다.**

- **C를 지원하지 않는다면** — 중간 CA를 중앙에 두는 단순한 구조로 간다. ②와 ③ 중 **돈이냐 운영 부담이냐**의 교환이고, 월 $400이 C/S 출동 한두 번 값이라는 점에서 ②가 설명하기 쉽다. ③은 OpenBao를 이미 쓰고 있다는 점이 크다
- **C를 지원한다면** — **9.6.1 하이브리드가 사실상 유일한 답**이다. 중앙에 루트, Edge마다 중간. 이때도 루트 운영은 ②/③ 어느 쪽이든 된다

> ⭐ **①을 단독으로 고르는 선택지는 사실상 없다.** C 대응이 필요하면 9.6.1이 ①의 상위 호환이고(중앙 루트가 붙어 TOFU·복구 문제가 사라진다), C가 없으면 ①을 쓸 이유가 없다.

### 9.9 GW 재사용 범위 — 주의

GW의 enroll은 AWS IoT Core의 `CreateCertificateFromCsr`를 쓴다. 즉 **AWS IoT의 CA**이고 그 인증서는 **IoT Core mTLS 전용**이라 LAN 서버 인증서로는 쓸 수 없다.

재사용할 수 있는 것은 **CA가 아니라 흐름**이다.

- 디바이스가 키페어를 만들고 **CSR만 제출**한다
- **개인키가 디바이스를 떠나지 않는다**
- 서버가 서명해 인증서를 돌려준다
- enroll 한 번으로 자격을 확립한다

이 패턴을 그대로 쓰되 **LAN용 CA는 별도로** 세워야 한다. enroll 응답에 IoT 인증서 옆에 LAN 서버 인증서를 하나 더 얹는 그림이다.

## 12. 용어 주의 — 헷갈리는 세 가지

**(1) "v2"가 두 가지를 가리킨다**

- **REST API v2 서버(RSV)** = 제품 이름. PHP EzWebServer를 대체하는 Rust 서버
- **`routes/v2`** = 그 서버 안의 신규 API 경로

대화에서 "v2"가 나오면 어느 쪽인지 먼저 맞춰야 한다.

**(2) RPC ≠ gRPC**

- **RPC** = 개념("원격 함수를 부른다"는 모양)
- **gRPC** = 구현체 하나 (HTTP/2 + Protobuf + `.proto` IDL)
- **vt-edge** = 둘 다 아님. 자체 정의한 JSON 기반 RPC 스타일

**(3) 계약이 있다 ≠ IDL이 있다**

vt-edge는 계약이 **있지만** Rust 소스 형태라 언어 중립이 아니다(§6).
