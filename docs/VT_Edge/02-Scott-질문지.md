## 0. 세션 전 머리에 넣을 것

지금 vt-edge 상태는 이렇다.

- Scott 단독 11커밋 · 2026-09 중순 작업
- 플러그인 2개 — `hello`(수명주기 검증) · `device-registry`(장비 등록)
- **의료영상 저장·장비 SDK·EzServer 연동·마이그레이션·업데이트·롤백은 전부 미착수**(문서에 명시적 제외)

"올해 개발"이면 **남은 기간이 3개월**이다. 같은 기간에 EzServer 팀은 VAG 연동과 PLAN-1330 병행 사용(10MD)을 해야 하고 GW는 10월 정식 오픈이다. **인력이 겹친다.**

⭐ 그래서 **"올해 무엇까지 만드나"가 가장 먼저 확인할 것**이다. 범위가 정해지면 나머지 답이 대부분 따라온다.

⚠ **그리고 잊지 말 제약 하나** — **외부 연결 없이 내부망으로만 쓰는 클리닉이 있다.** vt-edge도 오프라인 동작을 설계 원칙으로 명시했다("인터넷 연결 없이도 이미 설치한 플러그인은 실행할 수 있다"). 이 제약이 **TLS(§5)·자동 업데이트(§6)·GW 승계(§7)를 한꺼번에 가르므로** 질문할 때마다 "격리 클리닉에서도 되나"를 함께 확인할 것. 별도 항목으로 §8에 정리했다.

## 1. 올해 개발 범위가 어디까지입니까

플랫폼 뼈대(플러그인 호스트·Base)까지인지, 실제 업무 기능(영상·장비)까지인지.
내년 "출시"가 무엇을 파는 것인지도 같이 확인한다.

- **왜 묻나** — 지금 상태와 3개월 사이의 간극이 크다. 범위가 안 정해지면 나머지 논의가 공중에 뜬다
- **듣고 싶은 답** — 올해 산출물의 구체적 목록과 "이것은 내년"의 경계

## 2. 의료영상 저장 모델은 언제 설계합니까

현재 저장 모델은 `(service_id, collection, record_key)` + JSON 레코드 + revision이다.
문서도 선을 그어 뒀다 — "모든 임상 데이터를 JSON 레코드에 맞추기로 결정한 것이 아니다", "관계형 쿼리나 추가 고유 인덱스가 필요한 실제 서비스가 등장하면 서비스 소유 스키마와 마이그레이션 계약을 설계한다".

- **왜 묻나** — **제품의 본체가 여기인데 아직 설계 전이다.** 이 설계가 늦어지면 나머지가 다 바뀐다
- **같이 확인** — 영상 원본을 DB(BLOB)에 넣을 것인가, 파일로 두고 메타만 DB에 둘 것인가

---

### 2-1. 본격 환자·영상 관리에 SQLite로 충분합니까 — PostgreSQL 선택지는 열어 둡니까

질문이 세 겹이다. **엔진보다 모델이 먼저**다.

**(1) 저장 모델** — 현재는 `(service_id, collection, record_key)` + JSON 레코드다. 관계형 쿼리나 고유 인덱스가 필요한 임상 데이터는 이 모양이 아니다. 문서도 "**실제 서비스가 등장하면 서비스 소유 스키마와 마이그레이션 계약을 설계한다**"고 유보해 뒀다.

**(2) 엔진** — 모델이 정해진 뒤 따져야 할 것들.

- **영상 원본은 어차피 파일시스템**이므로 DB가 다루는 건 메타데이터다. 클리닉 한 곳 규모(환자 수만~수십만·영상 메타 수십만~수백만 행)는 **SQLite가 충분히 감당하는 범위**다
- ⚠ 걸리는 지점은 **동시 쓰기**다. SQLite는 writer가 하나이고 현재 `busy_timeout`이 **500ms**로 짧다. 영상 수집이 초당 수십 건을 쓰는 동안 다른 플러그인의 쓰기가 밀릴 수 있다
- ⚠ **복구 요구 수준** — SQLite는 백업 API·파일 스냅샷이고, PostgreSQL은 WAL 아카이빙과 **시점 복구(PITR)** 가 된다. 의료 데이터에서 "어제 14시 상태로" 요구가 있으면 설계가 달라진다
- 전문 검색·JSON·윈도 함수는 SQLite도 되지만 **파티셔닝·복제는 없다**

**(3) 철학과의 긴장** — Base가 SQLite를 내장한 이유는 "**운영자가 DB 서버를 설치하지 않는다**"이다. PostgreSQL을 넣으면 설치·초기화·백업·업그레이드가 한 겹씩 늘고 **단일 바이너리 장점이 사라진다.**

- **왜 묻나** — ⭐ **전환 대상 클리닉에는 이미 PostgreSQL이 깔려 있다**(EzServer가 쓴다). 그 환경에서는 "DB 서버 불필요"라는 장점이 성립하지 않는다
- **듣고 싶은 답** — SQLite를 끝까지 갈 것인지, 데이터 백엔드를 교체 가능하게 둘 것인지. **이 결정이 EzServer 데이터 이관 비용을 크게 가른다**(`03-Thomas-기술논의.md` §4)

## 3. 클라이언트가 보는 API를 REST로 갈 것입니까, RPC로 유지합니까

현재 `POST /api/services/{id}/call` + `operation`은 **RPC 스타일**이다. 리소스가 URL에 없고 메서드가 의미를 갖지 않는다.

플러그인 디스패치를 단순화한 선택으로 보이는데, **경로 접두어 위임**(`/api/services/{id}/**`를 해석 없이 플러그인에 전달)으로도 같은 목적이 달성되면서 REST가 가능하다. 우리 GW가 이미 그 방식이다 — 서브도메인으로 라우팅하고 경로·body는 verbatim 통과시킨다.

- **왜 묻나 (중요)** — Edge가 GW의 device가 되면 GW의 정책(`allowed_endpoints`)·호환성 매트릭스(`apis[].path`)·감사(`resource_type`/`resource_id`)가 **전부 경로와 리소스를 전제**한다. RPC면 그 기능들을 쓸 수 없다
- **또 하나** — 동시성·멱등이 표준으로 풀린다. revision 충돌은 `If-Match`+`412`, 멱등은 `Idempotency-Key`(GW도 쓴다). 지금은 body에 revision을 넣고 409를 쓴다
- **운영** — 로그에 `POST /…/call`만 쌓이면 무엇이 느린지 안 보인다
- ⚠ **지금이 가장 싼 시점** — 플러그인 둘, 클라이언트는 콘솔뿐. 업무 플러그인이 늘고 클라이언트가 붙은 뒤에는 못 바꾼다
- **내 의견** — **바깥은 REST, 안(호스트↔플러그인 파이프)은 지금처럼 RPC.** 경계마다 맞는 모양을 쓰는 것이지 섞는 게 아니다

---

### 3-1. 플러그인 간 호출이 필요해지면 어떻게 할 계획입니까

통신 구간이 셋인데 **③만 비어 있다**(파악노트 §7.0).

```
① 클라이언트 → Edge Base        RPC 스타일 (REST 권고)
② Edge Base → 플러그인          RPC · 전용 파이프
③ 플러그인 ↔ 플러그인           경로 없음
```

③이 없는 건 설계 의도로 보인다 — `plugin-first-design.md` §8이 "플러그인 간 의존성"을 명시적 제외로 두고, 구조적으로도 호스트가 **플러그인마다 전용 파이프**를 주어 서로를 부를 통로가 없다.

- **왜 묻나** — 업무 기능이 늘면 "영상 수집 플러그인이 환자 플러그인의 데이터를 봐야 하는" 상황이 반드시 온다
- **선택지** — 호스트 경유 중계(권한 판정 지점이 한 곳에 남음) vs 직접 연결(격리가 무너짐)
- 문서의 "다른 서비스 데이터는 그 서비스의 **공개 유스케이스를 통해** 사용한다"가 호스트 경유를 전제한 것으로 읽히는데, **아직 구현은 없다**

## 4. 플러그인 계약을 Rust SDK로 계속 갈 것입니까, 언어 중립 IDL로 뺄 것입니까

현재 계약은 `plugin-sdk` 90줄의 Rust 구조체다. `deny_unknown_fields`·태그드 유니온·`=0.2.0` 버전 핀·`hostApiVersion 2`까지 **꽤 엄격하다.**

다만 계약이 Rust 소스에 있어 **사실상 Rust 플러그인만 가능하다.**

- **왜 묻나** — 장비 SDK는 보통 C++이고 벤더가 제공한다. 그 연동 플러그인을 C++로 만들어야 하면 계약을 손으로 재구현하게 된다
- **같이 확인** — 플러그인을 벤더에게 열 계획이 있는가. 문서에 "외부 개발자 플러그인을 허용할 때는 신뢰·권한 모델을 별도로 설계한다"고 돼 있는데, **언어 선택은 그보다 먼저 오는 결정**이다
- **중간 선택지** — Rust를 정본으로 두되 JSON Schema를 생성해 배포하면, 지금 구조를 안 바꾸고도 다른 언어를 받을 수 있다

---

### 4-1. Rust 고정이라면 호스트↔플러그인을 `tarpc`로 바꿀 생각은 없습니까

4번의 답이 **"Rust 전용 확정"이면** 이어서 물을 것이다. 상세 비교는 파악노트 §8.5에 있다.

**지금 직접 구현한 것들이 라이브러리로 대체된다.**

| 지금 | tarpc |
| --- | --- |
| `ServiceFrame` enum 4종 | trait 메서드 |
| `request_id` 발급·상관, `pending` 맵 | 라이브러리 |
| 응답 대기 4초 타임아웃 | `Context::deadline` |
| `operation` 문자열 매칭 | **컴파일 타임 검사** |
| `call_id`로 역방향 호출 상관 | `await` 한 줄 |
| **"직렬 호출" 제약** | **다중화 기본** |

⭐ 가장 큰 둘은 **다중화**와 **타입 안전**이다. 지금 `"devices.registar"` 같은 오타는 런타임에야 드러나는데 trait이면 빌드가 막는다.

⭐ **소유권 판정도 개선된다** — 지금은 `call_id`로 "어느 invoke가 낸 data 요청인가"를 추적하는데, 연결 기반이면 **연결 자체가 세션**이 되어 "자칭 `pluginId`를 믿지 않는다"가 구조로 보장된다.

**대가도 분명하다.**

- ⚠ **양방향을 다시 설계해야 한다** — 서비스가 둘이고 방향이 반대다(`DeviceService` 호스트→플러그인 · `DataApi` 플러그인→호스트). 지금은 단일 스트림에 `type` 태그로 섞어 흘려 **이미 푼 문제**인데, tarpc는 보통 한 연결에 한 서비스라 연결을 둘로 나누거나 다중화를 얹어야 한다
- ⚠ **그 층이 Rust에 못 박힌다** — 되돌리기 비용이 생긴다
- 디버깅 — wire가 bincode면 눈으로 못 본다(JSON transport로 완화 가능)

**덧붙여 물을 것** — `tarpc`가 해주지 **않는** 것이 있다. 변화 적응(**6-1**)은 별개다.

- `deny_unknown_fields` 정책 — **tarpc로 가도 그대로 남는다**(serde 설정 문제)
- capability 협상 · operation 디스커버리

> **내 의견** — Rust 고정이 확정이면 좋은 선택이다. 다만 **지금 당장 할 일은 아니다.** ②는 내부라 호스트와 플러그인이 같이 배포되므로 **나중에 바꿔도 된다.** 반면 ①(클라이언트 API)은 외부라 나중에 못 바꾼다. **바꿀 수 없는 것부터** 정하는 게 맞다.

## 5. LAN 구간 TLS를 어떻게 할 계획입니까

EzServer가 self-signed + 검증 끄기로 간 것은 **LAN 호스트에 공인 인증서를 받을 수 없어서**였고, 인증 심사에서 문제가 된 지점이다.

심사가 보는 것은 "암호화했나"가 아니라 **"상대를 인증하는가 · 키와 인증서를 누가 발급·회전·폐기하는가 · 그 과정이 통제되는가"** 다. `self-signed + 검증 끄기`는 거기에 답이 없다.

⭐ **문제는 "인증서가 self-signed라서"가 아니라 "검증을 끌 수밖에 없어서"다.** 클라이언트마다 인증서를 심을 방법이 없으니 검증을 껐고, 그래서 암호화는 해도 상대를 확인하지 않는 상태가 됐다.

- ⭐ **Edge는 클라이언트를 새로 배포하므로 지금이 이 구조를 바꿀 수 있는 유일한 시점이다.** EzServer가 못 고친 이유는 이미 나간 클라이언트들 때문이었다
- **제안** — 사설 CA로 Edge별 서버 인증서를 발급(개인키는 Edge를 떠나지 않게 CSR만 제출)하고, **클라이언트 설치 프로그램이 CA를 신뢰 저장소에 심는다.** 그러면 검증을 켜고도 클리닉 IT 부담이 없다
- ⚠ 이건 **REST/RPC 선택과 무관**하고, **올해 범위에 들어가야 하는 항목**이다

### 5-1. 사설 CA를 셋 중 어디에 둘 것입니까

| | ① 클리닉별 로컬 CA | ② AWS Private CA | ③ OpenBao를 AWS에 직접 구축 |
| --- | --- | --- | --- |
| CA 위치 | **각 Edge 안** | AWS 관리형 | **우리가 AWS에 세움** |
| 루트 키 보관 | 클리닉마다 | AWS HSM | **AWS KMS**(auto-unseal) |
| 클라이언트가 신뢰할 것 | **클리닉 수만큼** | 루트 하나 | 루트 하나 |
| 고정비 | 0 | **CA당 월 $400 수준** | 컴퓨트 + KMS 키(낮음) |
| 운영 부담 | 낮음(분산) | **거의 없음** | **구축 + 상시 운영** |
| 키 유출 반경 | **그 클리닉만** | 전체 | 전체 |
| 폐기·회전 통제 | **중앙 불가** | 중앙 | 중앙 |
| 심사 입증 | **어렵다**(CA가 N개) | **쉽다** | 가능하나 문서화 부담 |
| 구현 도구 | **로컬 OpenBao**(이미 있음) | AWS 관리형 | **중앙 OpenBao**(별도 인스턴스) |

> ⭐ **축은 "OpenBao냐 AWS냐"가 아니라 "CA를 어디에 두느냐"다.** OpenBao는 ①의 구현체도 ③의 구현체도 된다. `edge-security up`이 이미 Edge 머신에 OpenBao를 띄우고 Transit을 쓰고 있으므로, ①은 **PKI 엔진 하나 더 켜는 일**이다. 다만 도구가 같다고 ①의 약점이 사라지지 않는다.

**물어볼 것**

- ①을 고려했습니까 — 가장 싸고 **도구가 이미 있지만**, 설치 시점에 "지금 받은 이 CA가 진짜인가"를 검증할 방법이 없고(TOFU) 중앙에서 폐기·회전이 안 됩니다. 클라이언트가 여러 클리닉에 붙으면 CA가 여러 개가 됩니다
- ⚠⚠ **①의 결정적 문제는 복구입니다.** `security/README.md`에 **"키 서비스까지 새 장비로 복원하는 자동화는 아직 미제공/미검증"**이라고 적혀 있습니다. 여기에 CA 키까지 얹으면 **Edge 장비 고장 = 그 클리닉 CA 소실 = 클라이언트 전부 재설치**가 됩니다. 중앙 CA면 새 장비에 인증서만 다시 발급하면 끝입니다 — **이 복구 자동화를 먼저 할 계획입니까?**
- ①은 **auto-unseal을 KMS로 걸 수 없습니다** — 오프라인 동작이 전제라 unseal 수단이 그 머신에 있어야 하고, 머신을 장악하면 CA 키가 넘어갑니다. 지금 `edge-security up`은 **무엇으로 봉인을 해제합니까?**
- ③을 간다면 **`auto-unseal`을 AWS KMS로 거는 것이 전제**입니다. 그래야 "루트 키를 사람이 들고 있지 않다"가 성립해 ②의 핵심 장점을 가져옵니다. 없이 가면 재기동마다 사람이 unseal 키를 넣어야 해 **운영도 심사도 곤란**합니다
- ③의 진짜 부담은 가용성이 아니라 **백업·복구**입니다. 발급은 enroll·갱신 때만 일어나고 CA가 몇 시간 내려가도 **기존 인증서는 유효**하지만, **루트 키를 잃으면 복구가 불가능**합니다
- 참고 — OpenBao 구동이 아직 "**Windows 서비스 설치·자동 부팅 등록·프로세스 감독기가 아닌 개발 도구**"라고 적혀 있습니다. **운영 형태(서비스 등록·부팅 자동 시작)는 언제 할 계획입니까?** ①을 가려면 이것이 선행됩니다

### 5-1-1. ⚠ 그런데 외부 연결 없는 클리닉은 어떻게 합니까

**②③은 "인터넷이 된다"를 전제하는데, vt-edge는 오프라인 동작을 설계 원칙으로 명시했습니다.**

> 인터넷 연결 없이도 이미 설치한 플러그인은 실행할 수 있다. — `docs/plugin-first-design.md`
> 인터넷이 끊겨도 로컬 키 서비스가 정상 동작하면 읽기·쓰기가 가능합니다. — `security/README.md`

**먼저 갈라야 할 것** — "외부 연결 없다"는 말이 셋 중 어느 것입니까.

| | 상황 | 중앙 CA |
| --- | --- | --- |
| **A** | inbound 차단 · **outbound 가능** | ⭕ 문제 없음 |
| **B** | 가끔 연결 | ⭕ 갱신 여유를 크게 |
| **C** | **완전 격리** | ❌ 깨짐 |

- ⭐ **현장에서 "외부 연결 없다"의 대부분은 A일 것으로 보는데 맞습니까.** A면 중앙 CA에 아무 문제가 없습니다
- **C 클리닉이 실제로 있습니까 · 비율이 어느 정도입니까** — 이 답이 설계를 가릅니다
- C에서는 **발급보다 갱신이 치명적**입니다. 발급은 설치 때 한 번이라 어떻게든 되지만, ⚠ **갱신은 1년마다 반복**되어 자동화가 없으면 **1년마다 LAN이 죽고 C/S가 나갑니다** — 없애려던 바로 그것입니다

**듣고 싶은 답** — C를 제품 범위에 넣을 것인지. 넣는다면 5-2의 하이브리드가 사실상 유일한 답입니다.

### 5-2. ⭐ 구현체보다 먼저 정해야 할 것 — 루트/중간 분리

```
루트 CA     오프라인 보관 · 장수명(10~20년) · 평소엔 쓰지 않음
  └─ 중간 CA   실제 발급 담당 · 수명 짧게 · 교체 가능
       └─ Edge 서버 인증서
```

**루트를 나중에 바꾸는 것은 거의 불가능합니다** — 클라이언트에 심은 신뢰 앵커를 바꾸려면 **전 클라이언트를 다시 배포**해야 합니다.

나눠 두면 클라이언트는 **루트만** 신뢰하면 되고, **중간 CA는 교체 가능**해집니다. ③으로 시작했다가 ②로 옮겨도 클라이언트는 그대로입니다. 즉 **①②③을 지금 확정하지 않아도 되게 만드는 장치**입니다.

#### ⭐⭐ 오프라인 대응형 — 중간 CA를 Edge에 둔다

5-1-1의 C 문제는 **이 분리를 한 단계 더 쓰면** 풀립니다.

```
중앙 루트 CA (오프라인 보관 · 10~20년)
  └─ Edge별 중간 CA      ← 설치·온보딩 때 1회만 발급 · 수명 길게(5~10년)
       └─ 서버 인증서      ← Edge가 로컬에서 발급·갱신 · 인터넷 불필요
```

- 클라이언트는 **중앙 루트 하나만** 신뢰합니다 — ①의 **TOFU 문제가 사라집니다**
- 서버 인증서 **갱신이 로컬**입니다 — **오프라인 설계 원칙을 지킵니다**
- 온라인이 필요한 건 **설치 때 중간 CA 발급 1회**뿐입니다
- ⭐⭐ **Edge 장비가 죽어도 새 장비에 새 중간 CA를 발급하면 끝**이고 **클라이언트는 그대로**입니다 — 5-1에서 지적한 ①의 복구 문제가 해소됩니다

**물어볼 것**

- 이 구조를 염두에 두고 있었습니까, 아니면 Edge가 스스로 self-signed를 내는 지금 방식을 유지할 생각이었습니까
- Edge가 중간 CA 키를 들게 되는데 **9.5에서 지적한 unseal·복구 문제가 그대로 따라옵니다.** 중간 CA 키도 로컬 OpenBao에 넣을 생각입니까
- X.509 **Name Constraints**로 Edge 중간 CA의 발급 범위를 묶는 것을 검토했습니까 — ⚠ 클라이언트별 지원이 고르지 않아 검증이 필요합니다

| 순서 | 결정 | 되돌릴 수 있나 |
| --- | --- | --- |
| **1** | **클라이언트가 검증을 켤 수 있는가** | ❌ 클라이언트 재배포 시점에만 |
| **2** | **완전 격리(C) 클리닉을 지원하는가** | ❌ 제품 등급 문제 — §8 |
| **3** | **루트/중간 분리 구조** | ❌ 루트 교체 = 전 클라이언트 재배포 |
| **4** | 중간 CA를 어디에 (중앙 / Edge) | △ C를 지원하면 Edge로 고정 |
| **5** | 루트 운영 구현체 (② / ③) | ⭕ 교체 가능 |

⚠ **1번이 전부입니다.** CA를 세워 놓고 클라이언트가 여전히 검증을 끄면 아무것도 나아지지 않습니다. **인프라 작업이 아니라 클라이언트 작업과 세트**입니다.

⭐ **①을 단독으로 고르는 선택지는 사실상 없습니다** — C 대응이 필요하면 위 하이브리드가 ①의 상위 호환이고, C가 없으면 ①을 쓸 이유가 없습니다.

### 5-3. 짚어 둘 것 — GW enroll은 그대로 쓸 수 없습니다

GW의 enroll은 AWS IoT Core의 CA로 서명하므로 그 인증서는 **IoT mTLS 전용**이고 **LAN 서버 인증서로는 쓸 수 없습니다.**

재사용할 수 있는 것은 **CA가 아니라 흐름**입니다 — 디바이스가 키페어를 만들고 **CSR만 제출**하고, **개인키가 디바이스를 떠나지 않으며**, enroll 한 번으로 자격을 확립하는 패턴. **LAN용 CA는 별도로** 세워야 합니다.

> 신뢰 배포 쪽도 미리 확인할 것 — 설치 시 **관리자 권한**이 필요하고, Chrome·Edge는 OS 저장소를 쓰므로 같이 해결되지만 ⚠ **Firefox는 자체 저장소**라 별도 처리가 필요합니다.

## 6. 업데이트와 롤백은 범위에 들어갑니까

C/S 출동의 원인은 "손으로 설치해야 해서"가 아니라 **"가서 봐야만 알 수 있어서"** 다. 그걸 없애려면 셋이 필요하다.

| | 무엇 | 현재 |
| --- | --- | --- |
| 알기 | 각 클리닉 구성을 중앙에서 안다 | **GW에 있음**(clients 인벤토리·fleet) |
| 판정 | 이 조합이 호환되는지 기계가 답한다 | **GW에 있음**(호환성 매트릭스·semver 3단계) |
| 되돌리기 | 실패해도 복구된다 | ❌ **vt-edge 명시적 제외** |

- **왜 묻나** — **셋 중 롤백만 비어 있다.** 데이터와 실행파일 분리가 이미 돼 있어 지금 넣는 비용이 가장 싸다
- **같이 확인** — Base 자신의 업데이트 경로. 플러그인은 설치·제거가 되는데 Base 바이너리 교체는 수동이고 프로세스를 먼저 죽여야 한다. **현장에서 아픈 건 보통 이쪽이다**
- **덧붙여** — 단계적 배포(소수 → 확대, 문제 시 중단)는 호환성 판정이 틀렸을 때의 안전망이다
- ⚠ **전제 주의** — "알기"와 "판정"은 둘 다 **중앙과 통신이 된다**는 전제 위에 있다. **완전 격리 클리닉에서는 셋 다 안 되고 여전히 C/S가 나간다**(§8)

---

### 6-1. 플러그인과 호스트가 각자 버전을 올려도 동작해야 합니까

플러그인은 **추가·변경·업그레이드**가 계속 일어난다. 그런데 현재 설계는 **양쪽을 동시에 교체해야만** 동작한다.

**함정 둘이다.**

**(1) `deny_unknown_fields`** — 모르는 필드가 오면 **거부**한다.

```rust
#[serde(deny_unknown_fields)]  pub struct ServiceError
#[serde(deny_unknown_fields)]  pub struct Record
```

- 호스트가 새 필드 추가 → **구버전 플러그인이 거부**
- 플러그인이 새 필드 추가 → **구버전 호스트가 거부**

Protobuf가 모르는 필드를 보존·무시하는 이유가 이것이다(전진 호환).

**(2) 정확히 일치 요구** — "지원하는 `schemaVersion`, `hostApiVersion`, 플랫폼이 **정확히 맞아야** 설치할 수 있다"에 더해 SDK 버전도 `=0.2.0`으로 핀돼 있다.

→ **진화를 허용하지 않고 "같이 올려라"로 푼 것**이다. 플러그인 둘이고 전부 우리가 만들 땐 성립하지만, 열 개가 되거나 벤더가 만들면 성립하지 않는다.

**물을 것 셋**

| # | 질문 | 효과 |
| --- | --- | --- |
| 1 | unknown field 정책을 **무시로 바꿀 생각이 있는가** | 지금 구조 그대로 **전진 호환** 확보. 가장 싸고 효과 크다 |
| 2 | 버전을 정확 일치 → **capability 협상**으로 바꿀 것인가 | 부분 호환 가능. "이 플러그인은 X를 모른다"로 분기 |
| 3 | 플러그인이 자기 operation을 **런타임에 선언**하게 할 것인가 | 새 플러그인 추가 시 **콘솔 코드 0** |

- ⭐ **3번은 GW에서 쓴 방법과 같다** — device 카탈로그가 "무엇을 연동할 수 있나 + 무엇을 입력받아야 하나(`fields[]`)"를 내려줘 화면을 동적 렌더하게 했다. vt-edge에는 그 장치가 아직 없다
- ⚠ 1번의 대가 — 오타가 조용히 통과한다. 절충은 **계약 필드는 엄격, 확장 영역은 관대**로 나누는 것
- ⚠ **이 셋은 `tarpc`가 해주지 않는다**(4-1). 프로토콜 교체와 별개이고 **더 급하다**

## 7. Edge가 GW의 device가 됩니까

EzServer가 fade out하면 enroll(private_key_jwt)·device 토큰·fleet heartbeat·연동 카탈로그·org-binding·하행 MQTT 구독을 Edge가 승계해야 한다.

- 우리 GW SRS는 device를 "EzServer 한 종류"로 쓰고 있지만, **"device도 EzServer 외의 종류가 생길 수 있다"**는 확장 여지를 §1.2에 이미 적어 뒀다. 구조적으로는 받을 준비가 돼 있다
- ⭐ **가장 싸고 효과가 큰 한 수** — Edge가 `Vatech-Product: VTEdge`로 heartbeat만 보내도 **전 클리닉 Edge 버전이 중앙에 보인다.** 그것만으로 "가서 봐야 안다"가 "화면에서 안다"로 바뀐다
- 다음 단계로 heartbeat에 **설치된 플러그인 목록·버전**을 실으면 구성 전체가 보인다
- ⚠ **이 절 전체가 "Edge가 바깥으로 나갈 수 있다"를 전제한다.** 완전 격리 클리닉은 enroll부터 안 되므로 **§8이 먼저 정해져야 범위가 확정된다**

## 8. ⚠ 완전 격리(오프라인) 클리닉을 어디까지 지원합니까

> 5-1-1에서 TLS 때문에 나온 질문인데, **실은 TLS보다 훨씬 큰 범위**라 따로 둔다.

**C 클리닉이면 이것들이 전부 안 된다.**

| 기능 | 영향 |
| --- | --- |
| **자동 업데이트** | ⚠ §6에서 풀려던 핵심 문제인데 **격리 클리닉은 여전히 C/S 출동**이다 |
| **호환성 매트릭스 조회** | 무엇을 올려도 되는지 못 받아온다 — §6-1의 전제가 깨진다 |
| **GW device enroll** | 안 된다 — **§7이 통째로 성립하지 않는다** |
| 원격 백업 | `security/README.md`에 있는 기능인데 안 된다 |
| CleverSpace 연동·동기화 | Edge의 존재 이유 중 하나인데 안 된다 |
| 중앙 CA 발급·갱신 | §5-1-1 |

⭐ **Edge의 포지셔닝이 "클라우드 플랫폼의 현장 말단"인데 C 클리닉은 클라우드에 안 붙는다.** EzServer는 독립 제품이라 가능했던 것이고, Edge로 가면서 그 고객을 어떻게 할지가 정해져야 한다.

**물어볼 것**

- **C 클리닉이 실제로 있습니까 · 비율이 어느 정도입니까** — 추정이라도 필요하다
- 셋 중 어디로 갈 생각입니까

| 선택 | 의미 |
| --- | --- |
| **오프라인 등급을 만든다** | 로컬 기능만 · 업데이트 수동 · 명시적으로 축소된 제품 |
| **온라인을 요구한다** | C 고객을 받지 않거나 전환시킨다 |
| **A·B만 지원한다** | outbound만 열면 된다고 요구 — ⭐ **가장 현실적일 수 있다** |

- "오프라인에서도 돈다"는 설계 원칙(`plugin-first-design.md`)이 **"이미 설치한 플러그인의 실행"**까지인지, **"설치·업데이트·연동까지"**인지 — 문장은 실행만 보장하는 것으로 읽힌다. 의도가 맞습니까
- A·B만 지원한다면 **"outbound 허용"을 설치 요구사항으로 문서화**할 생각입니까 — 지금은 어디에도 없다

**듣고 싶은 답** — 이건 기술 결정이 아니라 **제품 범위 결정**이고, 정해지지 않으면 TLS·업데이트·GW 연동 셋이 전부 떠 있는 상태가 된다.

---

## 시간이 남으면

- **누가 만듭니까** — 지금 Scott 단독이고 EzServer 팀은 VAG 연동·PLAN-1330으로 묶여 있다
- **`ezserver_suite/backend/rest_api` 트랙은 어떻게 됩니까** — 해당 경로가 2026-07-16 이후 조용한데 의도적 중단인지 작업이 옮겨간 것인지 (상세는 `03-Thomas-기술논의.md`)
- **SQLite 운영 규칙** — 코드는 이미 WAL + `synchronous=FULL`로 잘 잡혀 있다. 남은 건 환경 규칙이다
  - DB를 **반드시 로컬 디스크**에 — 공유 폴더·NAS·동기화 폴더(OneDrive 등) 금지. WAL은 네트워크 파일시스템에서 특히 위험
  - 백신 예외 등록 — DB·`-wal`·`-shm` 세 파일
  - 주기적 무결성 점검과 손상 시 운영자 알림 — 지금은 백업 시점에만 검사한다
- **플러그인 프로세스 격리** — 문서가 "보안 샌드박스가 아니다"라고 반복해 못 박는다. 자사 코드 한정이면 괜찮지만 열려면 신뢰 모델이 따로 필요하다
