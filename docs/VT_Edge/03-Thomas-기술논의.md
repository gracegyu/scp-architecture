## 1. EzServer Rust 포팅의 실제 내용 (확인됨)

one-pager 원문 — `doc/onepager/porting_fs_api_to_rust/` (2025-05-30 · Thomas Min)

> PHP로 구현된 EzWebServer API 중 fs API를 Rust로 변환하여 REST API v2 서버에 포팅한다. v6.2.1에서 제공한 **모든 fs API를 포함**한다.

### 라우트 구조

```
routes/v1/fs/   ct_file · dir · e2tag · export_file · file · image_file_info
                multi_file · patient_file · sys_file · sysinfo · third_party_file   (13파일)
routes/v2/      file · health · implant                                            (7파일)
```

- **`routes/v1`은 PHP fs API의 1:1 포팅이다.** 경로도 레거시 그대로 — `/ctfilesbychartnoandpath/chartno/{chartNo}/path/{path}`
- **`routes/v2`는 재설계가 아니라 신규 기능 몇 개다.** `v2/file`은 `/thumbnails/{image_file_name}` 하나

⭐ **1:1 포팅은 올바른 방식이다.** 언어 이식에서 동작을 바꾸지 않아야 회귀를 잡을 수 있다. 비판 대상이 아니다.

⭐ 다만 결론은 이것이다 — **"API를 RESTful하게 정리하는 작업"은 아직 시작 전이다.**

## 2. 논의 1 — 두 Rust 트랙의 관계

**질문: `backend/rest_api`와 vt-edge는 어떻게 만나는가.**

세 갈래가 있다.

1. **`rest_api`가 vt-edge의 플러그인으로 들어간다**
   - ⚠ 그러면 PostgreSQL을 쓰는 플러그인이 되는데, **"플러그인에 DB 연결을 주지 않는다"는 Base 설계와 정면으로 부딪힌다**
2. **둘이 별개이고 vt-edge가 결국 `rest_api`도 대체한다**
   - 295파일을 또 다시 쓰는 셈이다
3. **fade out 대상이 EzServer 전체가 아니라 PHP뿐이다**
   - 그러면 `rest_api`는 남고 vt-edge는 다른 역할을 맡는다

**확인할 것** — `backend/rest_api`가 해당 경로 기준 7월 이후 조용한 것이 **의도적 중단**인지 **작업이 다른 곳으로 옮겨간 것**인지.

- 의도적 중단이면 — 이미 Scott 방향으로 정리된 것이고 승계 논의만 남는다
- 진행 중이면 — **두 팀이 서로 다른 전략을 실행하고 있는 상태**다

⚠ 정리되지 않으면 가장 큰 리스크는 기술이 아니라 **같은 기능이 세 벌(v1 · v2 · Edge 플러그인) 만들어지는 것**이다.

## 3. 논의 2 — 새 API 계약을 어디서 그리나

클라이언트를 한 번에 못 바꾸므로 호환 경로가 필요하다. 그런데 **EzServer를 안 건드려도 클라이언트 계약은 반드시 건드려진다** — Edge가 대체하면 결국 Edge의 API를 써야 하기 때문이다.

### 제안하는 정리

> **EzServer 본체는 동결한다. 새 API 계약은 Edge에서 태어나게 한다. 클라이언트는 그 계약으로 한 번만 옮긴다.**

- **EzServer** — v1(fs)만 유지. **보안 수정과 데이터 손상 버그만.** 기능 추가·성능 개선 금지
  - ⚠ 이건 기술이 아니라 조직 규율 문제라 **문서로 못 박아야** 지켜진다. "이것만 급하니까"가 쌓이면 이동 유인이 사라진다
- **새 API** — Edge의 플러그인이 제공한다. 리소스 모델을 제대로 그린다
- **과도기** — Edge와 EzServer가 한 클리닉에 공존하고 클라이언트는 **기능 단위로** 넘어간다
- **결과** — 클라이언트는 한 번만 바뀌고 EzServer는 손대지 않는다

### `routes/v2`(thumbnail·health·implant)는 어떻게 하나

이미 만들어진 것이라 선택이 필요하다.

1. 계속 EzServer에서 키운다 → 클라이언트가 v1 → v2 → Edge로 **두 번** 옮긴다. **가장 나쁘다**
2. 여기서 멈추고 Edge로 옮긴다 → 이미 만든 것은 Edge 플러그인의 출발점으로 쓴다
3. 계약을 Edge가 그대로 승계하기로 못 박는다 → 어디서 구현하든 **계약은 하나**. 클라이언트는 주소만 바뀐다

→ **2번이나 3번.** 핵심은 같다 — **"새 API 계약은 하나뿐이고 그것이 Edge의 계약이다."**

### v1 종료 조건

- 날짜보다 **조건**이 낫다 — "v1 호출 비중이 N% 미만이면 제거" 또는 "EzServer vX 이후 미지원"
- 그러려면 **v1 사용량을 측정**해야 한다. 안 재면 절대 못 끈다
- ⭐ GW가 이미 `Vatech-Product`·`Version`을 받고 `/v1/admin/clients`로 클리닉별 제품·버전을 보여준다. **"누가 아직 v1을 쓰는가"를 중앙에서 답할 수 있다**

## 4. 논의 3 — 기존 DB와 파일 저장소를 어떻게 하나

**DB와 파일은 정반대 답이다.**

### DB — 그대로는 못 쓴다

- **엔진** — EzServer는 PostgreSQL, vt-edge는 SQLite뿐이다(`rusqlite` 하나, PostgreSQL 드라이버 없음)
- **모델** — vt-edge는 `(service_id, collection, record_key)` + JSON 레코드다. 관계형 임상 스키마가 아니다

따져볼 것 하나 — **vt-edge가 반드시 SQLite여야 하나.**
SQLite를 내장한 이유는 "운영자가 DB 서버를 따로 설치하지 않아도 되게"인데, **전환 대상 클리닉에는 이미 PostgreSQL이 깔려 있다.** 그 장점이 성립하지 않는다.

### 파일 — 옮기면 안 된다

영상은 TB 단위다. 복사하면

- 며칠이 걸리고 그동안 진료가 멈춘다
- 디스크 여유 공간이 두 배 필요하다
- 실패 시 어디까지 됐는지 추적해야 한다

⭐ **"이관"이 아니라 "그 자리에서 소유권 인수(adopt in place)"가 정답이다.**

- EzServer에 `file_storage` 트레이트 + `local_file_storage` 구현이 이미 있다 — 추상화가 있으면 같은 규칙으로 읽는 구현을 Edge에 만들 수 있다
- ⚠ **vt-edge 설계에 이 요구가 없다.** 지금은 신규 설치만 가정한다. **나중에 넣으면 굳은 저장 모델을 뜯어야 한다**

### 현실적 경로

1. **Edge = 신규 기능 전용** — 기존 데이터를 안 건드린다. 위험 0
2. **읽기 어댑터** — Edge 플러그인이 기존 PostgreSQL·파일을 **읽기 전용**으로 본다. 데이터 이동 0
3. **쓰기 커트오버** — 그 시점부터 신규는 Edge가 쓰고 과거는 그대로 둔다. 조회 계층이 둘을 합쳐 보여준다
4. **과거 데이터는 옮기지 않거나** 한참 뒤 백그라운드로

다운타임이 없고 되돌릴 수 있으며 TB 복사가 필요 없다.

## 6. 논의 5 — 자동 업데이트와 C/S 출동

**문제의 본질은 기술이 아니라 신뢰다.** C/S가 나가는 이유는 "손으로 설치해야 해서"가 아니라 **"가서 봐야만 알 수 있어서"** 다.

출동을 없애려면 셋이 동시에 필요하다.

| | 무엇 | 현재 |
| --- | --- | --- |
| 알기 | 각 클리닉이 무엇을 쓰는지 중앙에서 안다 | **GW에 있음** — `/v1/admin/clients`·`/v1/admin/fleet` |
| 판정 | 이 조합이 호환되는지 기계가 답한다 | **GW에 있음** — 호환성 매트릭스·semver 3단계 게이팅 |
| 되돌리기 | 실패해도 복구된다 | ❌ **vt-edge 명시적 제외** |

⭐ **EzServer의 자동 업데이트 문제는 Edge 혼자서는 안 풀리고 GW 연동과 같이 가야 풀린다.**

⚠ **다만 "알기"와 "판정"은 둘 다 중앙과 통신이 된다는 전제 위에 있다.** 외부 연결이 없는 클리닉에서는 셋 다 성립하지 않고 **여전히 C/S가 나간다**(§7 말미). 그 비율이 얼마인지가 이 접근의 실효 범위를 정한다.

### 호환성 매트릭스 확장 (검토 가치 있음)

현재 매트릭스는 `minClientVersion`(하한선 하나)이고 요청 시점에 그 요청의 헤더만 본다. "플러그인 P를 v2로 올려도 되나"에 답하려면 셋이 필요하다.

1. **Edge 구성을 인벤토리에 올린다** — heartbeat에 설치된 플러그인 목록·버전
2. **매트릭스에 조합 제약 축을 추가한다** — 플러그인별 `hostApiVersion`(**Edge manifest에 이미 있다**) · 플러그인↔클라이언트 제약 · 상한/배제 표현
3. **사전 판정 수단** — "올리기 전에 묻는" 엔드포인트

⚠ **함정** — 지금 꺼져 있는 클라이언트는 아무도 모른다. 가끔 쓰는 장비 PC가 나중에 켜지면 그때 깨진다.
→ 판정 계약에 **"최근 N일 내 관측된 구성 기준"**을 명시해야 한다. GW의 clients 인벤토리는 관측 기반이라 "마지막으로 본 시각"을 가질 수 있다.

## 7. 논의 6 — LAN TLS와 인증 심사

EzServer가 self-signed + 검증 끄기로 간 것은 **LAN 호스트에 공인 인증서를 받을 수 없어서**였다.

심사가 보는 것은 "암호화했나"가 아니라 **"상대를 인증하는가 · 키와 인증서를 누가 발급·회전·폐기하는가 · 통제되는가"** 다.

- ⭐ **Edge는 클라이언트를 새로 배포하므로 지금이 이 구조를 바꿀 수 있는 유일한 시점이다.** EzServer가 못 고친 이유는 이미 나간 클라이언트들 때문이었다
⭐ **문제는 "인증서가 self-signed라서"가 아니라 "검증을 끌 수밖에 없어서"다.** 클라이언트마다 인증서를 심을 방법이 없으니 검증을 껐고, 그래서 암호화는 해도 상대를 확인하지 않는 상태가 됐다.

- **제안** — 사설 CA로 Edge별 서버 인증서를 발급(CSR만 제출 · 개인키는 Edge를 떠나지 않음)하고 **클라이언트 설치 프로그램이 CA를 신뢰 저장소에 심는다**
- ⚠ **GW enroll은 그대로 못 쓴다** — AWS IoT Core의 CA로 서명하므로 그 인증서는 **IoT mTLS 전용**이고 LAN 서버 인증서로는 쓸 수 없다. 재사용할 수 있는 건 **CA가 아니라 흐름**이다(CSR만 제출 · 개인키 비이동 · enroll 1회로 자격 확립). **LAN용 CA는 별도로** 세워야 한다
- ⚠ REST/RPC 선택과 **무관**한 문제이고, **올해 범위에 들어가야** 한다

### ⚠ 그런데 외부 연결 없는 클리닉이 이걸 가른다

**EzServer는 독립 제품이라 외부 연결 없이 내부망만으로 쓰는 클리닉이 실제로 있다.** 중앙 CA는 그 전제와 충돌한다.

| | 상황 | 중앙 CA |
| --- | --- | --- |
| **A** | inbound 차단 · **outbound 가능** | ⭕ 문제 없음 |
| **B** | 가끔 연결 | ⭕ 갱신 여유를 크게 |
| **C** | **완전 격리** | ❌ 깨짐 |

- ⭐ **Thomas에게 확인할 것 — 현장에서 "외부 연결 없다"의 대부분이 A입니까, C가 실제로 있습니까.** EzServer 설치 경험이 이 답을 갖고 있다
- C에서는 **발급보다 갱신이 치명적**이다. 발급은 설치 때 한 번이라 어떻게든 되지만 ⚠ **갱신은 1년마다 반복**되어 자동화가 없으면 **1년마다 LAN이 죽고 C/S가 나간다**

**답은 루트/중간 분리다.**

```
중앙 루트 CA (오프라인 보관 · 10~20년)
  └─ Edge별 중간 CA      ← 설치·온보딩 때 1회만 발급 · 수명 길게(5~10년)
       └─ 서버 인증서      ← Edge가 로컬에서 발급·갱신 · 인터넷 불필요
```

클라이언트는 **중앙 루트 하나만** 신뢰하고, 서버 인증서 **갱신은 로컬**이라 격리망에서도 돈다. Edge 장비가 죽어도 **새 장비에 중간 CA만 다시 발급**하면 되고 클라이언트는 그대로다.

### ⚠ 그리고 이건 TLS만의 문제가 아니다

C 클리닉이면 **§6의 자동 업데이트·호환성 매트릭스 조회**도, **§8의 GW 승계**도 전부 성립하지 않는다. EzServer가 독립 제품이라 가능했던 운영 형태인데, **Edge는 "클라우드 플랫폼의 현장 말단"이라 포지셔닝 자체가 다르다.**

| 선택 | 의미 |
| --- | --- |
| 오프라인 등급을 만든다 | 로컬 기능만 · 업데이트 수동 · 명시적으로 축소된 제품 |
| 온라인을 요구한다 | C 고객을 받지 않거나 전환시킨다 |
| **A·B만 지원한다** | outbound만 열면 된다고 요구 — ⭐ **가장 현실적일 수 있다** |

⭐ **EzServer 전환 대상 중 C의 비율이 이 결정의 근거**이고, 그 숫자는 EzServer 쪽에 있다.

## 8. 논의 7 — GW 연동의 승계

EzServer가 fade out하면 지금 만들고 있는 VAG 연동을 누가 승계하나.

- enroll(private_key_jwt) · device 토큰 · fleet heartbeat · target 카탈로그 · org-binding · 하행 MQTT 구독
- GW SRS는 device를 "EzServer 한 종류"로 쓰지만 **"device도 EzServer 외의 종류가 생길 수 있다"**는 확장 여지를 §1.2에 이미 적어 뒀다
