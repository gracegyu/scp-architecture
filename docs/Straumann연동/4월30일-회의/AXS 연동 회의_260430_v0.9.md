**2. 아젠다별 논의 내용**

**2-1. AXS API 연동 아키텍처 방향 파악**

- AXS API 하나로 Straumann 디지털 생태계 전체(SIRIOS & 랩오더, Smilecloud, Smile in a Box, Codiagnostic X) 접근 가능하며, 환자 관리의 중추 역할 수행 가능함을 Straumann 측이 소개함
- EzServer-SIRIOS 직접 연결 방식을 제안했으나, 본 회의에서 Straumann 측이 AXS API를 통한 연결 방식을 제안함
- 직접 연결 방식은 보안 등 기술적 복잡성이 상당하여 권장하지 않는다고 안내함
- AXS API는 Backend 간 연결을 위한 클라우드 API로, 보안 및 허가 정책상 Public Client에 직접 노출되지 않음
- 온프레미스 디바이스와 AXS API 사이에는 Auth Server 등 중간 계층이 필요함
- Auth Server를 통한 연동 시나리오 세부 내용은 호주 법인이 Straumann 측과 별도 논의 후 공유 예정
- **ES 검토 필요: Auth Server를 통한 연동 방향에 대해 수용 가능 여부 및 개발 방향 내부 검토 필요**

**2-2. Auth Server 필요성 및 구현 방향 제안**

- 온프레미스 디바이스의 AXS API 직접 연결은 지원되지 않으며, Vatech 측에서 클라우드 기반 Auth Server(또는 API 게이트웨이)를 개발 및 운영할 것을 Straumann 측이 제안함
- Auth Server 주요 역할 및 특징
- Client ID 등 민감한 자격 증명을 안전하게 보관 (디바이스 탈취·노출 시 보안 위협이 되며, Client ID는 최소 연 1회 변경되므로 Auth Server 없을 시 모든 온프레미스 디바이스를 개별 업데이트해야 하는 관리 문제도 발생 → 온프레미스 디바이스에 저장하지 않는 것을 권장)
- AXS API와의 모든 통신을 중계하는 신뢰할 수 있는 Backend 역할 수행
- Auth Server 없을 시 90일마다 재연결 필요 / Auth Server 운영 시 재연동 없이 안전한 연결 유지 가능
- 단기적으로는 Auth Server, 중장기적으로는 API 게이트웨이 방식이 적합할 수 있다는 의견도 제시됨
- **ES 검토 필요:** Auth Server 구축은 기존 개발 계획에 포함되지 않은 사항으로, 구현 가능성 및 소요 리소스 내부 검토 필요

**2-3. 인증 및 토큰 관리 (OAuth 2.0)**

- 인증 흐름: **Vatech 온프레미스 디바이스 ↔ Auth Server ↔ Straumann AXS API**
- Auth Server가 저장된 클라이언트 자격 증명으로 AXS API에서 인증 토큰을 발급받아 온프레미스 디바이스에 전달
- 토큰 유효 기간은 **30분**이며, Auth Server에서 주기적으로 갱신 필요
- 온프레미스 디바이스는 발급받은 토큰으로 특정 AXS API 엔드포인트에 직접 호출 가능

**[ES 질의]** 온프레미스 디바이스가 토큰을 받아 Auth Server 경유 없이 AXS에 직접 호출하는 방식 가능 여부

- 기술적으로는 가능하나, Straumann 보안 정책상 환자 정보의 Public IP 노출을 차단하고 있어 별도 인증서가 추가로 요구되는 등 복잡성이 증가하므로 권장하지 않음

**2-4. 파일 업로드 프로세스 (2D/3D 이미지)**

**[ES 질의]** 2D/3D 이미지 업로드 방식 확인

- Straumann 안내 업로드 프로세스 (3단계)
1. EzServer → Auth Server 경유 → AXS API **Create Document** 엔드포인트 호출
2. AXS API가 임시 Pre-signed URL(예: AWS S3 URL) 반환
3. 온프레미스 디바이스가 해당 URL로 AXS에 **직접** 업로드 (이 단계에서는 Auth Server 미경유)
- 대용량 파일 업로드 시 Auth Server 부하를 줄이고 성능 향상 가능

**2-5. 클리닉 온보딩 및 동의 프로세스 확인**

**[ES 질의]** EzServer와 AXS 간 클리닉 매핑 방식 확인

- Straumann 안내 동의 프로세스 (일회성)
1. 클리닉 사용자가 EzServer에서 연결 요청 시작 → Straumann Invoice상 **Customer Number** 입력
2. 해당 클리닉의 Straumann Access 계정에 동의 요청 생성
3. 클리닉 관리자가 Access 포털에서 EzServer의 데이터 접근 요청 승인
4. 승인 완료 시 두 시스템 간 클리닉 매핑에 사용되는 **Organization ID** 생성
5. 클리닉은 언제든지 Access 포털에서 권한 철회(Revoke) 가능

**참고:** Customer Number(Invoice 기재)와 Organization ID(동의 승인 후 생성)는 별개의 개념으로, 동의 이전 단계에서 Organization ID 확인 불가

**2-6. 기타 논의**

**랩 오더 생성**

- IO 스캔 완료 후 기공소 정보, 촬영 정보 등이 포함된 파일이 AXS 웹에 자동 표시
- 사용자가 [Send] 버튼으로 오더 전송 여부 직접 선택 가능
- 동일 환자 폴더 내 다른 이미지 추가 첨부 가능
- AXS 웹에서 EzServer로의 데이터 전달 방식은 호주 법인이 Straumann 측과 별도 논의 후 공유 예정

**웹훅(Webhooks)**

- Straumann이 AXS → EzServer로 업데이트를 푸시하는 양방향 동기화 메커니즘으로 웹훅을 언급함
- ES는 단방향 동기화 방식으로 개발 검토 중이며, 웹훅 활용 여부는 내부 추가 논의 필요

**Clever Lab 연동**
