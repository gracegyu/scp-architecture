# 6.3 SonarQube에 테스트 커버리지 연동하기

> **선행**: `6.1 Jenkins Pipeline에서 SonarQube 연동하기` — 스캔 자체는 이미 돌고 있다는 전제다.
> 스캔이 아직 없다면 6.1 을 먼저 본다.
>
> ⭐ **6.1 이 "스캔을 붙이는 법" 이라면 이 문서는 "그 스캔이 커버리지를 읽게 하는 법" 이다.**
> 스캔은 도는데 `Coverage 0.0%` 로 보인다면 여기가 맞다.

---

## 이 문서를 쓰는 법

**두 부분으로 나뉘어 있다.**

| | 누가 읽나 | 무엇이 있나 |
|---|---|---|
| **1부 — 개요** | **사람** | 무엇을 하는 일인지, 누가 무엇을 맡는지, 내 프로젝트가 어느 경우인지 |
| **2부 — 구현 가이드** | **AI 또는 직접 구현하는 사람** | 순서대로 따라 하는 절차. 파일 내용·명령·검증까지 |

⭐ **2부는 그대로 AI 에게 넘길 수 있게 썼다.** 1부에서 자기 경우를 확인한 뒤,

2부 `2.0` 이 AI 가 먼저 확인해야 할 것을 적어 두었다.

# 1부 — 개요

## 1.1 무엇을 하는 일인가

한 문장이면 이렇다.

> **CI 가 테스트를 돌려 커버리지 리포트를 남기고, 스캐너가 그 파일을 읽어 SonarQube 로 보낸다.**

⚠ **스캐너는 커버리지를 만들지 않는다.** 읽을 뿐이다. 그래서 리포트가 없으면
"측정 안 함" 이 아니라 **"한 줄도 커버되지 않음"** 으로 기록된다. 이것이 `Coverage 0.0%` 의 정체다.

```
① CI 잡이 테스트를 돌린다          pnpm test:coverage
        ↓
② 테스트 러너가 리포트를 남긴다     coverage/lcov.info
        ↓
③ 레포의 sonar-project.properties 가 그 경로를 가리킨다
        sonar.javascript.lcov.reportPaths=coverage/lcov.info
        ↓
④ 같은 잡에서 스캐너가 돈다         sonar-scanner
        ↓
⑤ 스캐너가 그 파일을 읽어 서버로 보낸다
        ↓
⑥ SonarQube 에 커버리지가 뜬다
```

⭐ **`sonar-project.properties` 에 들어가는 것은 리포트가 아니라 리포트의 경로다.**
파일을 거기 넣는 것이 아니라, 어디에 있는지 알려주는 것이다.

**바뀌는 것은 둘뿐이다.**

| 어디 | 무엇 |
|---|---|
| **레포** | `sonar-project.properties` 추가 · 커버리지를 내는 테스트 스크립트 |
| **CI 설정** | 스캔 전에 그 테스트를 돌리는 단계 추가 |

## 1.2 누가 무엇을 하나

⚠ **레포 팀 혼자 끝낼 수 없다.** CI 쪽은 공용 자산이라 CI 담당이 만진다.

| | 레포 팀 | CI 담당 |
|---|---|---|
| `sonar-project.properties` 작성 | ✅ | |
| 커버리지 내는 테스트 스크립트 | ✅ | |
| 어떤 테스트를 합산할지 결정 | ✅ | |
| Jenkins 잡에 테스트 단계 추가 | | ✅ (`sbom/jenkins` PR) |
| ADO 서비스 연결·에이전트 도구 | | ✅ |
| 결과 확인 | ✅ 같이 | ✅ 같이 |

⭐ **레포 쪽 작업은 작다.** 파일 하나와 스크립트 하나다. 복잡해 보이는 부분
(파이프라인 변경·셸 스크립트·에이전트 이미지)은 **CI 담당이 한 번 해두면 다음 프로젝트는
재사용한다.** GW·Console 때 하루가 걸린 것은 그 기반을 처음 놓았기 때문이다.

**요청하는 법** — `sbom/jenkins` 저장소에 이슈나 PR 로, 아래를 적어 보낸다.

```
프로젝트 키   es-platforms_<레포이름>
테스트 명령   pnpm test:coverage        (레포 package.json 의 스크립트)
리포트 경로   coverage/lcov.info
Docker 필요   아니오
워커 상한 변수 CI
```

## 1.3 내 프로젝트는 어느 경우인가

```
① 빌드·테스트가 Windows 를 요구하나?
     예  → 케이스 C (Jenkins Windows 노드)
            ⚠ Windows 노드에는 Docker 가 없다
     아니오 → ②

② 테스트 실행에 Docker 가 필요한가?   (Testcontainers 로 DB·큐를 띄우는 등)
     예  → 케이스 B (Azure DevOps)
            ⚠ Jenkins 에이전트에는 docker 소켓이 없어 불가능하다
     아니오 → ③

③ 이미 ADO 파이프라인에서 같은 테스트가 돌고 있나?
     예  → 케이스 B (Azure DevOps) — 중복 실행을 피한다
     아니오 → 케이스 A (Jenkins Linux 노드)
```

| | 케이스 A | 케이스 B | 케이스 C |
|---|---|---|---|
| 어디서 | Jenkins Linux | Azure DevOps | Jenkins Windows |
| 셸 | `sh` | `script` | **`bat`** |
| Docker | ❌ 소켓 없음 | ✅ 가능 | ❌ **Docker 자체가 없다** |
| 사내 사례 | **Console** | **GW** | EzServer · escloudplatform |
| 2부 절 | `2.2` | `2.3` | `2.4` |

## 1.4 이 숫자는 무엇을 재는가

⚠ **커버리지는 하나가 아니다.** 프로젝트끼리 비교하기 전에 무엇을 합산했는지 봐야 한다.

| 프로젝트 | 합산 대상 | 수치 |
|---|---|---|
| **Console** | unit + component (vitest) | 91.6% |
| **GW** | unit + E2E 합산 (jest, `nyc` 병합) | 96.3% |

⭐ **96.3 과 91.6 은 같은 척도가 아니다.** GW 가 테스트를 잘 짠 것이 아니라
**GW 는 E2E 로 커버되는 줄까지 세고 Console 은 안 센다.**

### E2E 를 뺀 것이 아니다 — 못 세는 것이다

Console 도 CI 에서 playwright 로 E2E 를 **돌린다.** 다만 그 실행이 커버리지에 기여하지 못한다.

| | Console E2E | GW E2E |
|---|---|---|
| 도구 | **playwright** | **jest** |
| 실행 | 브라우저가 **빌드된 앱**을 구동 | Node 프로세스에서 **소스를 직접 실행** |
| 계측 | ⚠ 빌드 산출물이라 안 된다 | 자기가 실행하는 코드를 계측한다 |

playwright 로 재려면 앱 빌드에 istanbul 계측을 넣거나 V8 coverage 를 수집해 소스맵으로
되짚어야 한다. 품이 들어 대부분 하지 않는다.

⭐ **그래서 프론트엔드 커버리지는 대개 unit + component 까지다.** 낮게 보이는 것이 정상이고
E2E 가 없다는 뜻이 아니다.

### 무엇을 합산할지 정하기

| 방식 | 대가 |
|---|---|
| **unit 만** | ⚠ 컨트롤러·가드·미들웨어 **배선 계층이 0% 로 잡힌다.** 그 계층을 E2E 로 검증하는 구조면 수치가 실제보다 **낮게** 나온다 |
| **unit + component** | 프론트엔드에서 흔하다. E2E 로만 닿는 경로는 빠진다 |
| **unit + E2E 합산** | 정직하지만 **E2E 가 계측 가능한 경우에만** 된다(jest·vitest). DB 를 띄우면 Docker 가 필요해져 케이스 B 로 간다 |

⚠ **undercount 가 미실행보다 나쁠 수 있다.** 게이트 기준이 80 인데 배선 계층이 빠져 70 이
나오면 통과할 것이 떨어진다. 그러면 숫자를 믿지 않게 되고, 믿지 않는 게이트는 결국 꺼진다.

## 1.5 알려진 제약

**SonarQube Community 25.4** 를 쓴다.

- **브랜치 분석 없음** — 프로젝트당 `main` 하나만 분석된다
- **PR decoration 없음** — PR 화면에 결과가 안 뜬다

⚠ 그래서 **스캔은 머지된 뒤 `main` 에서만** 돈다. PR 빌드에서 스캔하면 그 PR 의 부분 수치가
곧 프로젝트 수치가 되고 다음 PR 이 또 덮는다.

⚠ **같은 프로젝트를 두 곳에서 스캔하지 않는다.** 나중에 쓴 쪽이 이긴다.

## 2.0 시작 전 — 이 다섯 가지를 먼저 확인한다

⚠ **추측하지 말 것.** 레포마다 다르고, 틀리면 조용히 잘못된 숫자가 나온다.

### ① 커버리지를 내는 테스트 명령

`package.json` 의 `scripts` 를 본다.

```bash
cat package.json | python3 -c "import sys,json;[print(f'{k:24}{v}') for k,v in json.load(sys.stdin).get('scripts',{}).items() if 'test' in k or 'cov' in k]"
```

없으면 만든다. 있으면 **그 이름을 쓴다** — 명령을 CI 설정에 박지 않는다.

### ② 리포트가 떨어지는 경로

명령을 로컬에서 한 번 돌리고 확인한다.

```bash
pnpm test:coverage            # 또는 해당 명령
find . -name "lcov.info" -newermt "-5 minutes" -not -path "./node_modules/*"
```

⭐ **정해진 폴더가 없다.** SonarQube 는 당신이 적은 경로를 그대로 연다.
도구 기본값은 대개 아래와 같지만 **반드시 실측할 것.**

| 도구 | 기본 출력 |
|---|---|
| vitest · jest | `coverage/lcov.info` |
| nyc (병합) | `coverage/` 아래 |
| flutter | `coverage/lcov.info` |
| pytest-cov | CWD 의 `coverage.xml` |
| JaCoCo (maven) | `target/site/jacoco/jacoco.xml` |
| JaCoCo (gradle) | `build/reports/jacoco/test/jacocoTestReport.xml` |
| coverlet (C#) | `TestResults/<guid>/coverage.opencover.xml` |

### ③ 워커 상한 환경변수 — **이름이 레포마다 다르다**

테스트 러너는 보통 **코어 수만큼 워커를 띄운다.** 빌드 호스트는 32 코어이고 에이전트 상한은
3~6GB 다. 그대로 돌면 넘는다.

설정 파일에서 **무슨 변수를 보는지 직접 찾는다.**

```bash
grep -rnE "maxWorkers|process\.env\.(CI|TF_BUILD|[A-Z_]+)" \
  vitest.config.* jest.config.* playwright.config.* 2>/dev/null
```

사내 실례 — **두 프로젝트가 다르다.**

```js
// Console: vitest.config.mts
maxWorkers: (process.env.CI ?? process.env.TF_BUILD) ? 2 : undefined
// GW: jest.config.js
//   GW_CI_LIMIT_WORKERS 로 분기한다
```

⚠ **Jenkins 는 `CI` 를 넣지 않는다.** ADO 는 `TF_BUILD` 를 넣지만 `CI` 는 넣지 않는다.
찾아낸 변수를 **잡에서 명시적으로 export 한다.**

### ④ 패키지 매니저 선언

```bash
python3 -c "import json;d=json.load(open('package.json'));print('packageManager:',d.get('packageManager','(없음)'));print('engines:',d.get('engines','(없음)'))"
head -1 pnpm-lock.yaml 2>/dev/null
```

`packageManager` 가 없으면 추가한다. Jenkins 에이전트는 corepack 이 켜져 있어 **레포 선언을
따른다** — 선언이 없으면 에이전트 기본 버전이 쓰이고 lockfile 과 어긋날 수 있다.

### ⑤ 테스트에 Docker 가 필요한가

```bash
grep -rniE "testcontainers|dockerode|docker-compose" package.json test/ tests/ 2>/dev/null | head
```

걸리면 **케이스 B(ADO)** 다. 케이스 A 로 가면 안 된다.

## 2.1 공통 — 레포에 할 일 (모든 케이스)

### `sonar-project.properties` 를 **레포 루트**에 만든다

```properties
sonar.projectKey=es-platforms_<레포이름>

# 분석 대상
sonar.sources=src
sonar.tests=src,tests
sonar.test.inclusions=**/*.test.ts,**/*.test.tsx,tests/**/*

# 커버리지 리포트 경로 — 2.0 ②에서 실측한 값
sonar.javascript.lcov.reportPaths=coverage/lcov.info
sonar.typescript.lcov.reportPaths=coverage/lcov.info

# 분석에서 제외 — 생성 코드·번역 카탈로그 등
sonar.exclusions=src/generated/**,src/locales/**,**/*.d.ts

# 커버리지 분모에서 제외 — ⚠ 테스트 러너 exclude 와 같은 기준으로 맞춘다
sonar.coverage.exclusions=src/generated/**,src/test/**
```

**언어별 속성 이름**

| 언어 | 속성 |
|---|---|
| TypeScript / JavaScript | `sonar.javascript.lcov.reportPaths` · `sonar.typescript.lcov.reportPaths` |
| Python | `sonar.python.coverage.reportPaths` |
| Java | `sonar.coverage.jacoco.xmlReportPaths` |
| C# | `sonar.cs.opencover.reportsPaths` |
| Dart / Flutter | `sonar.flutter.coverage.reportPath` |

### ⚠ 테스트 파일을 `sonar.exclusions` 에 넣지 않는다

넣으면 테스트 코드가 **분석에서 통째로 사라진다.** `sonar.tests` 로 분류한다 — 분석은 하되
제품 코드와 다른 잣대를 적용하기 위한 것이다.

⭐ **이 설정을 넣으면 `new_violations` 가 늘어난다.** 회귀가 아니라 그동안 분석되지 않던
테스트 코드에 규칙이 처음 도는 것이다. 사내 두 프로젝트에서 모두 일어났다.

### ⚠ 경로 기준은 **스캐너가 도는 위치**다

`reportPaths` 의 기준은 `sonar.projectBaseDir` — 보통 레포 루트다.
`sonar-project.properties` 가 있는 위치가 아니다.

**모노레포에서 하위 폴더만 스캔할 때가 함정이다.** `sonar.sources=apps/admin` 으로 좁혀도
스캐너는 여전히 루트에서 돈다. 리포트가 `apps/admin/coverage/lcov.info` 에 떨어졌다면
`reportPaths` 도 그렇게 적는다.

## 2.2 케이스 A — Jenkins Linux

**참고 실례**: `sbom/jenkins` 레포 `jenkinsfiles/vt-api-gateway-console-SonarQube.jenkinsfile`

### 절차

**① `2.1` 을 마친다** (레포에 properties 추가)

**② CI 담당에게 잡 수정을 요청한다** — `sbom/jenkins` 저장소 PR

해당 잡의 `Map config` 에 `SQUBE_PRE_SCAN` 을 넣는다.

```groovy
Map config = [PROJECT_NAME: env.STAGE_NAME] + [
    GIT_URL: '...',
    SQUBE_PROJECT_KEY: 'es-platforms_<레포이름>',
    SQUBE_PRE_SCAN: '''
        set -e
        export CI=1                     # ⚠ 2.0 ③에서 찾은 변수로 바꿀 것
        node --version
        pnpm --version
        pnpm install --frozen-lockfile
        pnpm test:coverage              # ⚠ 2.0 ①의 명령
        ls -l coverage/lcov.info        # ⚠ 2.0 ②의 경로
    '''
]
```

**③ `SQUBE_EXCLUSIONS` 가 있으면 지운다**

명령행 `-Dsonar.exclusions` 는 레포 파일을 **덮어쓴다.** 레포가 정본이다.

**④ 잡을 한 번 돌리고 `2.5` 로 검증한다**

### 이 스니펫의 각 줄이 왜 있나

| 줄 | 이유 |
|---|---|
| `set -e` | 중간 실패를 삼키지 않는다 |
| `export CI=1` | 없으면 워커가 코어 수만큼 뜬다 (2.0 ③) |
| `node/pnpm --version` | 결과가 이상할 때 **제일 먼저 보게 되는 값**이다 |
| `--frozen-lockfile` | 없으면 lockfile 과 다른 버전이 깔려 스캔 결과가 배포본과 달라진다 |
| `pnpm test:coverage` | 레포 스크립트를 부른다 — 명령을 잡에 박지 않는다 |
| `ls -l ...lcov.info` | ⚠ **없으면 스캐너는 불평 없이 0 을 기록한다.** 여기서 실패시킨다 |

## 2.3 케이스 B — Azure DevOps

**참고 실례**: `vt-api-gateway` 레포 `azure-pipelines.yml` · `scripts/coverage-merged.sh`

### 선행 — CI 담당이 한 번만 (이미 되어 있다)

- 서비스 연결 `sqube-ewoosoft` (SonarQube 타입)
- 에이전트 이미지에 `openjdk-17-jre-headless` — ⚠ 확장이 스캐너는 받아오지만 **JRE 는 받지 않는다**
- 새 파이프라인은 서비스 연결 **첫 사용 승인**이 필요하다 → CI 담당에게 요청

### 절차

**① `2.1` 을 마친다**

**② `main` 트리거가 있는지 확인한다**

⚠ **없으면 추가해야 한다.** 조건만 걸고 트리거가 없으면 스캔이 **영영 안 돈다.**

```yaml
schedules:
  - cron: "0 20 * * *"        # UTC 20:00 = KST 05:00
    displayName: daily main scan
    branches:
      include: [main]
    always: true
```

**③ 파이프라인 맨 끝에 sonar 블록을 넣는다**

```yaml
- ${{ if eq(variables['Build.SourceBranch'], 'refs/heads/main') }}:
  - task: SonarQubePrepare@8
    inputs:
      SonarQube: 'sqube-ewoosoft'
      scannerMode: 'CLI'
      configMode: 'file'          # sonar-project.properties 를 읽는다
  - task: SonarQubeAnalyze@8
  - task: SonarQubePublish@8
    continueOnError: true
```

**④ checkout 이 `fetchDepth: 0` 인지 확인한다**

⚠ `new_coverage` 는 git blame 으로 신규 줄을 판정한다. shallow fetch 면 틀어진다.

**⑤ `2.5` 로 검증한다**

### ⚠ 반드시 지킬 것

| | 왜 |
|---|---|
| **잡 맨 끝에 둔다** | 중간에 두면 스캐너 실패 시 **뒤따르는 보안 게이트가 skip 된다.** 품질 측정이 보안 검사를 무너뜨리면 안 된다 |
| **`main` 조건을 건다** | PR 빌드에서 스캔하면 그 PR 의 부분 수치가 곧 프로젝트 수치가 된다 (1.5) |
| **`extraProperties` 에 exclusions 를 넣지 않는다** | 레포 파일을 덮어쓴다 |
| **task 는 `@8`** | 확장 8.2.4 와 major 를 맞춘다. `SonarQubeScannerCli@3` 는 구세대다 |

### 테스트가 Docker 를 쓰는 경우

ADO 에이전트에는 docker 소켓이 있어 Testcontainers 가 동작한다.

⚠ **커버리지 리포트가 임계값 검사보다 먼저 쓰이게 한다.** 그래야 커버리지가 기준에 못 미쳐
스크립트가 실패해도 수치는 남아 추이를 볼 수 있다.

```sh
bash scripts/coverage-merged.sh || echo "exit=$? — lcov 확인 후 계속"
ls -l coverage/merged/lcov.info
```

## 2.4 케이스 C — Jenkins Windows

**참고 실례**: `sbom/jenkins` 레포 `vars/sharedPipelineSqubeGitDartWin.groovy` ·
`sharedPipelineSqubeGitRustWin.groovy`

⚠ **케이스 A 의 스니펫이 그대로 돌지 않는다.**

| | Linux | Windows |
|---|---|---|
| 셸 스텝 | `sh '...'` | **`bat '...'`** |
| 스캐너 도구 | `tool name: 'SonarQube Scanner'` | **`tool name: 'SonarQube Scanner Windows'`** |
| 환경변수 | `export X=1` | **`set X=1`** |
| Docker | 소켓 없음 | ⚠ **Docker 자체가 없다** |

```groovy
SQUBE_PRE_SCAN: '''
    set CI=1
    node --version
    pnpm --version
    pnpm install --frozen-lockfile
    pnpm test:coverage
    dir coverage\\lcov.info
'''
```

⚠ **Windows 노드는 컨테이너가 아니라 VM 이다.**
- 설치한 도구가 **남는다.** 편하지만 어느 빌드가 무엇을 깔았는지 추적되지 않는다
- 오염되면 **재생성으로 초기화할 방법이 없다**
- 언어 런타임(Rust·Dart 등)을 올리려면 그 VM 에 직접 설치해야 한다 → CI 담당에게 요청

## 2.5 검증 — 이 순서로 확인한다

**① 잡 로그에서** — 리포트가 실제로 생겼나

```
node --version          → 값이 찍히나
pnpm --version          → 레포 선언과 같은가
ls -l coverage/lcov.info → 크기가 0 이 아닌가
```

**② SonarQube 프로젝트 화면에서** — `Lines to cover` 를 본다

| 보이는 것 | 뜻 |
|---|---|
| `Coverage 0.0%` · `Lines to cover` 가 큼 | ⚠ **리포트를 못 읽었다.** ①로 돌아간다 |
| `Lines to cover 0` | 분석 대상 소스가 없다. `sonar.sources` 확인 |
| `Coverage` 가 로컬 실측과 비슷함 | ✅ 정상 |

**③ 로컬 수치와 비교한다**

```bash
pnpm test:coverage        # 로컬에서 한 번 더
```

⚠ 다르면 **`sonar.coverage.exclusions` 와 테스트 러너 exclude 가 어긋난 것**을 먼저 의심한다.
분모가 달라지면 같은 코드에서 다른 숫자가 나온다.

## 2.6 실패 진단

| 증상 | 원인 |
|---|---|
| `Coverage 0.0%` · `Lines to cover` 가 큼 | 리포트가 없다. 잡 로그의 `ls -l` 확인 |
| `Lines to cover 0` | `sonar.sources` 가 비었거나 경로가 틀렸다 |
| 로컬과 CI 수치가 다름 | `sonar.coverage.exclusions` 와 러너 exclude 불일치 |
| 메모리 부족 · 잡이 죽음 | 워커 상한 변수 (2.0 ③). **레포가 무슨 이름을 쓰는지 확인** |
| `new_coverage` 만 이상 | blame 문제. `fetchDepth: 0` 인지, repo 루트에서 스캔하는지 |
| **아침마다 수치가 0** | ⚠ **두 곳에서 스캔하고 있다.** 하나를 꺼야 한다 |
| `new_violations` 가 갑자기 늘어남 | 정상. 테스트 파일이 처음 분석된 것 (2.1) |
| ADO `Could not find 'java'` | 에이전트에 JRE 가 없다 → CI 담당 |
| ADO 가 `Checkpoint.Authorization` 에서 멈춤 | 서비스 연결 첫 사용 승인 대기 → CI 담당 |
| `sonar.branch.name` 오류 | Community 에디션. `main` 빌드에서만 스캔하도록 조건을 건다 |
| `--frozen-lockfile` 실패 | 에이전트 pnpm 과 레포 `packageManager` 불일치 (2.0 ④) |

## 2.7 ⚠ 하면 안 되는 것

이 절의 항목은 전부 **실패하지 않고 잘못된 숫자를 만든다.** 그래서 알아차리기 어렵다.

- **`-Dsonar.exclusions` 를 CI 설정에서 넘기기** — 레포 파일을 덮어쓴다
- **테스트 파일을 `sonar.exclusions` 에 넣기** — 분석에서 통째로 사라진다
- **`ls -l lcov.info` 확인을 빼기** — 리포트가 없어도 0 으로 조용히 기록된다
- **워커 상한 변수를 추측하기** — 레포마다 다르다. 찾아서 확인한다
- **PR 빌드에서 스캔하기** — 부분 수치가 프로젝트 수치를 덮는다
- **한 프로젝트를 두 곳에서 스캔하기** — 나중 것이 이긴다
- **테스트와 스캔을 다른 잡으로 나누기** — 워크스페이스가 달라 리포트를 못 찾는다
- **Jenkins 에이전트에 docker 소켓 붙이기** — 잡이 호스트 Docker 를 제어하게 된다.
  같은 호스트에 dependency-track·sonarqube·jenkins 가 함께 떠 있다
