# PostgreSQL & Jenkins 클라우드 백업 시스템

온프레미스 PostgreSQL 서버와 Jenkins 데이터를 클라우드 스토리지(AWS S3 또는 Azure Blob Storage)로 백업하는 자동화된 시스템입니다.

본 디렉터리의 스크립트는 운영 서버의 `/scripts/postgres-backup` 경로로 심볼릭 링크를 만들어 사용하도록 설계되어 있습니다.

예시

```bash
# 운영 서버에서 심볼릭 링크 구성 예시
sudo mkdir -p /scripts/postgres-backup
sudo ln -sf /path/to/_ops-resources_/bm2databackup/* /scripts/postgres-backup/
sudo chmod +x /scripts/postgres-backup/*.sh
```

## 권장사항: AWS S3

ES BuildMachine2 환경에서는 다음 이유로 AWS S3 사용을 권장합니다.

- 관리 자율성: 독립적으로 관리 가능
- Credential 설정의 자유도
- 운영 효율성: 내부 의존성 최소화
- 비용 효율성: 소규모 백업의 경우 월 비용이 낮음
- Jenkins 최적화: 빌드 히스토리 제외로 백업 크기 최소화

### **3) 클라우드 스토리지 설정 (AWS S3)**

```bash
# [관리자 계정에서 1회 수행] AWS CLI 설정 (관리자 권한)
aws configure  # Access Key, Secret, region: ap-northeast-2

# [관리자] S3 버킷 생성 (이미 존재하면 생략)
aws s3 mb s3://es-buildmachine2-backups --region ap-northeast-2 || true

# [관리자] 버킷 버전 관리 활성화(선택)
aws s3api put-bucket-versioning \
  --bucket es-buildmachine2-backups \
  --versioning-configuration Status=Enabled

# [관리자] 30일 만료 Lifecycle 규칙 적용 (Entire bucket)
cat > lifecycle-30days.json << 'JSON'
{
  "Rules": [
    { "ID": "expire-30d", "Status": "Enabled", "Filter": { "Prefix": "" }, "Expiration": { "Days": 30 } }
  ]
}
JSON
aws s3api put-bucket-lifecycle-configuration \
  --bucket es-buildmachine2-backups \
  --lifecycle-configuration file://lifecycle-30days.json

# [관리자] 백업 전용 IAM 사용자 및 Inline 정책 적용
aws iam create-user --user-name es-buildmachine2-backup-user
cat > buildmachine2-backup-policy.json << 'JSON'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:DeleteObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::es-buildmachine2-backups",
        "arn:aws:s3:::es-buildmachine2-backups/*"
      ]
    }
  ]
}
JSON
# Inline 정책을 사용자에 적용
aws iam put-user-policy \
  --user-name es-buildmachine2-backup-user \
  --policy-name BuildMachine2BackupPolicy \
  --policy-document file://buildmachine2-backup-policy.json

# [관리자] Access Key 발급 (값을 안전하게 보관하세요)
aws iam create-access-key --user-name es-buildmachine2-backup-user

# [백업 서버에서 수행] 위 Access Key/Secret으로 AWS CLI 설정
aws configure  # Access Key, Secret, region: ap-northeast-2
```

AWS 콘솔로 설정하기

- S3 콘솔 → 버킷 `es-buildmachine2-backups` 선택 → Management → Lifecycle rules → Create lifecycle rule
- Rule name: "expire-30d"; Scope: This rule applies to all objects in the bucket (Entire bucket)
- Expiration: Permanently delete current objects (and previous versions, 선택) after 30 days → Create rule

### **4) Jenkins 파이프라인 설정 (Azure DevOps Repo 연동)**

전제조건

- Jenkins 서버(또는 에이전트)에서 Docker CLI 사용 가능하고 `/var/run/docker.sock` 접근 가능
- awscli 설치됨
- Jenkins에 AWS 자격증명 준비(Username/Password 타입 추천)
- Azure DevOps 리포지토리 접근용 PAT 크리덴셜 `azure-devops-pat`가 이미 있음

절차

1. Jenkins Credentials 생성
    - Jenkins → Manage Jenkins → Credentials → System → Global credentials (unrestricted) → Add Credentials
    - Kind: Username with password
    - ID: `aws-backup-user`
    - Username: AWS_ACCESS_KEY_ID, Password: AWS_SECRET_ACCESS_KEY
    - Description: AWS backup inline policy user
2. Jenkins Item 생성 (선택 1: 파이프라인)
    - Jenkins 대시보드 → New Item → 이름 입력(예: `bm2-backup`) → Pipeline → OK
    - Pipeline → Definition: Pipeline script from SCM
    - SCM: Git
    - Repository URL: Azure DevOps Git HTTPS URL (이 저장소 URL)
    - Credentials: `azure-devops-pat` 선택
    - Script Path: `.jenkins/Jenkinsfile`
    - 저장
    
    또는 (선택 2: Multibranch Pipeline)
    
    - New Item → Multibranch Pipeline → Branch Sources에 Azure DevOps Git 설정
    - Credentials: `azure-devops-pat` 선택 후 저장소 URL 입력
    - Build Configuration: by Jenkinsfile (script path: `.jenkins/Jenkinsfile`)
3. 빌드 환경 확인
    - Jenkins 에이전트에서 docker, aws 확인: Manage Nodes → Agent → Script Console 또는 Build log에서 `docker version`, `aws --version`
    - 필요한 경우 에이전트 컨테이너 실행 시 `/var/run/docker.sock` 마운트
4. 수동 실행 및 스케줄 확인
    - Jenkins Job에서 Build Now로 1회 수동 실행해 성공 여부 확인
    - Jenkinsfile의 cron(`H 3 * * *`)에 따라 매일 03:00 근처에 Jenkins가 자동 실행

주의

- 스케줄링은 Jenkins가 담당합니다. 서버 crontab은 사용하지 않습니다.

## S3 저장 구조

- 경로: `s3://es-buildmachine2-backups/<YYYYmmdd_HHMMSS>/`
- 파일명(고정):
    - `postgres.sql.gz`
    - `jenkins.tar.gz`
    - `nginx.tar.gz` (선택)
    - `web.tar.gz` (선택)
    - `uploads.tar.gz` (선택)

복원 시에는 원하는 날짜 폴더를 한 번만 지정하면, 해당 폴더 내의 고정 파일명을 사용합니다.

## 전체 복원 절차

### **복원 전 준비사항**

**복원 스크립트가 작동하려면 다음 Docker 컨테이너가 미리 구성되어 있어야 합니다:**

1. **PostgreSQL 컨테이너** (`abc-wbs-postgres`)
    - 이름이 정확히 `abc-wbs-postgres`여야 함
    - 실행 중일 필요는 없음 (복원 시 자동 시작)
    - 빈 상태여도 됨 (복원 시 데이터 덮어씀)
2. **Jenkins 컨테이너** (`jenkins-server`)
    - 이름이 정확히 `jenkins-server`여야 함
    - Jenkins Docker 볼륨(`jenkins_home`)이 존재해야 함
    - **중요**: Item(Job)이 아예 없어도 됨 - 백업에 Job 설정이 포함되어 있음

### **Docker 컨테이너 구성**

**기존 WBS 서비스(`docker-compose.onpremise.yml`) 사용 시:**

```bash
cd abc_wbs
docker-compose -f docker-compose.onpremise.yml up -d postgres
```

**Jenkins는 별도 구성:**

```bash
docker run -d \
  --name jenkins-server \
  -p 8080:8080 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts
```

### **수동 복원 절차**

1. **복원 스크립트 다운로드**

```bash
git clone https://your-azure-devops-repo-url bm2databackup
cd bm2databackup
```

1. **AWS 자격증명 설정**

```bash
export AWS_ACCESS_KEY_ID="your-access-key"
export AWS_SECRET_ACCESS_KEY="your-secret-key"
export AWS_DEFAULT_REGION="ap-northeast-2"
```

1. **복원 실행**

```bash
chmod +x restore_es_buildmachine2.sh
./restore_es_buildmachine2.sh 20241221_020000
```

1. **복원 후 WBS 서비스 시작**

```bash
cd abc_wbs
docker-compose -f docker-compose.onpremise.yml up -d
```

### **복원 스크립트 동작 흐름**

1. **서비스 중지**: jenkins-server, nginx-proxy 중지
2. **S3 다운로드**: PostgreSQL, Jenkins, Nginx, Web, Uploads 백업 파일 다운로드
3. **PostgreSQL 복원**: `psql`로 데이터베이스 복원
4. **Jenkins 복원**: Jenkins 볼륨을 완전히 비운 후 tar 압축 해제로 복원
5. Jenkins는 플러그인 포함 전체 백업/복원 (plugins.txt 불사용)
6. **Uploads 복원**: `./uploads` 디렉토리에 업로드 파일 복원 (WBS 서비스용)
7. **정적 파일 복원**: Nginx, Web 복원
8. **서비스 시작**: 모든 컨테이너 재시작
