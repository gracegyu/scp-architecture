# 6.1 SonarQube에 테스트 커버리지 연동하기

> 대상: 자기 프로젝트를 SonarQube 에 붙이려는 개발자
> 선행: `6. Docker에 SonarQube 설치.md` (서버는 이미 떠 있다)

---

## 0. 한 줄 요약

> **스캐너는 커버리지를 읽을 뿐 만들지 않는다.** CI 잡이 테스트를 돌려 리포트를 남겨야 한다.

커버리지가 `0.0%` 로 보인다면 대개 코드 문제가 아니다. **리포트가 없어서** 스캐너가
"한 줄도 커버되지 않음" 으로 기록한 것이다. `0.0` 은 "측정 안 함" 이 아니다.

구분하는 법 — SonarQube 프로젝트 화면에서 **Lines to cover** 를 본다.

| 보이는 것 | 뜻 |
|---|---|
| `Coverage 0.0%` · `Lines to cover 6337` · `Uncovered 6337` | ⚠ **리포트가 없다.** 배선 문제 |
| `Coverage 0.0%` · `Lines to cover 0` | 분석 대상 소스가 없다. `sonar.sources` 확인 |
| `Coverage 91.6%` · `Uncovered 128` | 정상 |

---

## 1. ⚠ 먼저 — 이 숫자는 무엇을 재는가

**커버리지는 하나가 아니다.** 어떤 테스트를 돌렸느냐에 따라 전혀 다른 숫자가 나온다.
프로젝트끼리 비교하기 전에 무엇을 합산했는지 확인해야 한다.

사내 두 사례가 실제로 다르다.

| 프로젝트 | 합산 대상 | 제외 | 수치 |
|---|---|---|---|
| **vt-api-gateway-console** | **unit + component**<br>(vitest `unit`·`component` 프로젝트) | ⚠ **E2E(playwright) 제외** | 91.6% |
| **vt-api-gateway** | **unit + E2E 합산**<br>(jest unit + jest e2e, `nyc` 병합) | — | 96.3% |

⭐ **96.3 과 91.6 은 같은 척도가 아니다.** GW 가 Console 보다 테스트를 잘 짰다는 뜻이 아니라,
**GW 는 E2E 로 커버되는 줄까지 세고 Console 은 안 센다.**

### 무엇을 합산할지 어떻게 정하나

| 방식 | 언제 | 대가 |
|---|---|---|
| **unit 만** | 가장 가볍다. 로컬에서 빨리 돈다 | ⚠ 컨트롤러·가드·미들웨어·라우팅 **배선 계층이 0% 로 잡힌다.** 그 계층을 E2E 로 검증하는 구조라면 수치가 실제보다 **낮게** 나온다 |
| **unit + component** | 프론트엔드에서 흔하다. 렌더링까지 본다 | E2E 로만 닿는 경로는 빠진다 |
| **unit + E2E 합산** | 배선 계층까지 정직하게 센다 | ⚠ E2E 가 DB·외부 의존을 띄우면 **무거워지고 Docker 가 필요**하다. 그러면 Jenkins 가 아니라 ADO 로 가야 한다(3절) |

⚠ **undercount 가 미실행보다 나쁠 수 있다.** Quality Gate 기준이 `new_coverage >= 80` 인데
배선 계층이 빠져 70 으로 나오면, 통과해야 할 것이 떨어진다. 그러면 숫자를 믿지 않게 되고,
믿지 않는 게이트는 결국 꺼진다.

⚠ **`sonar.coverage.exclusions` 를 테스트 러너 설정과 맞춘다.** 어긋나면 분모가 달라져
로컬에서 본 숫자와 SonarQube 숫자가 다르게 나온다. 둘을 같은 기준으로 유지하는 것이
레포 안에서 관리해야 하는 이유다.

---

## 2. 어떤 방식이 있나

**두 가지다. 고르는 게 아니라 프로젝트 조건이 정한다.**

| | Jenkins 잡 | Azure DevOps 파이프라인 |
|---|---|---|
| 스캐너 실행 | `sonar-scanner` CLI | `SonarQubePrepare/Analyze/Publish@8` |
| Docker 필요한 테스트 | ❌ **불가** | ✅ 가능 |
| 이미 ADO 에서 테스트가 돈다 | 중복 실행 | ✅ 자연스럽다 |
| 실행 시점 | 야간 정기 | 커밋·PR·정기 선택 |
| 사내 사례 | Console | GW |

### 판단 순서

```
① 테스트 실행에 Docker 가 필요한가?
     예  → ADO   (Testcontainers 로 DB·큐를 띄우는 경우 등)
     아니오 → ②

② 이미 ADO 파이프라인에서 같은 테스트가 돌고 있나?
     예  → ADO   (중복 실행을 피한다)
     아니오 → Jenkins
```

### ⚠ 왜 Docker 가 필요하면 Jenkins 가 안 되나

**Jenkins 에이전트 컨테이너에는 docker 소켓이 마운트돼 있지 않다.** 이미지에 docker CLI 는
있지만 붙을 데몬이 없다 — 바이너리가 있는 것과 데몬에 붙는 것은 다르다.

소켓을 붙이면 잡이 **호스트 Docker 를 제어**하게 된다. 같은 호스트에 dependency-track ·
sonarqube · jenkins · abc-wbs 가 함께 떠 있고, Testcontainers 가 띄우는 DB 는 에이전트
메모리 상한 **밖에서** 호스트 메모리를 직접 먹는다. 2026-09 에 이 호스트가 메모리 고갈로
멈춘 적이 있어(load average 249) 그 경계를 열지 않는다.

ADO 에이전트에는 소켓이 있다. 그래서 GW 는 ADO 로 간다.

### ⚠ 같은 프로젝트를 두 곳에서 스캔하지 않는다

**나중에 쓴 쪽이 이긴다.** SonarQube Community 에는 브랜치 구분이 없어서, 커버리지 없는
스캔이 한 번 돌면 그전 수치가 `0` 으로 돌아간다. 낮에는 맞다가 아침에 틀려 있어서
원인을 찾기 어렵다.

## 3. 환경이 영향을 주나

### Windows / macOS — **개발자 PC 는 상관없다**

CI 에이전트는 전부 **Linux 컨테이너**다. 개발자가 Windows 를 쓰든 macOS 를 쓰든 CI 결과는
같다. 다만 로컬에서 확인할 때 두 가지가 다르다.

| | 주의 |
|---|---|
| **Windows** | ⚠ 로컬에서 워커 상한 없이 돌리면 메모리를 많이 먹는다. `CI=1` 을 주고 돌려보면 CI 와 같은 조건이 된다 |
| **macOS** | 로컬 실측이 CI 와 대체로 일치한다. 다만 **메모리 사용량은 컨테이너 상한과 다르다** — 로컬 730MB 가 CI 에서 같다는 보장은 없다 |

⭐ 로컬 수치와 CI 수치가 다르면 **`sonar.coverage.exclusions` 와 테스트 러너 exclude 가
어긋난 것**을 먼저 의심한다.

### 언어 — 리포트 형식과 속성 이름만 다르다

| 언어 | 리포트 | `sonar-project.properties` 키 |
|---|---|---|
| TypeScript / JavaScript | `lcov.info` | `sonar.javascript.lcov.reportPaths`<br>`sonar.typescript.lcov.reportPaths` |
| Python | `coverage.xml` | `sonar.python.coverage.reportPaths` |
| Java | JaCoCo `.xml` | `sonar.coverage.jacoco.xmlReportPaths` |
| C# | OpenCover / Cobertura | `sonar.cs.opencover.reportsPaths` |
| Dart / Flutter | `lcov.info` | `sonar.flutter.coverage.reportPath` |
| Rust | `lcov.info`(grcov 등) | `sonar.rust.lcov.reportPaths` (플러그인 필요) |

⚠ **경로는 상대 경로**이고 **스캐너가 도는 위치 기준**이다. 모노레포에서 하위 폴더를 스캔하면
그 기준이 달라진다.

### 그 밖의 환경 요인

- **테스트가 외부 서비스를 필요로 하나** — DB·큐·메일 서버 등. Testcontainers 로 띄우면
  Docker 가 필요하고, 실제 외부 서버에 붙으면 CI 에서 네트워크가 열려 있어야 한다
- **테스트 시간** — 정기 야간 잡이면 수 분은 괜찮다. 커밋마다 돌리면 체감이 다르다
- **메모리** — 에이전트 컨테이너에 상한이 있다(Jenkins 3g · ADO 6g). 테스트 러너가
  코어 수만큼 워커를 띄우면 넘는다. 4절의 `CI` 항목 참조

## 4. ⚠ 반드시 챙겨야 할 것 — 안 하면 조용히 틀린다

이 절의 항목은 전부 **실패하지 않고 잘못된 숫자를 만든다.** 그래서 알아차리기 어렵다.

### ① 워커 상한 환경변수

테스트 러너는 보통 **코어 수만큼 워커를 띄운다.** 빌드 호스트는 32 코어이고 에이전트
컨테이너 상한은 3~6GB 다. 그대로 돌리면 넘는다.

대부분의 레포가 설정에 상한을 걸어 두는데 **조건이 레포마다 다르다.**

```js
// Console
maxWorkers: (process.env.CI ?? process.env.TF_BUILD) ? 2 : undefined
// GW
// jest.config.js — GW_CI_LIMIT_WORKERS 로 분기
```

⚠ **Jenkins 는 `CI` 를 자동으로 넣지 않는다.** ADO 는 `TF_BUILD` 를 넣지만 `CI` 는 넣지 않는다.
**잡에서 명시적으로 export 한다.**

```sh
export CI=1                      # vitest/jest 관례
export GW_CI_LIMIT_WORKERS=1     # 레포가 쓰는 이름이 따로 있으면 그것도
```

⭐ 자기 레포 설정 파일을 열어 **무슨 변수를 보는지 직접 확인할 것.** 추측하면 빗나간다.

### ② lockfile 과 패키지 매니저 버전

```sh
pnpm install --frozen-lockfile
```

⚠ `--frozen-lockfile` 없이 설치하면 lockfile 과 다른 버전이 깔릴 수 있고, **스캔 결과가
실제 배포본과 달라진다.**

⚠ 에이전트에 깔린 pnpm 버전이 레포의 `packageManager` 선언과 다르면 `--frozen-lockfile` 이
깨지거나 **lockfile 을 조용히 다시 쓴다.** Jenkins 에이전트는 corepack 이 켜져 있어
레포 선언을 따른다 — 레포 `package.json` 에 `packageManager` 를 적어 두면 된다.

### ③ exclusions 는 레포가 정본이다

`sonar-project.properties` 에 적는다. **CI 설정에서 `-Dsonar.exclusions` 로 넘기지 않는다** —
넘기면 레포 파일을 덮어쓴다.

⚠ **테스트 파일을 `sonar.exclusions` 에 넣지 않는다.** 넣으면 테스트 코드가 분석에서
**통째로 사라진다.** 테스트는 `sonar.tests` 로 분류한다 — 분석은 하되 제품 코드와 다른
잣대를 적용하기 위한 것이다.

```properties
sonar.sources=src,app
sonar.tests=src,tests
sonar.test.inclusions=**/*.test.ts,**/*.test.tsx,tests/**/*
sonar.exclusions=src/generated/**,src/locales/**,**/*.d.ts
sonar.coverage.exclusions=src/generated/**,src/test/**   # 테스트 러너 exclude 와 맞춘다
```

⭐ **이것을 고치면 `new_violations` 가 늘어난다.** 회귀가 아니라, 그동안 분석되지 않던
테스트 코드에 규칙이 처음 도는 것이다. 사내 두 프로젝트에서 모두 일어났다.

### ④ 리포트가 실제로 생겼는지 확인한다

```sh
ls -l coverage/lcov.info
```

⚠ **스캐너는 리포트가 없어도 불평하지 않는다. 커버리지 0 으로 기록한다.**
잡에서 확인하고 없으면 거기서 실패시킨다. 그래야 "왜 0 이지" 가 아니라
"lcov 가 안 생겼다" 로 보인다.

### ⑤ blame 이 필요하다

`new_coverage`(신규 코드 커버리지)는 **git blame 으로 신규 줄을 판정**한다.
`.git` 이 온전해야 한다.

⚠ ADO 의 `fetchDepth: 1`(shallow) 이면 신규 코드 구분이 틀어진다. `fetchDepth: 0` 으로 둔다.
Jenkins 에서는 **repo 루트에서 스캐너를 돌려야** blame 이 동작한다.

### ⑥ 로그에 버전을 남긴다

```sh
node --version
pnpm --version
```

결과가 이상할 때 제일 먼저 보게 되는 값이다. 두 줄이 없으면 원인 추적이 몇 배 길어진다.

## 5. 쉬운 경우 — 기존 사례를 복사한다

자기 프로젝트가 아래 둘 중 하나에 가까우면 그 파일을 열어 그대로 따라 한다.

### 5-A. Jenkins · Docker 불필요 (Console 형)

**참고 파일**: `sbom/jenkins` 레포 `jenkinsfiles/vt-api-gateway-console-SonarQube.jenkinsfile`

**① 레포에 `sonar-project.properties` 를 만든다** (4절 ③ 참고)

**② Jenkins 잡 설정에 테스트 명령을 넣는다** — CI 담당자에게 요청하거나 직접 PR

```groovy
SQUBE_PRE_SCAN: '''
    set -e
    export CI=1
    node --version
    pnpm --version
    pnpm install --frozen-lockfile
    pnpm test:coverage
    ls -l coverage/lcov.info
''',
```

⭐ **`pnpm test:coverage` 처럼 레포 스크립트를 부른다.** 명령을 잡에 박지 않는다 —
나중에 플래그를 바꿀 때 잡을 고치지 않아도 된다.

**③ 잡을 한 번 돌리고 SonarQube 에서 `Lines to cover` 를 확인한다**

### 5-B. Azure DevOps · Docker 필요 (GW 형)

**참고 파일**: `vt-api-gateway` 레포 `azure-pipelines.yml` · `scripts/coverage-merged.sh`

**① 레포에 `sonar-project.properties` 를 만든다**

**② 파이프라인 **맨 끝**에 sonar 블록을 넣는다**

```yaml
- ${{ if eq(variables['Build.SourceBranch'], 'refs/heads/main') }}:
  - task: SonarQubePrepare@8
    inputs:
      SonarQube: 'sqube-ewoosoft'     # 서비스 연결 이름
      scannerMode: 'CLI'
      configMode: 'file'               # sonar-project.properties 를 읽는다
  - task: SonarQubeAnalyze@8
  - task: SonarQubePublish@8
    continueOnError: true
```

⚠ **잡 맨 끝에 둔다.** 중간에 두면 스캐너가 실패했을 때 **뒤따르는 보안 게이트가 skip 된다.**
품질 측정이 보안 검사를 무너뜨리면 안 된다.

⚠ **`main` 조건을 건다.** Community 에디션은 브랜치 구분이 없어서, PR 빌드에서 스캔하면
그 PR 의 부분 수치가 곧 프로젝트 수치가 되고 다음 PR 이 또 덮는다.
**`main` 트리거(또는 daily schedule)가 없으면 추가해야 한다** — 없으면 스캔이 영영 안 돈다.

⚠ **`extraProperties` 에 `sonar.exclusions` 를 넣지 않는다.** 레포 파일을 덮어쓴다.

## 6. 새로운 경우 — 개발이 필요할 때

기존 사례와 다르면 순서대로 정한다.

### ① 무엇을 합산할지 정한다 (1절)

배선 계층을 E2E 로 검증하는 구조라면 **unit 만으로는 수치가 낮게 나온다.** 합산이 필요하면
리포트를 병합해야 한다.

**병합 예** — GW `scripts/coverage-merged.sh`

```
jest unit  → coverage/unit/coverage-final.json
jest e2e   → coverage/e2e/coverage-final.json
nyc 로 병합 → coverage/merged/lcov.info
```

⭐ **lcov 는 임계값 검사보다 **먼저** 쓴다.** 그래야 커버리지가 기준에 못 미쳐 잡이 실패해도
수치는 SonarQube 에 남아 추이를 볼 수 있다.

### ② 실행 위치를 정한다 (2절 판단 순서)

### ③ Jenkins 라면 — 공용 파이프라인에 옵트인

`vars/sharedPipelineSqubeGit.groovy` 의 `SQUBE_PRE_SCAN` 은 **지정한 잡에서만** 돈다.
지정하지 않은 잡은 동작이 변하지 않는다(C#·Rust 프로젝트도 같은 파이프라인을 쓴다).

### ④ ADO 라면 — 서비스 연결이 필요하다

**최초 1회**, CI 담당자가 준비한다.

```
Server URL  http://sqube.ewoosoft.com
Token       ado-ci 계정의 PROJECT_ANALYSIS_TOKEN
Name        sqube-ewoosoft
```

⚠ **분석 토큰은 `USER_TOKEN` 으로 내지 않는다.** 새 계정은 `sonar-users` 기본 그룹에
자동으로 들어가고 그 그룹이 이슈 심사 권한을 갖는다 — **CI 토큰으로 취약점을 "오탐" 으로
닫을 수 있게 된다.** 기본 그룹에서 뺄 수도 없다(서버가 거부).
발급 절차는 `sbom/jenkins` 레포 `admin/sq_bootstrap.py --ci-account` 참조.

⚠ **새 서비스 연결은 첫 사용에 승인이 필요하다.** 파이프라인 단위로 부여한다 —
run 단위 permit 은 재실행마다 다시 막힌다.

⚠ **ADO 에이전트에 Java 가 필요하다.** SonarQube 확장이 스캐너는 받아오지만 **JRE 는 받지
않는다.** 에이전트 이미지에 `openjdk-17-jre-headless` 가 들어 있다(2026-09-21 추가).
`JavaToolInstaller@0` 의 `PreInstalled` 는 Microsoft 호스팅 에이전트 전제라 쓸 수 없다.

### ⑤ 기존 스캔이 있으면 전환 순서를 지킨다

```
① 새 경로에 스캔 추가
② SonarQube 에서 coverage 가 올라온 것 확인
③ 그때 기존 스캔을 끈다
```

⚠ **②보다 먼저 끄면 공백**이 생기고, **②가 끝난 뒤에도 안 끄면 덮어쓴다.**
같은 사실이 시점에 따라 반대 결론을 낸다.

## 7. 안 될 때 어디를 보나

| 증상 | 먼저 볼 것 |
|---|---|
| `Coverage 0.0%` · `Lines to cover` 가 큼 | **리포트가 없다.** 잡 로그에서 `ls -l ...lcov.info` 확인 |
| `Lines to cover 0` | `sonar.sources` 가 비었거나 경로가 틀렸다 |
| 로컬과 CI 수치가 다름 | `sonar.coverage.exclusions` 와 테스트 러너 exclude 가 어긋났다 |
| 메모리 부족 · 잡이 죽음 | 워커 상한 환경변수(4절 ①). 레포가 무슨 변수를 보는지 확인 |
| `new_coverage` 만 이상함 | blame 문제. `fetchDepth: 0` 인지, repo 루트에서 스캔하는지 |
| 아침마다 수치가 0 | **두 곳에서 스캔하고 있다.** 하나를 꺼야 한다 |
| `new_violations` 가 갑자기 늘어남 | 정상이다. 테스트 파일이 처음 분석된 것(4절 ③) |
| ADO `Could not find 'java'` | 에이전트 이미지에 JRE 가 없다. CI 담당자에게 문의 |
| ADO 가 `Checkpoint.Authorization` 에서 멈춤 | 서비스 연결 첫 사용 승인 대기 |
| `sonar.branch.name` 오류 | Community 에디션. `main` 빌드에서만 스캔하도록 조건을 건다 |

## 8. 알려진 제약

**SonarQube Community 25.4** 를 쓴다. 다음은 상위 에디션 기능이다.

- **브랜치 분석** — 프로젝트당 브랜치 하나(`main`)만 분석된다
- **PR decoration** — PR 화면에 품질 결과가 표시되지 않는다

⭐ 그래서 스캔은 **머지된 뒤 `main` 에서만** 돈다. PR 단계에서 품질 피드백을 받으려면
Developer Edition 이 필요하고, 그것은 별도 판단 사안이다.
