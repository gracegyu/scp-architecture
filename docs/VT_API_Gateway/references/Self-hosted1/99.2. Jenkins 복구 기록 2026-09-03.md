# 99.2. Jenkins 복구 기록 (2026-09-03)

> win10 VM 재기동(Jenkins Windows 노드 복구 목적) 과정에서, Jenkins 마스터의 **잠복 문제(플러그인이 코어보다 최신인데 미재시작 상태)** 가 재시작으로 표면화되어 부팅 실패 → 코어·플러그인 정합화로 **클린 복구**한 기록. SSH(스펙 세션)로 수행.

## 1. 사건 경위

- **트리거**: win10 VM 재기동 후 Jenkins 마스터 재시작.
- **잠복 문제**: 플러그인이 UI에서 최신으로 업데이트돼 있었으나(commons-lang3-api 등 코어 ≥2.479.3, 일부 `-api`는 ≥2.555.1 요구) **Jenkins가 재시작된 적이 없어** 옛 버전을 메모리로 계속 돌고 있었음. 재시작 = 디스크의 새 플러그인 로드 시도 → 코어 부족으로 `HudsonFailedToLoad`.
- 이 지뢰는 **어떤 재시작(재부팅·크래시)에서도 터졌을 상태**였음(메모리 캡 작업과 무관).

## 2. 코어 버전 결정 — 2.541.3-jdk17 (Java 17)

**정확한 타임라인 (Java는 17→21→17·순 결과=17 유지 · 코어는 2.462.3→2.568.3→2.541.3·순 결과=상향):**

| 단계 | Jenkins 코어 | Java | 상태 |
| --- | --- | --- | --- |
| **원래**(4개월 구동) | 2.462.3 | **17**(17.0.12) | 정상 구동이나 디스크 플러그인은 이미 최신(코어 요구 초과)·마스터 미재시작이라 옛 플러그인 메모리 구동 |
| 재시작(사건 발생) | 2.462.3 | 17 | 디스크 새 플러그인 로드 시도 → **코어 부족·부팅 실패** |
| 1차 시도 | **2.568.3**(최신 LTS) | **21** | 플러그인 0 실패지만 **에이전트(Java 17)가 `UnsupportedClassVersionError`로 못 붙음** → 반려 |
| **최종** | **2.541.3**(`lts-jdk17`) | **17**(17.0.18) | **플러그인 요구 충족 + Java 17이라 에이전트 호환** ✅ |

- **핵심**: **Java는 원래부터 17이고 최종도 17**(중간 2.568.3에서 잠깐 21을 밟았다가 에이전트 비호환으로 즉시 되돌림 = 17→21→17). 실제로 바뀐 것은 **Jenkins 코어를 올린 것**(2.462.3 → 2.541.3). "Java를 내렸다"가 아니라 "**Java 17 유지 + 코어 상향**"이 정확한 표현.
- `2.541.3`이 **Java 17로 도는 마지막 LTS**(`lts-jdk17` 태그). 그 위(2.555.1+)는 Java 21 전용이라 에이전트를 못 붙임 → 그래서 Java 21 이관은 향후 숙제(§9).

## 3. 플러그인 정합화 (핵심)

- **1차 시도(실패)**: Jenkins가 남긴 `<name>.bak`(이전 버전) 124개를 일괄 복원 → `.bak`들이 시점이 제각각(Jun 12·Aug 25)이라 **일관 스냅샷이 아니어서** 플러그인 간 의존 버전 불일치로 **32개 실패**(git·pipeline·workflow-cps·docker-workflow 등 CI 핵심 포함).
- **2차(성공)**: **Jenkins 공식 Plugin Installation Manager Tool**(`jenkins-plugin-manager-2.15.0.jar`)로 현재 설치 목록(134개)을 입력해 **2.541.3 호환 일관 세트(137개)를 업데이트 센터에서 재해석·다운로드** → 교체 → **0 실패**.
  - 명령: `java -jar pm.jar --war /usr/share/jenkins/jenkins.war --plugin-download-directory /tmp/newplugins --plugin-file /tmp/plugins.txt --latest true`
  - 깨진 세트 백업: `/var/jenkins_home/plugins.broken-bak`
  - `prism-api`(2.555.1·고아 플러그인): `plugins.broken-bak`에 보존(비활성).

## 4. 마스터 컨테이너 재생성 파라미터

```bash
docker run -d --name jenkins-server --restart always -u root \
  --network webnet \
  --dns 192.168.6.140 --dns 192.168.6.5 --dns 192.168.6.40 \
  -p 8090:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  -e JAVA_OPTS=-Xmx2g \
  --memory 3g --memory-swap 3g \
  jenkins/jenkins:lts-jdk17   # = 2.541.3
```

## 5. 부수 조치 (같은 세션)

- **메모리 캡**(호스트 62.4G OOM 방지): LinuxNode×4=3g · DT=8g · SonarQube=4g · Jenkins=3g(`-Xmx2g`) · Azure×4=6g(기존). 상세 = [메모리-캡-배분안](../CI-DevSecOps-SelfHosted/메모리-캡-배분안.md).
- **nginx**: 활성 `default.conf`가 깨져 있던 것(heredoc 생성 스크립트 잔여 `EOL`) → 사용자가 `default.conf.bak` 기준 복구 → 컨테이너 재시작 → **sbom·sqube·dtrack·wbs 전부 200**. (⚠ `default.conf`를 자동 생성하는 스크립트가 있어 재배포 때 또 깨질 수 있음 → 원인 스크립트 확인 필요. 백업=`default.conf.org`)
- ⚠ **접속은 `http://sbom.ewoosoft.com`** — 이 nginx는 80(http)만 서빙. https로 접속하면 안 됨.

- ✅ **Linux 에이전트 4대 online**(LinuxNode1~4).

- ✅ nginx 라우팅 정상.

## 7. Windows 노드 복구 (2026-09-07 완료)

- **경위**: win10 VM 내부 Jenkins 에이전트 서비스(WinSW: `JenkinsAgentNode1`/`JenkinsAgentNode2`)가 마스터 다중 재시작 중 끊겼음. WindowsNode2는 이번 사건 전부터 offline.
- **조치(RDP·VM 내부)**: win10 VM에서 두 WinSW 서비스 재시작 → Jenkins UI 확인.
- **결과**: **6개 노드(LinuxNode1~4 + WindowsNode1·2) 전부 online** 확인(2026-09-07 UI 기준).
- 참고: 두 Windows 서비스가 Automatic인데 부팅 시 1개만 자동 start되는 현상 → startup type을 **Automatic (Delayed Start)** 로 두면 재발이 줄어듦.
- 호환성: 마스터 코어 2.541.3(Java 17·class 61)은 win10의 JDK(구축 문서상 23)와 호환. `agent.jar`는 재접속 시 자동 갱신됨.
- 계측 노트: 호스트 `ss`로는 win10 VM(libvirt 192.168.122.x) 연결이 안 보임 — docker-proxy가 출처를 172.18.0.1로 마스킹해 LinuxNode와 구분 불가. **노드 online 판정의 정본 = Jenkins UI**(호스트 네트워크 스냅샷 아님).

## 9. Java 21 이관 (밀린 유지보수·기한 경과)

> **진행 상태 (2026-09-07)**: **✅ 이관 완료 — 마스터·에이전트 전부 Java 21.**
>
> **2단계 실행 내역(마스터)**: 코어를 `jenkins/jenkins:lts` = **2.568.3(Java 21.0.12.1)** 으로 교체(§4 run 파라미터 동일·이미지 태그만 변경). 현재 플러그인 세트(2.541.3용·모두 코어 요구 ≤2.541.3)는 더 높은 코어에서 그대로 로드 → **부팅 0 실패**·nginx(sbom) 200·6노드 재접속. 롤백점 = `jenkins/jenkins:lts-jdk17`(2.541.3) 이미지. **1단계로 에이전트를 미리 Java 21화해 둔 덕에**, 복구 때 막혔던 "2.568.3에서 에이전트 탈락"이 재현되지 않고 깔끔히 정렬됨.
> **플러그인 refresh (2026-09-07 완료)**: 코어 상향 직후 UI에 업데이트 15건(그 중 `pipeline-groovy-lib` 보안 패치 SECURITY-3815·CSRF)이 떠서, plugin-manager로 **2.568.3용 최신 세트(137개)를 재해석·교체** → **0 실패**·보안 플러그인 `pipeline-groovy-lib` 805.va_fc79344957d 로 갱신. 교체 전 롤백 백업 = `/var/jenkins_home/plugins.pre-refresh`. (2.568.3은 최신 코어라 straggler 없음 = 복구 때와 반대의 쉬운 방향.)
>
> **deprecated 플러그인 정리 (2026-09-07 완료)**: Manage Jenkins에 뜨던 deprecated 경고 = 전부 **Blue Ocean 계열(옛 대체 UI·Jenkins 프로젝트가 개발 중단)**. UI 레이어라 빌드·파이프라인 실행과 무관하고 대체재(Pipeline: Graph View)가 이미 설치돼 있어 **`blueocean*` 19개 일괄 삭제**(백업 `/var/jenkins_home/plugins.pre-blueocean`) → 플러그인 137→118·**0 실패**·deprecated 경고 해소.
>
> **1단계 실행 내역(에이전트)**: `jenkins-node:latest`(17개월 전 빌드·Java 17) 위에 **Temurin 21 레이어**를 얹어(`/opt/java/openjdk` 심링크를 jdk21로 교체·기존 Dart/Flutter/FVM/node/docker/az 툴체인 전부 보존) `jenkins-node:java21` 빌드 → LinuxNode1~4 재생성(이름·secret·workdir·3g 캡·**내부 DNS `192.168.6.5/140/40`** 유지). **4대 모두 현재 마스터(2.541.3·Java 17)에 "Connected" 재접속 확인** — Java 21 에이전트가 Java 17 마스터에 하위호환으로 붙음을 실증. 롤백용 `jenkins-node:java17-bak` 태깅 보존. Windows 노드는 이미 JDK 23이라 불요.
> - ⚠ **주의(1단계 재현 시)**: LinuxNode는 내부 호스트(`sbom.ewoosoft.com`) 해석을 위해 **`--dns 192.168.6.5 --dns 192.168.6.140 --dns 192.168.6.40`가 필수**(누락 시 `UnknownHostException`으로 재접속 실패). azp-agent와 동일.
> - ⚠ **영속성 후속**: 현재는 `jenkins-node:java21` 이미지로만 반영됨. 원본 `jenkins-node.dockerfile`(Java 17 베이스)은 아직 미수정 → 원본에서 재빌드하면 Java 17로 회귀. 원본 dockerfile에 Java 21 반영은 후속 정리 대상.

- **왜**: 이번 복구로 맞춘 **Java 17 코어(2.541.3)는 임시 고정점**이다. Java 17은 Jenkins 기준 **2026-03-31 EOL**, LTS는 **2026-05-13(2.555.1)부터 Java 21 전용**으로 Java 17 지원을 제거했다. 즉 2.541.3은 직전 세대라 **보안 백포트가 이미 끊긴 상태**(미패치 노출 누적). GW 서비스와 무관(GW CI는 Jenkins 미사용). 리스크는 격리(사내 abc-wbs 제품 스캔용·외부 미노출)되나 **미룰 수 없는 밀린 유지보수**.
- **핵심 구분 — "Java(JDK) 업그레이드"와 "Jenkins SW 업그레이드"는 별개**이고, 대상마다 손대는 범위가 다르다:

  | 대상 | 현재 | 필요 작업 |
  | --- | --- | --- |
  | **마스터**(`jenkins-server`) | 2.541.3 / Java 17 | **이미지 교체 한 번**(`jenkins/jenkins:lts` = 최신 코어 + Java 21 내장) — §4 run 파라미터 그대로, 태그만 변경 |
  | **Linux 에이전트**(`LinuxNode1~4`) | `jenkins-node:latest`에 Java 17 내장 | **Java 21로 재빌드**만(`/home/raymond/azp-agent-in-docker/jenkins-node.dockerfile`의 베이스를 jdk21로) → 4개 컨테이너 재생성. **agent.jar는 손대지 않음**(마스터 접속 시 자동 다운로드) — 즉 "Java 런타임만 21이면" 됨 |
  | **Windows 에이전트**(`WindowsNode1~2`) | win10 VM에 **JDK 23** | **손댈 것 없음**(이미 Java 21 요건 충족·agent.jar 자동 갱신) |

- **순서(중요)**: **에이전트(Linux) Java 21 재빌드 먼저 → 마스터 최신 LTS 나중.** 반대로 하면(마스터를 Java 21 전용 최신으로 먼저 올리면) Java 17 에이전트가 `UnsupportedClassVersionError`로 못 붙어 **전 노드 탈락** — 이번 사건(2.568.3 시도) 때 정확히 그랬음.
- **실행 시점**: CI 한가한 창. 앞당김 트리거 = 2.541.3 심각 보안 권고(CVE) 또는 필수 플러그인 비호환.
