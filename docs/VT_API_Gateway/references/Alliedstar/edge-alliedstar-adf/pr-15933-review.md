## 확인한 것 (업체 공식 문서 대조)

- Alliedstar 보안 문서의 규칙과 같다 — `sign` 과 빈 값 제외 · 이름 오름차순 · `이름=값` 을 `&` 로 연결 · SHA256WithRSA(PKCS#1 v1.5) · Base64.
- **공식 예제의 정규 문자열과 서명을 공식 공개키로 검증**한다 — 우리 구현이 업체와 같은 문자열을 만든다는 가장 강한 근거다.
- 값을 URL 인코딩하거나 JSON 을 다시 직렬화하지 않는다("복합 객체는 JSON 문자열로 바꿔 넣는다"는 업체 규칙대로 호출자가 직렬화). `URLSearchParams` 로 만든 문자열이 검증에 실패하는 반례 테스트가 좋다.
- 공개키·비 RSA·RSA-PSS·1024비트 키를 거부한다.
- **fixture 에 개인키가 없다.** `appid`·`openid` 는 업체 문서에 공개된 테스트 값이다.
- 공통 프록시에서 import 하지 않는다 — "common proxy 에 vendor 분기를 넣지 않는다"는 방향과 맞다.

## 짚을 것

1. **정렬 기준이 주석과 다르다.** `Array.prototype.sort()` 는 UTF-16 코드 단위 순서인데 테스트 이름은 "code point" 다. 업체 문서는 "ascending alphabetical" 뿐이다. 업체 파라미터 이름은 모두 ASCII 라 실제로 차이는 없으니, **이름을 ASCII(`^[A-Za-z0-9_]+$`)로 제한**해 모호함을 없애는 편을 제안한다(지금은 `&`·`=` 만 거부).
2. **공백만 있는 값.** `" "` 는 빈 값으로 보지 않고 서명에 넣는다. 업체 SDK 가 trim 후 빈 값을 빼는지 확인되지 않았다. 실제 API 로 한 번 확인하기 전까지 현행 유지가 맞고, 확인 결과를 테스트로 고정하면 된다.
3. **콜백 검증 helper 가 없다.** 업체 문서상 콜백도 Alliedstar 가 자기 개인키로 RSA2 서명한다(`sign` 이 JSON 본문 안에 있음). 콜백을 GW 가 받으려면 검증 쪽(공개키 verify + JSON 본문의 정규화 규칙)이 필요하다. 이 PR 범위 밖이니 후속 과제로 둔다.
