# self-hosted 빌드 호스트(wbs.ewoosoft.com) — 메모리 캡 배분안

> OOM 대책은 **Azure 에이전트 4대에만** 캡(6GB)을 걸었을 뿐, 같은 호스트의 Jenkins·SonarQube·Dependency-Track·Jenkins Linux 노드는 **전부 무제한**이었다. 특히 두 개의 치명적 JVM 천장(DT `MaxRAMPercentage=90`→호스트 56GB, Jenkins 기본 힙 16.7GB)을 하나만 팽창시켜도 호스트가 죽는다. 본 문서는 **모든 대형 소비자에 캡을 걸어 폭주로 인한 호스트 다운을 구조적으로 차단**하는 배분안이다.

- **작성/개정**: 2026-09-03 (스펙 세션·SSH 구축)
- **대상 호스트**: BuildMachine2(`wbs.ewoosoft.com`) · 총 RAM **62.4GB** · 접속 `ssh -i ~/.ssh/id_rsa raymond@wbs.ewoosoft.com`
- **상태**: ✅ **적용 완료**(아래 §5 결과)

---

## 1. 배경 — 왜 필요한가

- OOM 사고(CI self-hosted 전환 직후)의 근본원인은 **테스트 러너 워커 자동 증식 × 에이전트 4대**였고, 대책으로 **Azure 에이전트 컨테이너에 6GB 캡**을 걸었다.
- 그러나 같은 호스트에 **Jenkins 마스터 + Jenkins Linux 노드 4대 + SonarQube + Dependency-Track + win10 VM**이 함께 돌고, 이들은 **캡이 없었다**.
- 숨은 천장 2개(단일 컨테이너가 호스트를 죽일 수 있는 크기):
  - **Dependency-Track apiserver**: JVM `-XX:MaxRAMPercentage=90.0` + 컨테이너 무제한 → 힙 천장 = **호스트 62GB의 90% ≈ 56GB**.
  - **Jenkins 마스터**: JVM 기본 `MaxHeapSize ≈ 16.7GB`(호스트 25% ergonomic) + 컨테이너 무제한.
- 결론: 보호가 **비대칭**이었다. 캡은 "예약"이 아니라 "천장"이며, 목적은 **어떤 단일 컨테이너도 폭주로 호스트를 죽이지 못하게** 하는 것이다(최악의 경우 컨테이너 하나만 OOM-kill = 빌드 1건 실패, 서버 전체 다운 아님).

## 2. 메모리 배분안 (호스트 62.4GB)

| 소비자 | 기동 방식 | 캡 전 | **캡** | 적용법 |
| --- | --- | ---: | ---: | --- |
| OS·커널·페이지캐시 예비 | — | — | **~4GB**(미할당) | — |
| win10 VM(Windows 에이전트 6개 수용) | libvirt/KVM | 8.1 | **8GB**(고정·유지) | 변경 안 함 |
| Azure 에이전트 ×4(`azp-agent-linux1..4`) | `docker run`(reinstall_agent.sh) | ~1.6 | **6GB×4 = 24GB**(유지) | 이미 적용됨 |
| **Dependency-Track apiserver** | compose `~/Documents/dtrack/docker-compose-dependency-track.yml` | 7.7 | **8GB** | `mem_limit: 8g` |
| **SonarQube** | compose `~/Docker/docker-compose.sonarqube-dtrack.yml` | 2.3 | **4GB** | `mem_limit: 4g` |
| **Jenkins 마스터**(`jenkins-server`) | `docker run` | 1.5 | **3GB**(+ `-Xmx2g`) | 재생성 |
| **Jenkins Linux 노드 ×4**(`LinuxNode1..4`) | `docker run` | ~1.6 | **3GB×4 = 12GB** | `docker update` |
| abc-wbs·nginx·DT frontend 등 소형 | compose/run | ~1 | 미할당(소형) | — |

**하드 캡 합계 = 8 + 24 + 8 + 4 + 3 + 12 + 1 ≈ 60GB** (+ OS 예비 ~2.4GB + 회수가능 페이지캐시).

### 핵심 효과
- **치명적 천장 제거**: DT 56GB→8GB · Jenkins 16.7GB→3GB.
- **Jenkins Linux 노드 상한**: 무제한 → 12GB(합).
- 어떤 컨테이너도 폭주로 호스트를 죽일 수 없다.

## 3. 한계·설계 노트 (정직한 기록)

1. **캡은 천장이지 예약이 아니다.** 합 60GB지만 실제 동시 사용은 훨씬 낮다(유휴 시 ~33GB). 이론상 전원 풀피크는 여전히 빡빡하다.
   - **완전 무-오버커밋 보장**을 원하면 Jenkins Linux 노드를 **4→2대로 감축**(−6GB → 캡 합 54GB)해 OS 여유까지 확보한다(throughput과의 trade-off).
2. **JVM은 컨테이너 캡만으론 부족**하다. 캡을 걸고 **재시작해야** cgroup-aware JDK가 힙 천장을 캡 기준으로 재계산한다.
   - **DT**: `MaxRAMPercentage=90`이 캡 8g의 90%=7.2GB로 자동 수렴 → 재생성만으로 깔끔.
   - **Jenkins**: 확실히 하려면 `-Xmx2g` 명시(재생성 시 `JAVA_OPTS`에 주입).
3. **swap 여유가 얇다**(1.4GB). 캡을 건 JVM은 `--memory-swap = --memory`로 swap 사용을 막아 얇은 swap을 잠식하지 못하게 한다.

## 4. 적용 절차

무중단 → 짧은 다운 → 잡 중단 순.

```bash
# (1) Jenkins Linux 노드 ×4 — 무중단(docker update, HostConfig 갱신·재시작 후에도 유지)
for n in 1 2 3 4; do docker update --memory 3g --memory-swap 3g LinuxNode$n; done

# (2) Dependency-Track — compose에 mem_limit 추가 후 재생성
#   ~/Documents/dtrack/docker-compose-dependency-track.yml 의 apiserver 서비스에:  mem_limit: 8g
docker compose -f ~/Documents/dtrack/docker-compose-dependency-track.yml up -d

# (3) SonarQube — compose에 mem_limit 추가 후 재생성
#   ~/Docker/docker-compose.sonarqube-dtrack.yml 의 sonarqube 서비스에:  mem_limit: 4g
docker compose -f ~/Docker/docker-compose.sonarqube-dtrack.yml up -d

# (4) Jenkins 마스터 — 캡 + -Xmx2g (docker run이라 재생성). 실행 중 잡 없는 창에서.
#   기존 config를 docker inspect로 캡처해 --memory 3g --memory-swap 3g + -e JAVA_OPTS=-Xmx2g 로 재생성
```

## 6. 운영·검증·롤백

| 무엇 | 방법 |
| --- | --- |
| **캡 확인** | `docker inspect --format '{{.HostConfig.Memory}}' <컨테이너>`(0=무제한) |
| **메모리 관측** | `free -h` · `docker stats --no-stream` · 스와핑 여부 `vmstat 1 3`(si/so=0이면 정상) |
| **JVM 실제 힙 천장** | `docker exec <c> java -XX:+PrintFlagsFinal -version | grep MaxHeapSize` |
| **롤백** | compose는 `mem_limit` 줄 제거 후 `up -d` · docker run은 `docker update --memory 0`(무제한 복귀)·Jenkins는 이전 run으로 재생성 |
| **감축안(무-오버커밋)** | Jenkins Linux 노드 4→2대(불용 2대 `docker stop`·Jenkins 노드 목록서 offline) |

**주의**: DT·SonarQube·Jenkins는 **팀 공용 서비스**다. 캡값 변경·재시작은 다운타임을 수반하므로 한가한 창에서, 그리고 본 문서를 갱신해 이력을 남긴다.
