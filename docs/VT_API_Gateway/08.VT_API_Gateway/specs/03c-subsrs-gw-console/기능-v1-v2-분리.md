# GW Console (③-C) 기능 — v1.0 / v2.0 분리 (SRS 집필 전 정리)

> 목적: ③-C Sub-SRS 집필 **전에** Console 기능을 v1.0/v2.0으로 나눈 작업 정리. **SRS 본문은 v1.0·v2.0을 모두 포함**하되, 각 기능에 이 분류로 단계 표기한다.
> 정본 근거 = GW SRS **§7.9.1**(테넌트·키·디바이스 관리 API)·**§7.1.4**(운영자 OIDC)·**§7.9.2**(운영자 RBAC)·**§7.9.3**(감사)·**§7.6.3**(payload)·**§7.8**(fleet·config)·**§7.7.5**(호환성 매트릭스)·`_status.md` 씨앗.
> 상태: 초안(1차 분류·조정 예정). 작성일 2026-08-04.

## 분류 기준 (2026-08-04 확정)
- **v1.0** = ① **필수**(없으면 GW 서비스 자체가 안 됨) + ② 필수는 아니나 **주요** 기능.
- **v2.0** = **부가**·없어도 서비스 가능·**확장**·**고급** 기능.
- 분류는 우리가 정한다(제품 스코프·일정에 걸린 소수 경계 항목만 회의 공유·확인 — 맨 아래).

> **설계 원칙 — GW·Console은 target-agnostic(대상 무관).** 새 target(AXS·CleverSpace 등) 추가 = **데이터**(`target` 행 + 정책 + org_mapping)이지 코드/재배포가 아니다(target-routed proxy·§7.5·§7.6·§7.9.1·ADR-11). **Console의 target 관리 화면도 공통 1벌** — AXS 전용 화면을 따로 만들지 않고 같은 폼에 값만 다르게 넣는다. **CleverSpace를 target으로 추가해도 Console 추가 구현 불필요**(내부 backend라 라우팅 필드만 채움). **AXS 고유의 가입/구독**(Org-ID 취득·`customerNumber`·link/check/unlink·동의)만 AXS 특화이며 = ④(AXS Sub-SRS) 소관 + v2.0 편의 화면일 뿐, **v1.0 core Console엔 없다**(운영자가 out-of-band Org-ID를 generic org-mapping에 입력). 예외: GW가 미지원인 근본적 신규 역량(없던 인증/서명 스킴)이 필요할 때만 GW backend 확장(= target 추가가 아니라 역량 확장).

## 경계·논점 (회의에서 확인할 소수)

1. **target 관리 화면의 v1.0 "실운영" 시점** (AXS 전용이냐가 아님 — 위 원칙대로 화면은 target-무관·공통·v1.0). 논점은 **v1.0에 어떤 target을 실제로 등록·운영하느냐**: 내부 target(CleverSpace 라우팅)은 v1.0에 필요할 수 있고, 외부(AXS)는 **④ 연동(P7/P9=AXS baseline 후 대기)** 시점에 달림. 화면 자체는 v1.0이되 초기 실사용 대상이 무엇인지 → **제품/일정 의존 = 공유·확인**.
2. **payload break-glass 열람 UI** — PHI 접근이라 v1.0에 두되 **masking·전량 감사 강제**(규제). 열람 권한은 특정 역할로 제한(§7.9.2)할지 = 정책 결정(우리+보안).

## 이걸 주간회의에서 논의/공유 해야 하나?
- **분류 자체는 우리 결정** — 회의 의결 대상 아님.
- **공유(S#)는 하는 게 좋음**: v1.0 Console 스코프 투명성(9/1 착수·당김·Raymond) + 아래 경계 확인.
- **논의가 필요한 건 경계 1건**(위 §1 — AXS 연동 관리 화면의 v1.0 포함)뿐 — 제품/일정에 걸려서. 나머지는 공유로 충분.
