  - 🟢 **[IoT 다운링크] 거기까지 가는 데 고친 것들**
    - ✅ 실 IoT 배선 + 시드 진입점 머지([#15215](https://dev.azure.com/ewoosoft/es-platforms/_git/vt-api-gateway/pullrequest/15215)) · 시드 파이프라인은 ③-I가 클러스터 안 Job 방식으로 전환([#15212](https://dev.azure.com/ewoosoft/es-platforms/_git/vt-api-gateway/pullrequest/15212)) · **둘 다 CI 녹색**
      - 34파일 · +1066/−390 · **신규 테스트 17건**(단위 15 + **실 DB 통합 2**) · 단위 2165·e2e 674 통과
    - ✅ **dev 새 이미지도 올라갔다** — 그 머지 커밋으로 배포 파이프라인 4종이 돌았다(10/12)
    - 🛑 **그런데 E2E 를 막는 것이 하나 더 있었다 — 같은 병이 SQS 에도 있었다**(10/13 발견)
      - receiver 와 dispatcher 가 **각자 자기 메모리 큐**를 보고 있었다. 별 프로세스라서다
      - ⭐ **webhook 이벤트가 오류 없이 사라지고 있었다** — dev 는 지금도 그 상태다
      - E2E 의 **`webhook 발사 → dispatcher 발행` 단계가 여기서 막힌다.** 순서를 다시 잡았다
    - ✅ **둘 다 머지했다** — 더미 자격 6곳 제거([#15232](https://dev.azure.com/ewoosoft/es-platforms/_git/vt-api-gateway/pullrequest/15232)) · 배포에서 가짜 어댑터로 안 떨어지게([#15235](https://dev.azure.com/ewoosoft/es-platforms/_git/vt-api-gateway/pullrequest/15235))
    - ✅ **dev 로그로 고쳐진 것을 실측 확인했다**(10/13 11:52 Pod) — ③-I 가 준 Grafana 로 직접 봤다
      - `KmsPort → LocalKms` · `QueuePort → LocalSqsQueue` · **`creds=default-chain`**(더미 자격 아님·Pod Identity)
      - ⭐ **직전 Pod 은 같은 줄이 `InMemoryKms` 에 경고 레벨이었다.** 로그 레벨만 보고도 갈린다 — 설계대로 동작한다
      - 그래서 **`KMS_ENDPOINT`·`SQS_ENDPOINT` 는 주입할 필요가 없다** — 미설정이 곧 실 서비스다
    - 🟡 **시드 Job 을 처음 돌렸고 우리 코드 가드에 막혔다**(10/13) — ③-I 배선은 전부 정상이었다
      - 이미지·서명검증·자격·`ALLOW_PROD_SEED` 주입·승인 게이트·로그 수집까지 **설계대로** 돌았다
      - 막은 것은 시더의 *"배포 환경에서는 실행 불가"* 가드 하나다. **고치는 중**(Scott 승인 완료)
      - ⭐ 덕분에 미지수가 풀렸다 — **실행 모드 값이 Job 까지 전달된다**(시크릿 경유). 문서 모순도 같이 해소
    - ✅ **enroll 1건이 dev 에서 끝까지 통과했다 — 한 달 막혀 있던 경로가 실 AWS 까지 뚫렸다**(10/13)
      - **실 IoT 인증서가 발급됐다** — 인증서 식별자·디바이스·클라이언트 ID 수령, 상태 `pending`
      - ⭐ **이것이 IoT 권한의 실증이다** — 인증서 발급·사물 생성·정책 부착이 **실제로** 성공했다. 아침까지 「호출 0 건」이던 그 경로다
      - 정적 자격 없이 **Pod Identity 로 통과**했다
      - ③-I 가 권한·키 별칭·큐 이름을 반영하고 네 앱을 재기동했다(10/13 오후)
    - ✅ **로그를 우리가 직접 본다** — ③-I 가 모니터링 읽기 전용 토큰을 줬다. 배선·오류 조회에 더는 사람을 거치지 않는다
    - 🛑 **그 enroll 이 스펙 충돌 하나를 드러냈다 — 같은 클리닉에 두 번째 EzServer 를 넣으면 첫 번째가 끊긴다**
      - 두 번 돌렸더니 **두 번째가 첫 번째 device 를 회전**시켰다(= 자격 교체·옛 인증서 폐기). 디바이스 식별자가 같게 나왔다
      - ⚠ **구현 탓이 아니라 문서가 그렇게 적혀 있었다** — §7.2.7 이 *"클리닉당 활성 공개키 1 개(1:1)"* 라고 쓰는데 §1.1·§1.4·§6.3 은 **1:N 모델**이다. 한 문서가 두 말을 했다
      - ⭐ **더 중요한 것은 순서였다** — 회전이 **C/S 승인 전에** 일어난다. 새 디바이스는 아직 승인 대기라 못 쓰고 옛 것은 이미 죽어, 그 사이 클리닉이 멈춘다
      - ✅ **§7.2.7 을 고쳤다** — 1:N 명확화 + **회전은 승인 시점에만**. 교체인지 증설인지는 **승인자가 고른다**(GW 가 추측하지 않는다)
      - ⓘ **Console 새 화면은 필요 없다** — 승인 후 옛 디바이스를 기존 kill API 로 정리하면 된다. 한 화면에서 고르게 하는 것은 편의 개선
      - ⓘ 자주 밟는 경로는 아니다(EzServer 고장·재설치 때 가끔). 승인자 판단 재료(시리얼)는 **B-28** 로 뒀다 — 시리얼 형식 확정이 선행
    - ✅ **enroll 계약 문서 결함도 하나 고쳤다** — 공개키·서명 예시가 **EC 인데 구현은 RSA 만 받는다.** 예시대로 만들면 401 이다. **외부 연동사가 문서만 보고 구현할 자리**였다
    - 🛑 **그리고 한 절만 고친 것이 다음 결함을 만들었다** — 같은 계약을 말하는 **일곱 자리**가 옛 서술로 남아 **계약서가 거짓**이 됐다(1.0.99 로 정정)
      - ⚠ **자동 검사가 못 잡는다** — 생성물이 커밋됐는지만 보고 **통제문서와 대조하지 않는다.** 사람이 안 보면 영원히 남는다
      - ⭐ **오늘 그 문서를 기준으로 삼은 사람이 나였다** — 코드와 인프라를 추론하며 네 번 틀렸고, 해당 절을 읽은 뒤 한 번에 풀렸다
    - ✅ **시드도 통과했다**(10/13) — 가드를 고치고 다시 돌려 실 RDS 에 데이터가 들어갔다
      - ⭐ **그 실행이 실 KMS 호출의 첫 지점이었다** — 시더가 payload·자격을 실제로 암호화했으니 **키 권한과 키 별칭 선재가 한 번에 증명**됐다
    - ✅ **수신 호스트를 ③-I 가 열었다**(10/14) — **경로·메서드 무관**으로 받는다. 요청 때 그 조건을 못박은 것이 통했다
      - ⓘ 앞서 열려 있던 호스트는 **한 경로만** 지나가 발신 측이 "경로가 틀렸나 메서드가 틀렸나" 를 구분할 수 없었다. 실 연동 전 ③-I 가 확인한다
    - ✅ **디바이스 승인도 풀렸다** — Console 로그인이 되고 등록 대기열에서 승인하니 **인증서가 활성**됐다
      - ⓘ 승인 화면은 상세가 아니라 **별도 대기열**에 있다. 되돌릴 수 없는 전이라 일부러 갈라 둔 설계다
    - ✅ **접속 정보를 받을 계약이 없던 것도 고쳤다** — 브로커 주소는 **계정마다 달라 클라이언트가 만들 수 없는 유일한 값**인데, 그것을 내려 줄 필드가 스펙에 유예로 남아 있었다
      - 스펙(유예 해소) → 계약 → 구현계획 → 구현 → 환경값 주입 → **실응답 확인**까지 한 바퀴를 닫았다
      - ⭐ **오늘 내가 그 값을 문서에서 손으로 찾아 썼다** — EzServer 는 그럴 수 없다. 그게 계약이 필요한 이유였다
      - ⚠ **권한이 새로 필요해졌다** — 지금까지 가짜를 쓰고 있어 **실제로 있는지 아무도 확인할 일이 없었다.** SQS 4개·KMS 3개
      - ⭐ **새 위험이 아니라 이미 있던 고장이 드러나는 것이다** — 조용한 상태가 **명확히 실패하는 상태**로 바뀔 뿐이다
      - ⚠ **아직 증명되지 않았다** — 어댑터 배선은 **클라이언트를 만든 것**이지 AWS 를 불러 본 것이 아니다. 실제 트래픽이 흘러야 안다
    - 🛑 **이번에 막은 것이 전부 「조용히」 형태였다 — 넷이 같은 병이다**
      - **엔드포인트 값이 비면 가짜 어댑터로 떨어진다**(IoT·KMS·**SQS**) — 한 달을 잡아먹은 그 원인
      - **더미 자격을 넣으면 Pod Identity를 가로막는다** — 반대 방향이다. 넣지 말아야 할 것을 넣어서
      - **시더가 실패해도 종료 코드가 0이면 Job이 성공으로 잡힌다** — 데이터가 안 들어갔는데 들어간 줄 안다
      - 넷 다 **부팅에서 막고 기동 로그에 남기도록** 고쳤다. 실 어댑터면 로그, 가짜면 **경고**로 올라온다
    - ⭐ **목(mock)으로는 못 잡는 결함을 하나 잡았다** — 시더가 **첫 삽입에서 즉사**하는 상태였는데 단위 테스트는 전부 초록이었다. **실 DB 왕복만이 증명하는 부류**라 통합 테스트를 신설했다
    - ⓘ `import` 한 줄이 **이미지에 들어가는 파일 목록을 바꾼다** — 루트 파일을 참조하면 빌드 산출 경로가 생기는데 Dockerfile이 그 경로를 복사하지 않아 Job이 죽는다. 구현 위치를 옮겨 피했다

    - ⚠ **교차 스위트 e2e 플레이크** — 전체 실행마다 **다른 스위트**가 DB 접속·404로 실패하고 격리하면 전부 통과한다. 이번 작업 **이전부터** 있었고 원인 미규명이다. **CI 신뢰도 문제**라 적어 둔다
    - ⭐ **"고친 것" 과 "안 고치기로 한 것" 을 가른 것이 요점이다** — 판정도 조치이고, 근거를 남겨 **다음 사람이 같은 것을 다시 파지 않게** 한다
      - **`void` 55건** — 일부러 안 기다린다는 표시다. 떼면 _"실수로 `await` 을 놓친 것"_ 과 **구분이 안 된다**. ⚠ 규칙이 틀렸다고 적지 않았다 — 그 위험은 **`no-floating-promises` 로 떠다니는 프라미스 자체를 막는 쪽**이 맞고 도입은 별도 판단으로 뒀다
      - **`role="status"` 16건** — 규칙이 제안하는 `<output>` 은 **인라인 요소**라 바꾸면 시각 baseline 이 대거 흔들린다. 접근성 결과는 같고(암묵 role 이 `status`) axe 테스트도 통과 중이다
      - **CSS 2건은 `False Positive`** — `@theme`·`@custom-variant` 는 **Tailwind v4 의 정식 문법**이다. ⚠ DT 의 `js-yaml` 을 `Not Affected` 로 둔 것과 **정반대 경우**다 — 거기선 스캐너가 옳았고 여기선 틀렸다. **섞어 적으면 기록이 사실과 달라진다**
      - **핫스팟 ReDoS 7건은 `SAFE`** — 입력 길이를 공격자가 정하지 못한다(빌드 타임 env·우리가 배포하는 리전 디렉터리·계약에서 생성한 경로 템플릿). ⭐ 결정적 근거는 **정적 export 라 서버가 없다**는 것 — 자원 고갈이 성립하지 않는다
      - ⭐ **1건은 오탐이었다** — `6.3.1.3` 을 IP 로 읽었는데 **앱 버전 문자열**이었다
    - ⚠ **위 「0파일 분석인데 게이트 통과」 와 같은 집안 문제였다** — Console 커버리지가 0 이던 것도 **잡이 테스트를 안 돌려서**였지 코드 문제가 아니었다. 스캐너는 _"측정 안 함"_ 을 **_"한 줄도 커버 안 됨"_** 으로 기록한다
    - ⚠ **코드를 안 바꿨는데 수치가 움직인다** — 9/22 스캔에서 유지보수성이 78 → 124 로 늘었다(제외 범위가 걷히며 8월 이슈가 돌아옴). **등급은 개수가 아니라 가장 나쁜 항목으로 정해지므로**, 건수 추이만 보면 오독한다
