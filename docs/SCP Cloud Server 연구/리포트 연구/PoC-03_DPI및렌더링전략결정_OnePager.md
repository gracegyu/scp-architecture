- **유지보수성 향상**: 명확한 전략 수립으로 향후 변경 시 영향 범위 최소화
- **표준 준수**: 웹 표준 및 의료 인쇄 표준을 준수하는 전략 수립

**Technical Description**:

2. **폰트 단위**: **pt (Point)** ⚠️ **PoC-02에서 권장, PoC-03에서 최종 결정 필요**
   - PoC-02 Q&A 섹션에서 pt 사용 권장 (Q8, Q13, Q14)
   - 72 DPI 기준 정의 (1 pt = 1/72 inch ≈ 0.3528 mm)
   - 브라우저 자동 변환 지원
   - mm 좌표계와 통합 가능성 확인
   - **주의**: PoC-02에서는 "권장" 수준이며, PoC-03에서 최종 결정 및 검증 필요

**현재 상황 분석**:

PoC-02에서 mm 좌표계와 pt 폰트 단위를 결정했으나, 다음 항목들이 아직 결정되지 않아 복잡성이 존재:

1. **DPI 처리**:
   - 화면 렌더링: 96 DPI (웹 표준) vs 동적 DPI 감지
   - 프린트 렌더링: 300 DPI 가정 vs CSS pt 자동 vs 사용자 설정
   - 브라우저에서 프린터 DPI를 직접 알 수 없음

2. **폰트 단위**: ⚠️ **PoC-02에서 권장, PoC-03에서 최종 결정 필요**
   - PoC-02 Q&A에서 pt 사용 권장 (Q8, Q13, Q14)
   - 본 PoC에서 pt vs px를 재검토하여 최종 결정

3. **렌더링 방식**:
   - CSS 미디어 쿼리: `@media screen` vs `@media print`
   - 수동 변환: JavaScript로 DPI에 맞춰 픽셀 변환
   - PDF 생성: mm 단위 직접 지원, 가장 정확

4. **통합 전략**:
   - mm 좌표계와 폰트 크기의 완벽한 일치 보장
   - 화면과 프린트에서 동일한 물리적 크기 유지

**결정할 항목 (Decision Items)**:

**Item 1: 화면 렌더링 DPI 전략**

- **옵션 A**: 96 DPI 고정 (웹 표준)
  - 장점: 간단하고 예측 가능, 모든 브라우저에서 일관성
  - 단점: 고해상도 디스플레이에서 작게 보일 수 있음
- **옵션 B**: 동적 DPI 감지 (`window.devicePixelRatio` 활용)
  - 장점: 고해상도 디스플레이에 최적화
  - 단점: 복잡도 증가, 브라우저별 차이 가능성

**Item 2: 프린트 렌더링 DPI 전략**

- **옵션 A**: CSS pt 단위 사용 (브라우저 자동 변환)
  - 장점: 브라우저가 자동으로 프린터 DPI에 맞춰 변환, 간단함
  - 단점: 정확한 픽셀 제어 어려움, 브라우저별 차이 가능성
- **옵션 B**: `@media print` + 300 DPI 가정 (수동 변환)
  - 장점: 정확한 픽셀 제어 가능, 의료 표준 DPI 사용
  - 단점: 실제 프린터 DPI와 다를 수 있음
- **옵션 C**: 사용자 설정 옵션 제공
  - 장점: 사용자가 자신의 프린터에 맞춰 설정 가능
  - 단점: 사용자가 프린터 DPI를 알아야 함, 복잡도 증가

**Item 3: 폰트 단위 선택** ⚠️ **PoC-02에서 권장, 본 PoC에서 최종 결정**

**배경**: PoC-02 Q&A 섹션에서 pt 단위 사용을 권장했으나, 최종 결정은 본 PoC에서 검증 후 내려야 함.

- **옵션 A**: **pt (Point) 단위 사용** (PoC-02 권장)
  - 장점:
    - 브라우저가 자동으로 DPI에 맞춰 변환 (화면 96 DPI, 프린트 프린터 DPI)
    - mm 좌표계와 물리적 크기 일치 가능 (1 pt = 25.4/72 mm)
    - 웹 표준 및 의료 인쇄 표준 준수
    - 개발 복잡도 최소화 (CSS `font-size: 12pt` 직접 사용)
    - 인쇄 시 정확한 물리적 크기 보장
    - 폰트 크기의 표준 단위로 널리 사용됨
  - 단점:
    - 화면에서는 96 DPI 기준으로 해석되어 실제 물리적 크기와 약간의 차이 가능
    - 정확한 픽셀 제어 어려움 (브라우저 자동 변환에 의존)
    - 브라우저별 변환 방식 차이 가능성

- **옵션 B**: **mm (Millimeter) 단위 사용**
  - 장점:
    - 좌표 단위와 동일한 mm 단위로 통일성 있음
    - 물리적 크기 보장
    - CSS에서 기술적으로 지원됨 (`font-size: 10mm`)
  - 단점:
    - **폰트 크기 단위로 일반적이지 않음** (표준 관행에서 벗어남)
    - 브라우저 호환성 및 동작 방식이 pt 대비 덜 검증됨
    - 화면 표시 시 96 DPI 기준으로 변환되어 실제 물리적 크기와 차이 가능
    - 웹 표준에서 폰트 크기는 pt, px, em, rem 등이 권장됨
    - 개발자 및 디자이너에게 혼란 가능 (폰트 크기를 mm로 지정하는 것은 비표준)

- **옵션 C**: **px (Pixel) 단위 사용**
  - 장점:
    - 정확한 픽셀 제어 가능
    - 화면 표시에 최적화
    - DPI 변환 로직 명확 (수동 제어)
  - 단점:
    - DPI별로 다른 값 계산 필요 (화면 96 DPI, 프린트 300 DPI 등)
    - 복잡도 증가 (미디어 쿼리별 다른 px 값 필요)
    - 인쇄 시 DPI에 따라 물리적 크기가 달라짐
    - mm 좌표계와 통합 시 추가 변환 로직 필요

- **옵션 D**: **하이브리드 (pt + px)**
  - 화면: px 사용 (정확한 픽셀 제어)
  - 프린트: pt 사용 (정확한 물리적 크기)
  - 장점: 각 환경에 최적화
  - 단점: 복잡도 증가, 두 가지 단위 관리 필요

**검증 필요 사항**:
- pt 단위가 mm 좌표계와 실제로 완벽하게 일치하는지 실측 검증
- mm 단위 사용 시 브라우저 호환성 및 동작 방식 검증
- 브라우저별 pt → px 변환 일관성 검증
- 화면과 프린트에서 물리적 크기 일치 검증
- px 단위 사용 시 복잡도와 정확도 비교

**Item 4: 미디어 쿼리 전략**

- **옵션 A**: `@media screen`과 `@media print` 분리
  - 장점: 화면과 프린트를 명확히 분리, 각각 최적화 가능
  - 단점: CSS 코드 중복 가능성
- **옵션 B**: 단일 스타일 + JavaScript 동적 변환
  - 장점: CSS 단순화, 동적 제어 가능
  - 단점: JavaScript 복잡도 증가

**Item 5: PDF 생성 전략**

**배경**: 고정밀도 인쇄를 위해 PDF 생성이 필요하나, 클라이언트 사이드와 서버 사이드 중 어느 방식을 사용할지 결정 필요.

- **옵션 A**: **클라이언트 사이드 PDF 생성** (브라우저에서 직접 생성)
  - **라이브러리**: jsPDF, React-PDF, PDFKit (브라우저 버전)
  - 장점:
    - 서버 부하 없음 (클라이언트에서 처리)
    - 오프라인 동작 가능
    - 실시간 PDF 생성 및 미리보기
    - 서버 인프라 비용 절감
  - 단점:
    - 브라우저 성능 제약 (대용량 리포트 처리 시 느림)
    - 번들 크기 증가 (PDF 라이브러리 포함)
    - 브라우저별 호환성 차이 가능
    - 고해상도 이미지 처리 시 메모리 제약

- **옵션 B**: **서버 사이드 PDF 생성** (서버에서 생성 후 다운로드)
  - **라이브러리**: Puppeteer, PDFKit (Node.js), Playwright
  - 장점:
    - 가장 정확한 PDF 품질 (서버 환경 제어)
    - 고해상도 이미지 처리 용이
    - 브라우저 제약 없음
    - 클라이언트 번들 크기 영향 없음
    - 서버 리소스 활용 (CPU, 메모리)
  - 단점:
    - 서버 부하 증가
    - 네트워크 의존성 (온라인 필수)
    - 서버 인프라 비용 증가
    - API 엔드포인트 개발 필요

- **옵션 C**: **하이브리드 방식** (클라이언트 기본 + 서버 고품질)
  - 기본: 클라이언트 사이드 PDF 생성 (일반 사용)
  - 고품질: 서버 사이드 PDF 생성 (의료 표준 품질 필요 시)
  - 장점: 사용자 선택권 제공, 각 환경에 최적화
  - 단점: 두 가지 방식 유지 필요, 복잡도 증가

- **옵션 D**: **PDF 생성 없음** (브라우저 프린트만 사용)
  - 장점: 개발 복잡도 최소화, 추가 라이브러리 불필요
  - 단점: 정확도 제한, 브라우저/프린터 설정 의존적

**검증 필요 사항**:
- 클라이언트 사이드 PDF 생성 품질 (jsPDF, React-PDF 등)
- 서버 사이드 PDF 생성 품질 (Puppeteer, PDFKit 등)
- mm 단위 정확도 비교 (클라이언트 vs 서버)
- 성능 비교 (생성 시간, 메모리 사용량)
- 의료 인쇄 표준(300 DPI) 충족 여부
