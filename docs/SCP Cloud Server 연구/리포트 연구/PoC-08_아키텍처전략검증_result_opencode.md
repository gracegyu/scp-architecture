# PoC-08 결과 보고서: 아키텍처 전략 검증 (내부 운영 기준)

## 요약

- **재평가 전제**: 본 프로젝트는 외부 공개/판매 목적이 아닌 내부 업무 시스템 고도화 목적이며, 배포 전략도 내부 운영 기준으로 재정의
- **검증 결론**: 현 시점 최적안은 **Private NPM Package 중심 아키텍처**이며, 공통 자산은 필요 최소 범위의 내부 공용 서비스로 보조
- **핵심 이유**: 단일 조직 내부 배포에서는 SaaS의 상업적 이점(과금, 대외 확장)보다 운영 단순성과 오프라인 안정성이 우선
- **권장 구조**: 편집/렌더링/Export는 SDK 패키지로 제공, 템플릿 버전/에셋 동기화/감사 로그는 사내 API로 분리
- **실행 방안**: Phase 1 내부 패키지 표준화 → Phase 2 내부 공용 API 최소 도입 → Phase 3 운영 자동화 및 보안 감사 강화

## 1. 개요

### 1.1 검증 목표

`SCP Cloud Report PoC 설계` 문서의 PoC-08 목표(NPM Package vs SaaS)를 내부 운영 시나리오에 맞게 재해석하여, 다음 3개 옵션 중 내부 표준 아키텍처를 선정합니다.

1. **Option A: Private NPM Package** (사내 패키지 레지스트리 배포)
2. **Option B: Internal Shared Service** (사내 중앙 웹 서비스)
3. **Option C: Internal Hybrid** (Package + 내부 공용 API)

### 1.2 내부 전용 제약사항

`SCP Cloud Report PoC 설계.md` 기준으로 본 PoC의 맥락은 다음과 같이 정리됩니다.

- 작성 주체가 `SCP Cloud 개발팀`이며, 목적은 기존 Desktop 리포트의 **내부 전환 전략 검증**
- 외부 상용 배포/판매보다는 기존 제품 기능 호환, Migration, 품질 보장이 핵심
- PoC-08은 배포 방식 선택 가이드 산출이 목표이며, 상업적 과금 모델은 필수 요구사항이 아님

### 1.3 선행 PoC 반영

| PoC | 결정 사항 | PoC-08 반영 방식 |
| --- | --- | --- |
| PoC-03 | 렌더링 단위 전략(pt, DPI) | 내부/오프라인 환경에서도 동일 렌더링 품질 기준 유지 |
| PoC-04 | HTML DOM + SVG | SDK 내 렌더러 공통화로 서비스별 구현 편차 최소화 |
| PoC-05 | 기술 스택 선정 | 외부 판매가 아닌 내부 유지보수성 중심으로 의존성 관리 |
| PoC-06 | 통합 Element 스키마 | Package/API 간 계약 포맷 단일화 |
| PoC-07 | Migration 설계 | 내부 레거시 데이터 전환 경로를 모든 옵션의 필수 조건으로 적용 |

## 3. 옵션별 분석

### 3.1 Option A: Private NPM Package

**구조**:

```text
사내 업무 시스템
  └─ SCP Report SDK (Private NPM)
       ├─ 렌더링/편집 엔진
       ├─ 기본 템플릿
       ├─ Export 모듈
       └─ 내부 API 연동 어댑터
```

**장점**:

- 배포 단위가 명확하고 팀별 통합이 단순함
- 네트워크 의존도 낮아 오프라인/폐쇄망 대응이 유리함
- 내부 서비스별 UI/업무 흐름 맞춤 적용이 쉬움

**한계**:

- 패키지 버전 분산 관리 실패 시 운영 복잡도 증가
- 템플릿/에셋/감사 기능을 각 서비스가 중복 구현할 위험

### 3.2 Option B: Internal Shared Service

**구조**:

```text
사내 업무 시스템
  └─ 내부 공용 리포트 서비스(Web/API)
       ├─ 중앙 편집/렌더링
       ├─ 템플릿/에셋 저장소
       └─ 감사/권한/로그 관리
```

**장점**:

- 중앙 정책과 보안 통제를 강하게 적용 가능
- 기능 업데이트를 일관되게 전파 가능
- 로그/감사 추적 표준화가 쉬움

**한계**:

- 서비스 장애 시 영향 범위가 넓음
- 네트워크 품질/사내망 정책에 따라 사용성 저하 가능
- 초기 운영 인프라 준비 부담이 큼

### 3.3 Option C: Internal Hybrid

**구조**:

```text
사내 업무 시스템
  ├─ SCP Report SDK (Private NPM)
  │   ├─ 편집/렌더링/기본 Export
  │   └─ 로컬 캐시/임시 저장
  └─ 내부 공용 API
      ├─ 템플릿 버전 관리
      ├─ 공통 에셋 저장소
      └─ 감사 로그 수집
```

**장점**:

- 오프라인 작업 연속성과 중앙 관리 기능을 동시에 확보
- 단계적 도입이 가능해 기존 시스템 전환 리스크가 낮음

**한계**:

- 경계(API 계약, 동기화 정책) 설계가 미흡하면 복잡도 증가
- 운영 주체 구분이 불명확하면 책임 충돌 발생 가능

## 4. 정량 평가 결과

### 4.1 점수표 (100점 만점)

| 평가 항목 | 가중치 | Option A (Private NPM) | Option B (Shared Service) | Option C (Hybrid) |
| --- | --- | ---: | ---: | ---: |
| 운영 단순성 | 30 | 88 | 62 | 78 |
| 개발 생산성 | 25 | 84 | 70 | 82 |
| 보안/컴플라이언스 | 25 | 76 | 90 | 86 |
| 사용자 연속성 | 20 | 90 | 66 | 88 |
| **가중 합계** | **100** | **84.0** | **72.4** | **83.0** |

### 4.2 해석

- **Option A**: 내부 전용 전제에서 가장 높은 총점. 특히 운영 단순성과 사용자 연속성이 강점
- **Option B**: 중앙 통제는 우수하지만 내부망 의존성과 단일 장애점 리스크가 큼
- **Option C**: 균형형 대안으로 유효하나, 현 단계에서는 설계/운영 복잡도가 Option A 대비 높음

## 5. 최종 선정안

### 5.1 선정 결과

PoC-08 내부 재평가 결과, **Option A (Private NPM Package 중심)** 를 기본 아키텍처로 선정합니다.

### 5.2 선정 근거

1. 내부 시스템 특성상 외부 고객 확장/과금 모델이 핵심 의사결정 요인이 아님
2. 기존 업무 흐름을 유지하면서 단계적으로 전환하기에 SDK 방식이 가장 안전함
3. PoC-06/07/14 산출물(스키마·Migration·렌더링 엔진)을 패키지로 표준화해 재사용 가능
4. 폐쇄망/오프라인 환경에서도 편집/조회 연속성을 확보하기 쉬움

### 5.3 보조 전략

선정안은 패키지 중심이지만, 다음 3개 기능은 내부 공용 API로 분리해 중복 구현을 방지합니다.

- 템플릿 버전 레지스트리
- 공통 에셋 저장소
- 감사 로그 수집/조회

## 6. 목표 아키텍처 (내부 운영형)

### 6.1 책임 분리

**SDK 책임**:

- 문서 편집/렌더링
- 기본 Export
- 로컬 캐시 및 오프라인 임시 저장
- PoC-06 스키마 기반 직렬화/역직렬화

**내부 공용 API 책임**:

- 템플릿 정책/버전 관리
- 에셋 업로드/배포
- 보안 감사 로그 중앙 수집

### 6.2 계약 원칙

1. 문서 계약은 PoC-06 스키마 단일화
2. SDK 버전은 SemVer + LTS 채널 운영
3. API는 하위 호환 우선, 파괴적 변경은 분기 버전으로 분리
4. 네트워크 단절 시 SDK 단독 동작(저장 큐) 보장

## 7. 실행 로드맵

### 7.1 Phase 1: 내부 표준화 (4주)

- Private NPM 패키지 배포 파이프라인 정비
- 공통 UI/편집/Export 모듈 표준화
- 기존 시스템 1개 라인에 우선 적용

### 7.2 Phase 2: 공용 API 최소 도입 (4주)

- 템플릿 레지스트리 API
- 에셋 저장소 API
- 감사 로그 수집 API

### 7.3 Phase 3: 운영 고도화 (4주)

- 버전 릴리스 자동화 및 롤백 시나리오 확립
- 접근 권한/감사 리포트 강화
- 2개 이상 내부 시스템으로 확장 적용
