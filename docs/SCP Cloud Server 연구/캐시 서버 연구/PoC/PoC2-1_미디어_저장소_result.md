# PoC #2-1 미디어 저장소 아키텍처 검증 결과 보고서

## 1. 개요

### 1.1 검증 목표

치과 클리닉용 **로컬 캐시 서버**의 **미디어 저장소**에 최적화된 아키텍처를 선정하기 위해 파일시스템과 MinIO의 성능을 **실제 Docker 환경에서 측정**하여 비교하고, 프로덕션 개발 시 사용할 미디어 저장소 기술 스택을 확정한다.

**서비스 특성:**

- **클라우드의 느린 속도를 개선**하기 위한 로컬 캐시 전용 서비스
- 클라우드 연동이 아닌 **순수 로컬 성능 최적화**가 목표
- 클리닉 현장에서의 빠른 응답 속도가 핵심 가치

### 1.2 검증 범위

**실측 완료:**

- 미디어 파일 저장소: 파일시스템 vs MinIO

**검증 항목:**

- 성능 벤치마크: I/O 처리량, 지연시간, 메모리 사용량, 디스크 효율

**검증 제외:**

- RocksDB: Python 바인딩 컴파일 실패 및 로컬 캐시 목적과 부적합

**성공 기준:**

- 치과 이미지 조회 지연: 95p < 50ms
- 디스크 사용 효율: 200GB에 환자 200명 이상 캐싱

## 3. 미디어 파일 저장소 검증

### 3.1 검증 대상

이번 PoC에서는 **파일시스템**과 **MinIO** 두 가지 옵션을 실제 측정하여 비교했습니다.

#### 옵션 A: 파일시스템 (해시 기반 디렉터리) - 실측 완료

**구조:**

```
/var/cache/scp/media/
  ├── thumb/
  │   └── {hash[0:2]}/
  │       └── {hash[2:4]}/
  │           └── {clinicId}_{studyId}_{hash}.jpg
  ├── preview/
  │   └── {hash[0:2]}/{hash[2:4]}/{hash}.jp2
  └── raw/
      └── {hash[0:2]}/{hash[2:4]}/{hash}.dcm
```

**특징:**

- 해시 기반 2단계 디렉터리 구조 (256 × 256 = 65,536 하위 디렉터리)
- 파일명에 clinic_id, study_id 포함하여 디버깅 용이
- OS 파일시스템 캐시 자동 활용

#### 옵션 B: RocksDB - 검증 제외

**구조:**

```
Key:   clinic:{clinicId}:study:{studyId}:type:{thumb|preview|raw}
Value: <binary data>
```

**특징:**

- LSM-Tree 기반 키-값 저장소
- Snappy/LZ4 압축 지원
- 블록 캐시로 메모리 제어

**검증 제외 사유:**

1. **Python 바인딩 컴파일 실패 (ARM64 환경)**

   ```
   error: command '/usr/bin/clang++' failed with exit code 1
   Building wheel for python-rocksdb (setup.py) ... error
   ```

   - macOS ARM64(Apple Silicon)에서 `python-rocksdb` 빌드 실패
   - RocksDB C++ 라이브러리와 Python 바인딩 간 호환성 문제
   - 크로스 플랫폼 빌드 복잡도 높음 (Linux x86, ARM64, Windows 각각 별도 설정 필요)

2. **로컬 캐시 목적과 부적합**

   - RocksDB는 작은 키-값 데이터에 최적화 (수 KB~수 MB)
   - 치과 이미지는 **대용량 파일**(썸네일 200KB, CT 20MB)
   - 대용량 바이너리 저장 시 LSM-Tree 압축/병합 오버헤드 발생
   - 파일시스템의 직접 I/O가 더 효율적

3. **운영 복잡도**
   - 압축 알고리즘 튜닝 필요 (Snappy, LZ4, Zstd)
   - 블록 캐시 크기 조정 필요
   - 백업/복구 시 Export/Import 프로세스 복잡
   - 파일시스템 대비 디버깅 어려움 (바이너리 데이터베이스)

**향후 재검토 시점:**

- 메타데이터 저장소로 사용 (PostgreSQL 대안)
- 작은 파일 다수 저장 시 (< 100KB)
- 임베디드 환경에서 단일 바이너리 배포 필요 시

#### 옵션 C: MinIO (S3-Compatible Object Storage) - 실측 완료

**구조:**

```
Bucket: scp-cache-{clinicId}
Object: thumb/{studyId}/{hash}.jpg
Metadata:
  x-amz-meta-clinic-id: {clinicId}
  x-amz-meta-ttl: {timestamp}
  x-amz-meta-access-time: {timestamp}
```

**특징:**

- S3 API 호환 (boto3, aws-sdk 사용 가능)
- 객체 메타데이터 및 라이프사이클 정책 내장
- 멀티 버킷으로 클리닉별 격리
- mc (MinIO Client)로 S3 동기화 가능

### 3.2 성능 벤치마크 결과

**실측 완료 (2025-11-18):** 아래 데이터는 Docker 환경에서 실제 측정한 결과입니다.

#### 시나리오 1: 썸네일 쓰기 (200KB × 1,000개)

| 저장소     | 쓰기 처리량 (MB/s) | 평균 지연 (ms) | 95p 지연 (ms) | 디스크 사용량 |
| ---------- | ------------------ | -------------- | ------------- | ------------- |
| 파일시스템 | 42 MB/s            | 4.79 ms        | 15.99 ms      | 2,195 MB      |
| MinIO      | 6 MB/s             | 32.41 ms       | 93.97 ms      | 측정 불가     |

**분석:**

- 파일시스템이 쓰기 성능에서 **7배 빠름** (OS 버퍼 캐시 효과)
- MinIO는 HTTP 오버헤드로 **677% 느림**
- 파일시스템은 직접 I/O로 썸네일 쓰기에 최적화

#### 시나리오 2: CT 이미지 쓰기 (20MB × 100개)

| 저장소     | 쓰기 처리량 (MB/s) | 평균 지연 (ms) | 95p 지연 (ms) | 디스크 사용량 |
| ---------- | ------------------ | -------------- | ------------- | ------------- |
| 파일시스템 | 95 MB/s            | 210.03 ms      | 804.89 ms     | 2,195 MB      |
| MinIO      | 142 MB/s           | 141.00 ms      | 381.26 ms     | 측정 불가     |

**분석:**

- 대용량 파일에서 MinIO가 **33% 빠름** (HTTP 멀티파트 업로드 최적화)
- 파일시스템은 큰 파일에서 버퍼 캐시 효과가 줄어듦
- MinIO는 큰 파일 스트리밍에 유리

#### 시나리오 3: 랜덤 읽기 (1,000회)

**썸네일 (200KB):**

| 저장소     | 처리량 (req/s) | 평균 지연 (ms) | 95p 지연 (ms) | 99p 지연 (ms) |
| ---------- | -------------- | -------------- | ------------- | ------------- |
| 파일시스템 | 106            | 9.47 ms        | 25.86 ms      | 50.46 ms      |
| MinIO      | 44             | 22.62 ms       | 75.03 ms      | 151.93 ms     |

**CT 이미지 (20MB):**

| 저장소     | 처리량 (req/s) | 평균 지연 (ms) | 95p 지연 (ms) | 99p 지연 (ms) |
| ---------- | -------------- | -------------- | ------------- | ------------- |
| 파일시스템 | 7.5            | 133.27 ms      | 588.50 ms     | 707.65 ms     |
| MinIO      | 5.9            | 168.59 ms      | 403.85 ms     | 1,124.90 ms   |

**분석:**

- 썸네일: 파일시스템이 MinIO보다 **2.4배 빠름** (OS 캐시 효과)
- CT 이미지: 파일시스템이 **21% 빠름**, 큰 파일에서도 우위 유지
- MinIO는 읽기에서 HTTP 오버헤드가 명확히 나타남

### 3.3 메모리 사용량

| 저장소     | 기본 메모리 | Block Cache | 총 메모리 |
| ---------- | ----------- | ----------- | --------- |
| 파일시스템 | ~5 MB       | OS 관리     | ~5 MB     |
| MinIO      | ~280 MB     | -           | ~280 MB   |

**분석:**

- 파일시스템은 OS가 자동으로 메모리 관리 (유연함)
- MinIO는 Go 런타임과 HTTP 서버로 280MB 사용
- 소형 환경에서는 파일시스템이 메모리 효율적

### 3.4 운영 복잡도

| 항목      | 파일시스템     | MinIO                   |
| --------- | -------------- | ----------------------- |
| 백업      | rsync 가능     | mc mirror (S3 동기화)   |
| 복구      | 단순 복사      | S3에서 자동 복구        |
| 디버깅    | 파일 직접 확인 | mc ls, Web Console      |
| 모니터링  | df, du         | Prometheus metrics 내장 |
| 압축 튜닝 | 불필요         | 불필요 (자동)           |
| 서비스    | 불필요         | 별도 프로세스 (systemd) |

**분석:**

- 파일시스템이 운영 및 디버깅에서 압도적으로 간단
- MinIO는 S3 호환 도구(mc, aws-cli) 사용 가능, 모니터링 내장
- MinIO는 별도 서비스 관리 필요하나, 클라우드 동기화/백업 자동화 가능

### 3.5 미디어 저장소 선정 결과

**선정: 파일시스템 (해시 기반 디렉터리)**

**선정 근거 (파일시스템 vs MinIO 실측 비교):**

1. **성능 우수**:

   - 썸네일 쓰기 **7배 빠름** (4.79ms vs 32.41ms)
   - 썸네일 읽기 **2.4배 빠름** (9.47ms vs 22.62ms)
   - 작은 파일에서 압도적 우위

2. **운영 단순성**: 백업/복구/디버깅이 직관적, 별도 도구 불필요

3. **메모리 효율**: OS 캐시 자동 관리로 메모리 부담 없음 (5MB vs 280MB)

4. **OS 호환성**: Windows/Linux 모두 동일 구조 적용 가능

5. **비용 효율**: 추가 라이선스나 학습 곡선 없음

**RocksDB 제외 사유:**

1. **컴파일 실패**

   - ARM64 환경에서 Python 바인딩 빌드 실패
   - 크로스 플랫폼 빌드 복잡도 높음
   - 프로덕션 배포 시 각 환경별 빌드 필요

2. **로컬 캐시 목적과 부적합**

   - 대용량 파일(200KB~20MB) 저장 시 비효율적
   - LSM-Tree 압축/병합 오버헤드
   - 파일시스템의 직접 I/O가 더 빠름

3. **운영 복잡도**

   - 압축 알고리즘 튜닝 필요
   - 백업/복구 프로세스 복잡
   - 디버깅 어려움 (바이너리 DB)

4. **향후 재검토 가능**
   - 메타데이터 저장소로 검토 시
   - 작은 파일 다수 처리 시

**MinIO 제외 결정:**

본 서비스는 **클라우드의 느린 속도를 개선하기 위한 로컬 캐시 전용**이므로, MinIO의 주요 장점인 S3 호환성과 클라우드 동기화 기능이 불필요합니다.

**제외 근거:**

1. **서비스 목적과 불일치**: 클라우드 연동이 아닌 로컬 성능 최적화가 목표
2. **성능 저하**: 썸네일에서 **7배 느림** (4.79ms vs 32.41ms)
3. **메모리 낭비**: 56배 많은 메모리 사용 (5MB vs 280MB)
4. **운영 복잡도**: 별도 서비스 관리 필요
5. **불필요한 HTTP 오버헤드**: 로컬 I/O에서는 단점만 부각

**향후 고려 사항:**

- 클라우드 하이브리드 서비스로 전환 시 MinIO 재검토 가능
- 현재는 순수 로컬 캐시 성능에 집중
