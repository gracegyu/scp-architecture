# PoC #3: 캐시 알고리즘 검증 결과 보고서

## 1. 개요

### 1.1 검증 목표

로컬 캐시 서버의 캐시 알고리즘을 검증하여 최적 알고리즘을 선정하고, 향후 프로덕션 개발 시 캐시 전략을 확정한다.

**검증 방식:**

- 다양한 캐시 알고리즘별 성능 비교 (히트율, 메모리 사용량, 처리 지연)
- 치과 진료 패턴 시뮬레이션을 통한 실제 효과 검증
- 알고리즘 복잡도 vs 성능 향상 트레이드오프 분석

### 1.2 검증 범위

**검증 완료:**

- 합성 접근 패턴 데이터 생성 (Zipf 분포, 의료 특화 패턴)
- 시뮬레이터 구현 (LRU, SLRU, Window-TinyLFU)
- 알고리즘별 성능 측정 (요청/바이트 히트율, 메모리 오버헤드, 지연 시간)

**검증 대상 알고리즘:**

- LRU (Least Recently Used): 기본 알고리즘
- SLRU (Segmented LRU): 핫/콜드 세그먼트 분리
- Window-TinyLFU: 빈도 기반 입소 필터

**검증 대상 시나리오:**

- 의료 특화 패턴 (Temporal/Spatial Locality)
- Zipf 분포 패턴
- One-hit-wonder 패턴

### 1.3 성공 기준

**기능 요구사항:**

- 요청 기준 히트율: 80% 이상
- 바이트 기준 히트율: 70% 이상
- 오리진 트래픽 감소: 60% 이상

**성능 요구사항:**

- 알고리즘별 명확한 성능 차이 측정 (5% 이상 차이 시 의미 있음)
- 알고리즘별 장단점 정량화
- 기술적 의사결정 근거 문서화

## 2. 구현 내용

### 2.1 합성 접근 패턴 데이터 생성기

**구현 파일:** `poc3-simulator/generate_trace.py`

**기능:**

1. **Zipf 분포 기반 트레이스 생성**

   - Zipf 파라미터 조정 가능 (기본값: 1.2)
   - 상위 20% 항목이 80% 접근 패턴 반영

2. **의료 특화 패턴 생성**

   - Temporal Locality: 최근 진료 환자 집중 조회 (80% 확률)
   - Spatial Locality: 동일 환자의 여러 스터디 연속 조회 (70% 확률)
   - Hot/Warm/Cold 분포: Hot 60%, Warm 30%, Cold 10%

3. **One-hit-wonder 패턴 생성**
   - 설정 가능한 비율의 항목이 1회만 접근됨
   - TinyLFU 필터 효과 검증용

**생성된 트레이스 예시:**

- 의료 패턴: 100,000 ~ 1,000,000건
- 환자 수: 50 ~ 100명
- 스터디 수: 250 ~ 500개
- 리소스 타입: thumb, preview, slice, meta

### 2.2 캐시 알고리즘 구현

**구현 파일:** `poc3-simulator/cache_algorithms.py`

**구현된 알고리즘:**

1. **LRUCache**

   - 기본 LRU 구현
   - OrderedDict 기반
   - 용량 기반 제거

2. **SLRUCache (Segmented LRU)**

   - Probation 세그먼트 (20%): 신규 진입, 빠른 제거
   - Protected 세그먼트 (80%): 재접근 항목, 오래 유지
   - Probation에서 재접근 시 Protected로 승격

3. **WindowTinyLFU**
   - Window Cache (1%): 최근 항목 임시 보관
   - Main Cache (99%): SLRU 기반
   - Count-Min Sketch: 빈도 추정 (width=1M, depth=5)
   - 입소 필터: 빈도 임계치 미만 거부 (기본값: 5회)

**Count-Min Sketch 구현:**

- 메모리 효율적 빈도 추정
- 충돌 가능성 있으나 보수적 추정으로 보정
- 메모리 오버헤드: 약 20MB (width=1M, depth=5, int=4bytes)

### 2.3 캐시 시뮬레이터

**구현 파일:** `poc3-simulator/cache_simulator.py`

**기능:**

- 플러그 가능한 알고리즘 구조
- 통계 수집 (히트율, 바이트 히트율, 입소율, 지연 시간)
- 메모리 오버헤드 측정
- 진행 상황 표시 (100,000건 단위)

**측정 지표:**

- 요청 히트율 = HIT / (HIT + MISS)
- 바이트 히트율 = HIT_BYTES / (HIT_BYTES + MISS_BYTES)
- 입소율 = ADMITTED / (ADMITTED + REJECTED)
- 평균 지연 시간 (ms)
- 메모리 오버헤드 비율

### 3.3 알고리즘별 비교 분석

**LRU 장점:**

- ✅ 구현 단순, 성능 우수
- ✅ 의료 패턴에서 매우 높은 히트율
- ✅ 메모리 오버헤드 최소

**LRU 단점:**

- ❌ One-hit-wonder 항목에 취약
- ❌ 빈도 정보 미활용

**SLRU 장점:**

- ✅ Probation 세그먼트로 신규 항목 필터링 효과
- ✅ Protected 세그먼트로 핫 데이터 보호
- ✅ LRU 대비 One-hit-wonder 대응 향상 (이론상)

**SLRU 단점:**

- ⚠️ 구현 복잡도 증가 (세그먼트 관리)
- ⚠️ 실행 시간 약간 증가 (10~20%)
- ⚠️ 의료 패턴에서는 LRU와 유사한 성능

**TinyLFU 장점:**

- ✅ 빈도 기반 입소 필터로 One-hit-wonder 효과적 차단
- ✅ Window Cache로 최근성 보장

**TinyLFU 단점:**

- ❌ 입소 필터 임계치 튜닝 필요
- ❌ Count-Min Sketch 메모리 오버헤드 (~20MB)
- ❌ 실행 시간 증가 (6~7배)
- ❌ 의료 패턴의 높은 지역성과 상성이 낮음

## 4. 결론 및 권장사항

### 4.1 알고리즘 선정

**1차 권장: LRU**

**선정 근거:**

1. **의료 패턴 적합성:**

   - Temporal/Spatial Locality가 높은 의료 환경에서 99% 이상의 높은 히트율
   - 복잡한 알고리즘이 필요하지 않음

2. **구현 단순성:**

   - 구현 및 디버깅 용이
   - 운영 부담 최소
   - 성능 오버헤드 최소

3. **충분한 성능:**
   - 목표 히트율(80%) 초과 달성
   - 모든 성능 목표 충족

**2차 고려: SLRU (선택적)**

**고려 사항:**

- One-hit-wonder 항목이 많은 경우 SLRU 고려
- 의료 패턴에서는 LRU와 유사한 성능으로 큰 이점 없음
- 구현 복잡도 증가에 비해 성능 향상 미미

**미권장: TinyLFU (현재 상태)**

**미권장 근거:**

1. **의료 패턴 부적합:**

   - 입소 필터가 의료 패턴의 높은 지역성과 상성 낮음
   - 첫 접근 후 즉시 재접근되는 항목도 필터에 걸림

2. **성능 오버헤드:**

   - 실행 시간 6~7배 증가
   - 메모리 오버헤드 (Count-Min Sketch)
   - 복잡도 증가

3. **튜닝 필요:**
   - 임계치 조정 및 Window Cache 비율 튜닝 필요
   - 의료 환경에 맞는 추가 검증 필요

### 4.2 최종 권장 아키텍처

**기본 알고리즘: LRU**

```
캐시 크기: 50~200GB (클리닉 규모별)
알고리즘: LRU
TTL: 리소스 타입별 (썸네일 30일, 프리뷰 7일, 슬라이스 1일, 메타 5분)
```

**선택적 개선 사항:**

1. **SLRU 도입 (One-hit-wonder가 많은 경우):**

   - Probation 세그먼트: 10~20%
   - Protected 세그먼트: 80~90%

2. **프리페칭 전략 (선택적):**

   - ✅ **환자 기반 프리페칭**: 히트율 +0.40% 향상, 오버헤드 100MB

     - 환자 진입 시 썸네일 및 대표 프리뷰 5개 프리페치
     - 실용적인 트레이드오프로 권장

   - ⏳ **의료 특화 프리페칭 (향후):**
     - 진료 일정 데이터 연동 시 효과 증가 예상
     - 응급 환자 우선 프리페칭
     - 진료진별 개인화 캐싱

3. **의료 특화 우선순위 캐싱 (향후):**

   - 진료 일정 기반 우선순위 캐싱
   - 응급도별 TTL 차등
   - 진료진별 개인화 캐싱

### 5.2 사용 방법

**트레이스 생성:**

```bash
python3 generate_trace.py --pattern medical --num-requests 1000000 --output trace.json
```

**벤치마크 실행:**

```bash
python3 run_benchmark.py --trace-file trace.json --capacities 50 100 200
```

**다양한 시나리오 벤치마크:**

```bash
python3 run_benchmark.py --scenarios
```

**프리페칭 전략 벤치마크:**

```bash
python3 prefetch_benchmark.py --trace-file trace.json --algorithm LRU --capacity 100
```
