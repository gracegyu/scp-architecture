# PoC #3: 캐시 알고리즘 검증 결과 보고서

## 1. 개요

### 1.1 검증 목표

로컬 캐시 서버의 캐시 알고리즘을 검증하여 최적 알고리즘을 선정하고, 향후 프로덕션 개발 시 캐시 전략을 확정한다.

**검증 방식:**

- 다양한 캐시 알고리즘별 성능 비교 (히트율, 메모리 사용량, 처리 지연)
- 치과 진료 패턴 시뮬레이션을 통한 실제 효과 검증
- 알고리즘 복잡도 vs 성능 향상 트레이드오프 분석

### 1.2 검증 범위

**검증 완료:**

- 합성 접근 패턴 데이터 생성 (Zipf 분포, 의료 특화 패턴)
- 시뮬레이터 구현 (LRU, SLRU, Window-TinyLFU)
- 알고리즘별 성능 측정 (요청/바이트 히트율, 메모리 오버헤드, 지연 시간)

**검증 대상 알고리즘:**

- LRU (Least Recently Used): 기본 알고리즘
- SLRU (Segmented LRU): 핫/콜드 세그먼트 분리
- Window-TinyLFU: 빈도 기반 입소 필터

**검증 대상 시나리오:**

- 의료 특화 패턴 (Temporal/Spatial Locality)
- Zipf 분포 패턴
- One-hit-wonder 패턴

### 1.3 성공 기준

**기능 요구사항:**

- 요청 기준 히트율: 80% 이상
- 바이트 기준 히트율: 70% 이상
- 오리진 트래픽 감소: 60% 이상

**지표별 차이 설명:**

1. **요청 기준 히트율 (Request Hit Rate):**

   - 전체 요청 중 캐시에서 처리된 요청의 비율을 **개수 기준**으로 측정
   - 예: 100개 요청 중 80개가 캐시 히트 → 80%
   - 작은 파일(썸네일, 메타데이터)과 큰 파일(슬라이스 이미지)을 동일하게 카운트
   - 캐시의 요청 처리 효율성 측정

2. **바이트 기준 히트율 (Byte Hit Rate):**

   - 전체 전송 데이터 중 캐시에서 처리된 데이터의 비율을 **용량 기준**으로 측정
   - 예: 100GB 요청 중 70GB가 캐시 히트 → 70%
   - 큰 파일의 캐시 히트가 더 높은 가중치를 가짐
   - 네트워크 대역폭 절감 효과 측정

3. **오리진 트래픽 감소 (Origin Traffic Reduction):**
   - 원본 서버(클라우드)로 전송되는 트래픽이 줄어든 비율
   - 예: 원래 100GB 전송해야 하는데 40GB만 전송 → 60% 감소
   - 클라우드 서비스의 데이터 전송 비용과 직접 연관
   - 캐시 서버 도입의 경제적 효과를 가장 직접적으로 반영

**관계:**

- 요청 기준 히트율 80% ≠ 바이트 기준 히트율 80%
  - 작은 파일(썸네일)이 많이 캐시되면 요청 기준 히트율은 높지만, 바이트 기준은 낮을 수 있음
  - 큰 파일(슬라이스)이 캐시되면 바이트 기준 히트율이 더 높게 나타남
- 오리진 트래픽 감소는 바이트 기준 히트율과 유사하지만, 실제 클라우드로 전송되는 데이터만 측정
  - 프리페칭 등으로 인한 추가 다운로드는 제외

**성능 요구사항:**

- 알고리즘별 명확한 성능 차이 측정 (5% 이상 차이 시 의미 있음)
- 알고리즘별 장단점 정량화
- 기술적 의사결정 근거 문서화

## 2. 구현 내용

### 2.1 합성 접근 패턴 데이터 생성기

**구현 파일:** `poc3-simulator/generate_trace.py`

**기능:**

1. **Zipf 분포 기반 트레이스 생성**

   - Zipf 파라미터 조정 가능 (기본값: 1.2)
   - 상위 20% 항목이 80% 접근 패턴 반영

2. **의료 특화 패턴 생성**

   - Temporal Locality: 최근 진료 환자 집중 조회 (80% 확률)
   - Spatial Locality: 동일 환자의 여러 스터디 연속 조회 (70% 확률)
   - Hot/Warm/Cold 분포: Hot 60%, Warm 30%, Cold 10%
     - **Hot (핫 데이터)**: 자주 접근되는 데이터로, 전체 접근의 60%를 차지하는 인기 항목 (최근 진료 환자, 현재 조회 중인 스터디 등)
     - **Warm (웜 데이터)**: 가끔 접근되는 데이터로, 전체 접근의 30%를 차지하는 중간 인기 항목 (과거 진료 환자, 참고용 스터디 등)
     - **Cold (콜드 데이터)**: 거의 접근되지 않는 데이터로, 전체 접근의 10%를 차지하는 저인기 항목 (오래된 스터디, 보관용 데이터 등)

3. **One-hit-wonder 패턴 생성**
   - 설정 가능한 비율의 항목이 1회만 접근됨
   - TinyLFU 필터 효과 검증용

**생성된 트레이스 예시:**

- 의료 패턴: 100,000 ~ 1,000,000건
- 환자 수: 50 ~ 100명
- 스터디 수: 250 ~ 500개
- 리소스 타입: thumb, preview, slice, meta

### 2.2 캐시 알고리즘 구현

**구현 파일:** `poc3-simulator/cache_algorithms.py`

**구현된 알고리즘:**

1. **LRUCache**

   - 기본 LRU 구현
   - OrderedDict 기반
   - 용량 기반 제거

2. **SLRUCache (Segmented LRU)**

   - Probation 세그먼트 (20%): 신규 진입 항목이 먼저 배치되며, 재접근되지 않으면 빠르게 제거되어 One-hit-wonder 항목을 필터링함
   - Protected 세그먼트 (80%): Probation에서 재접근된 항목이 승격되어 배치되며, LRU 방식으로 오래 유지되어 핫 데이터를 보호함
   - Probation에서 재접근 시 Protected로 승격: 한 번 더 접근된 항목만 Protected로 이동하여 자주 사용되는 데이터를 장기 보존

3. **WindowTinyLFU**
   - Window Cache (1%): 최근 접근된 항목을 일시적으로 보관하여 최신성을 보장하고, 빈도 수집을 위한 관찰 창 역할을 함
   - Main Cache (99%): SLRU 알고리즘 기반으로 빈도가 높은 항목을 장기 보존하며, Window Cache에서 승격된 항목이 배치됨
   - Count-Min Sketch: 메모리 효율적인 확률적 자료구조로 각 항목의 접근 빈도를 추정하며, 설정값 width=1M, depth=5로 충돌 가능성을 최소화함
   - 입소 필터: Count-Min Sketch로 추정한 빈도가 임계치(기본값: 5회) 미만인 항목은 Main Cache에 저장되는 것을 거부하여 One-hit-wonder 항목을 차단함

**Count-Min Sketch 구현:**

- 메모리 효율적 빈도 추정
- 충돌 가능성 있으나 보수적 추정으로 보정
- 메모리 오버헤드: 약 20MB (width=1M, depth=5, int=4bytes)

### 2.3 캐시 시뮬레이터

**구현 파일:** `poc3-simulator/cache_simulator.py`

**기능:**

- 플러그 가능한 알고리즘 구조
- 통계 수집 (히트율, 바이트 히트율, 입소율, 지연 시간)
- 메모리 오버헤드 측정
- 진행 상황 표시 (100,000건 단위)

**측정 지표:**

- 요청 히트율 = HIT / (HIT + MISS)
- 바이트 히트율 = HIT_BYTES / (HIT_BYTES + MISS_BYTES)
- 입소율 = ADMITTED / (ADMITTED + REJECTED)
  - 입소(admission): 캐시에 새로운 항목이 들어가서 저장되는 것
  - 입소 거부(rejection): 캐시에 들어가지 못하고 거부되는 것
- 평균 지연 시간 (ms)
- 메모리 오버헤드 비율

### 3.3 알고리즘별 비교 분석

**LRU 장점:**

- ✅ 구현 단순, 성능 우수
- ✅ 의료 패턴에서 적절한 히트율 (34.56~40.74%)
- ✅ 메모리 오버헤드 최소

**LRU 단점:**

- ❌ One-hit-wonder 항목에 취약
- ❌ 빈도 정보 미활용

**SLRU 장점:**

- ✅ Probation 세그먼트로 신규 항목 필터링 효과
- ✅ Protected 세그먼트로 핫 데이터 보호
- ✅ LRU 대비 One-hit-wonder 대응 향상 (이론상)

**SLRU 단점:**

- ⚠️ 구현 복잡도 증가 (세그먼트 관리)
- ⚠️ 실행 시간 약간 증가 (10~20%)
- ⚠️ 의료 패턴에서는 LRU와 유사한 성능

**TinyLFU 장점:**

- ✅ 빈도 기반 입소 필터로 One-hit-wonder 효과적 차단
- ✅ Window Cache로 최근성 보장

**TinyLFU 단점:**

- ❌ 입소 필터 임계치 튜닝 필요
- ❌ Count-Min Sketch 메모리 오버헤드 (~20MB)
- ❌ 실행 시간 증가 (6~7배)
- ❌ 의료 패턴의 높은 지역성과 상성이 낮음

### 3.4 메모리 오버헤드

| 알고리즘 | 기본 오버헤드 | Count-Min Sketch | 총 오버헤드 (100GB 기준) |
| -------- | ------------- | ---------------- | ------------------------ |
| LRU      | 최소          | 없음             | ~1%                      |
| SLRU     | 낮음          | 없음             | ~1.1%                    |
| TinyLFU  | 낮음          | ~20MB            | ~1.2%                    |

**분석:**

- 메모리 오버헤드는 모두 1~2% 수준으로 무시할 만함
- Count-Min Sketch는 고정 크기이므로 캐시 크기가 커질수록 비율은 감소

### 3.5 한계점 및 개선 사항

**현재 한계:**

1. **LRU/SLRU 차이 미미:**

   - **결과**: 65.75GB 데이터 기준으로 LRU와 SLRU의 성능 차이가 1%p 미만으로 매우 작음
   - **원인**: 의료 특화 패턴의 높은 지역성으로 인해 One-hit-wonder 항목이 상대적으로 적어 SLRU의 Probation 세그먼트 필터링 효과가 제한적
   - **한계**: 실제 환경에서 다양한 접근 패턴이 혼재할 경우 차이가 더 나타날 수 있으나, 현재 테스트에서는 검증 불가
   - **개선 필요**: One-hit-wonder 비율을 조정한 혼합 패턴 테스트 추가

2. **TinyLFU 임계치 미조정 (0% 히트율):**

   - **원인**: 입소 필터 임계치(5회)가 너무 높아 첫 접근 시 빈도 추정이 1회로 카운트되어 모든 항목이 캐시에 저장되는 것을 거부받음
   - **구현 상태**: 알고리즘은 정상 구현되었으나, 설정값이 의료 패턴에 부적합
   - **결과**: 모든 요청이 캐시 저장 거부되어 히트율 0%
   - **개선 필요**: 임계치 1~2회로 낮추거나, Window Cache 비율 증가, 또는 첫 접근 시 임시 캐시 저장 허용 로직 추가

3. **목표 히트율(80%) 미달:**

   - **현재 결과**: 65.75GB 데이터 기준으로 최대 40.74% 히트율 (20GB 캐시)
   - **원인**: 고유 데이터(65.75GB)가 캐시보다 3~13배 크므로 많은 데이터가 캐시에서 제거됨
   - **개선 필요**: 캐시 크기 확대 또는 추가 최적화 전략 필요

4. **의료 특화 알고리즘 미구현:**

   - 진료 일정 기반 우선순위 캐싱
   - 응급도별 캐시 우선순위
   - 진료진별 개인화 캐싱

## 4. 결론 및 권장사항

### 4.1 알고리즘 선정

**1차 권장: LRU**

**선정 근거 (올바른 테스트 설계 기준):**

1. **의료 패턴 적합성:**

   - Temporal/Spatial Locality가 높은 의료 환경에서 적절한 히트율 (36.92~40.74%)
   - 복잡한 알고리즘이 필요하지 않음

2. **구현 단순성:**

   - 구현 및 디버깅 용이
   - 운영 부담 최소
   - 성능 오버헤드 최소

3. **안정적인 성능:**

   - 65.75GB 데이터, 10GB 캐시 기준 36.92% 히트율
   - 캐시 크기에 따라 34.56% (5GB) → 40.74% (20GB)로 향상
   - SLRU와 비교 시 성능 차이가 미미하여 단순한 LRU로 충분

**📊 테스트 결과 요약:**

- **테스트 조건**: 65.75GB 데이터, 캐시 5GB/10GB/20GB (데이터보다 작은 크기)
- **히트율 결과**: 34.56% (5GB) ~ 40.74% (20GB)
- **목표 히트율(80%)**: 현재 결과 미달
- **실제 운영 환경**: 서버 데이터가 캐시보다 클 것으로 예상되며, 목표 80% 달성에는 캐시 크기 확대 또는 추가 최적화 필요

**2차 고려: SLRU (선택적)**

**고려 사항:**

- 작은 캐시(5GB, 10GB)에서는 SLRU가 LRU보다 약간 우수 (+0.89~+0.91%p)
- 큰 캐시(20GB)에서는 LRU가 SLRU보다 약간 우수 (+0.55%p)
- 성능 차이가 미미하여(1%p 미만) 구현 복잡도 증가에 비해 큰 이점 없음
- One-hit-wonder 항목이 많은 환경에서는 SLRU의 Probation 세그먼트 효과가 더 명확할 수 있음

**미권장: TinyLFU (현재 상태)**

**미권장 근거:**

1. **의료 패턴 부적합:**

   - 입소 필터가 의료 패턴의 높은 지역성과 상성 낮음
   - 첫 접근 후 즉시 재접근되는 항목도 필터에 걸림

2. **성능 오버헤드:**

   - 실행 시간 6~7배 증가
   - 메모리 오버헤드 (Count-Min Sketch)
   - 복잡도 증가

3. **튜닝 필요:**
   - 임계치 조정 및 Window Cache 비율 튜닝 필요
   - 의료 환경에 맞는 추가 검증 필요

### 4.2 최종 권장 아키텍처

**기본 알고리즘: LRU**

```
캐시 크기: 50~200GB (클리닉 규모별)
알고리즘: LRU
TTL: 리소스 타입별 (썸네일 30일, 프리뷰 7일, 슬라이스 1일, 메타 5분)
```

**선택적 개선 사항:**

1. **SLRU 도입 (One-hit-wonder가 많은 경우):**

   - Probation 세그먼트: 10~20%
   - Protected 세그먼트: 80~90%

2. **프리페칭 전략 (향후 검증):**

   - 환자 기반 프리페칭: 환자 진입 시 썸네일 및 대표 프리뷰 프리페치
   - 의료 특화 프리페칭: 진료 일정 데이터 연동 기반 프리페칭
   - 응급 환자 우선 프리페칭
   - 진료진별 개인화 캐싱

3. **의료 특화 우선순위 캐싱 (향후):**

   - 진료 일정 기반 우선순위 캐싱
   - 응급도별 TTL 차등
   - 진료진별 개인화 캐싱

### 4.3 캐시 서버 도입의 장점

로컬 캐시 서버 도입을 통해 다음과 같은 장점을 얻을 수 있다.

**1. 성능 향상:**

- 캐시 히트 시 클라우드 서버 접근 없이 로컬에서 즉시 응답
- 네트워크 지연 제거로 사용자 대기 시간 대폭 단축
- 의료 영상 조회 속도 개선으로 진료 효율성 향상

**2. 네트워크 부하 감소:**

- 반복 요청을 로컬 캐시에서 처리하여 클라우드 서버 트래픽 감소
- 목표 오리진 트래픽 감소 60% 이상으로 네트워크 인프라 부담 완화

**3. 클라우드 운영 비용 감소 (핵심 장점):**

- **데이터 전송 비용 절감:**

  - 오리진 트래픽 감소 60% = 클라우드 데이터 전송 비용 60% 절감
  - 의료 영상 파일은 용량이 크므로(슬라이스 이미지 등) 절감 효과가 매우 큼
  - 예: 월 10TB 전송 시 → 캐시 도입 후 4TB만 전송 → 60% 비용 절감

- **API 호출 비용 절감:**

  - 요청 기준 히트율 80% 이상으로 클라우드 API 호출 횟수 감소
  - 반복 조회가 많은 의료 환경에서 특히 효과적

- **서버 부하 감소:**

  - 클라우드 서버의 처리 부하 감소로 인한 서버 인프라 비용 절감
  - 확장성 확보 및 안정성 향상

- **장기적 TCO 개선:**
  - 초기 캐시 서버 구축 비용 대비 장기 운영 비용 절감 효과
  - 클리닉 규모가 클수록 절감 효과 증가
  - 로컬 네트워크 사용으로 외부 네트워크 비용 부담 감소

**4. 가용성 향상:**

- 클라우드 서버 일시 장애 시에도 캐시된 데이터로 부분 서비스 가능
- 네트워크 단절 상황에서도 캐시 범위 내에서 조회 가능

**5. 데이터 보안 및 프라이버시:**

- 자주 사용되는 데이터를 로컬에 보관하여 외부 전송 최소화
- 민감한 의료 정보의 외부 노출 위험 감소
