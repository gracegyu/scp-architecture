# PoC #2-2: 메타데이터 저장소 기능 비교 및 선정

## Project Name

로컬 캐시 서버 메타데이터 저장소 기능 비교 및 선정

## Date

2025-11-19 (예정)

## Submitter Info

Raymond

## Project Description

치과 클리닉용 로컬 캐시 서버의 메타데이터 저장소를 선정한다. **기능 요구사항 충족 여부**를 우선 검증하고, 필요 시 성능을 측정한다.

## Business and Marketing Justification

**PoC 검증 가치:**

- 로컬 캐시 요구사항 기반 기능 비교 (TTL, 무효화, 재검증, 오프라인, 스풀링)
- 각 저장소의 장단점 정량화 (기능/운영/확장성)
- 향후 프로덕션 개발 시 메타데이터 저장소 확정

**핵심 요구사항 (0.로컬 캐시 서버 연구.md 기반):**

1. **캐시 메타데이터 저장**
   - 환자·스터디·시리즈 목록/요약
   - 이미지 캐시 인덱스 (파일 경로, TTL, 크기, 접근 시간)
   - 캐시 키 = clinicId + 경로 + 정규화 쿼리 + policyVersion

2. **TTL 관리**
   - 썸네일: 7~30일
   - 프리뷰: 1~7일
   - 메타 요약: 5~15분
   - 자동 만료 처리 필요

3. **무효화**
   - 환자ID/스터디ID 단위 강제 무효화
   - URL 버전 키 변경 시 즉시 무효화
   - Webhook 이벤트 수신 시 무효화

4. **재검증 (SWR)**
   - ETag·Last-Modified 조건부 재검증
   - stale-while-revalidate 지원
   - 응답 즉시, 백그라운드 갱신

5. **오프라인 모드**
   - 네트워크 단절 시 캐시 히트만 응답
   - 로컬 저널 기록 (메타 쓰기)
   - 복구 후 재동기화

6. **스풀링 (Write-back)**
   - 미디어 업로드 스풀 큐 관리
   - 멱등키/해시로 중복 방지
   - 재시도/백오프 정책

7. **복잡한 쿼리**
   - 클리닉별 최근 접근 환자 조회
   - 날짜 범위 검색
   - 타입별 필터링
   - JSONB/BSON 필드 쿼리

8. **동시성**
   - 다중 클라이언트 동시 읽기/쓰기
   - read-after-write 일관성 (요청자 세션)
   - 최종적 일관성 (전역)

**성공 기준:**

- 핵심 요구사항 8가지 모두 충족 가능 여부 확인
- 운영 복잡도 평가 (설치/백업/복구/모니터링)
- 확장성 평가 (대형 클리닉 대응)

## Risk Assessment

**기술 리스크:**

- PostgreSQL: 별도 서버 필요, 메모리 사용량
- MongoDB: 학습 곡선, Windows 서비스 안정성
- Redis: 메모리 제약, 영속성 설정, 복잡한 쿼리 제한

**완화 전략:**

- 기존 인프라 활용 (PostgreSQL)
- 하이브리드 구성 (주 저장소 + Redis 핫 캐시)
- Docker/systemd로 서비스 관리 단순화

## Technical Description

### 검증 대상

#### 옵션 A: PostgreSQL

**특징:**
- SQL 쿼리, JSONB 지원
- ACID 트랜잭션
- 복잡한 쿼리 지원 (JOIN, 범위 검색, 집계)
- 기존 인프라 활용 가능

**기능 검증:**
1. TTL: 배치 워커 필요 (별도 구현)
2. 무효화: DELETE WHERE 패턴 매칭
3. 재검증: ETag/Last-Modified 컬럼 + 애플리케이션 로직
4. 오프라인: 로컬 설치 + 저널 테이블
5. 스풀링: spool_queue 테이블
6. 복잡한 쿼리: 우수 (JSONB 인덱스)
7. 동시성: 우수 (MVCC)
8. SWR: 애플리케이션 로직 필요

#### 옵션 B: MongoDB

**특징:**
- BSON (JSON 네이티브)
- TTL 인덱스 내장 (`expireAfterSeconds`)
- 스키마리스 (동적 필드 추가)
- 샤딩 지원 (수평 확장)

**기능 검증:**
1. TTL: 내장 지원 (TTL 인덱스)
2. 무효화: deleteMany() 패턴 매칭
3. 재검증: 필드 기반 쿼리
4. 오프라인: 로컬 설치 가능
5. 스풀링: 컬렉션으로 관리
6. 복잡한 쿼리: 우수 (Aggregation Pipeline)
7. 동시성: 우수 (4.0+ 트랜잭션)
8. SWR: 애플리케이션 로직 필요

#### 옵션 C: Redis

**특징:**
- 인메모리 저장소
- TTL 내장 (자동 만료)
- Pub/Sub (무효화 이벤트 전파)
- AOF/RDB 영속성

**기능 검증:**
1. TTL: 내장 지원 (EXPIRE)
2. 무효화: KEYS 패턴 + DEL (주의: KEYS는 느림)
3. 재검증: 제한적 (애플리케이션 로직)
4. 오프라인: AOF 파일 보존
5. 스풀링: List/Stream으로 큐 구현
6. 복잡한 쿼리: 제한적 (Sorted Set, Lua)
7. 동시성: 우수 (싱글 스레드)
8. SWR: 제한적

### 기능 비교표 (핵심 요구사항 기준)

| 요구사항            | PostgreSQL        | MongoDB           | Redis             |
| ------------------- | ----------------- | ----------------- | ----------------- |
| TTL 관리            | ⚠️ 배치 워커 필요 | ✅ TTL 인덱스     | ✅ EXPIRE 명령    |
| 무효화 (패턴)       | ✅ WHERE 패턴     | ✅ deleteMany     | ⚠️ KEYS (느림)    |
| 재검증 (ETag)       | ✅ 컬럼 기반      | ✅ 필드 기반      | ⚠️ 제한적         |
| 오프라인 모드       | ✅ 로컬 설치      | ✅ 로컬 설치      | ✅ AOF            |
| 스풀링 큐           | ✅ 테이블         | ✅ 컬렉션         | ✅ List/Stream    |
| 복잡한 쿼리         | ✅ SQL + JSONB    | ✅ Aggregation    | ❌ 제한적         |
| 동시성              | ✅ MVCC           | ✅ 트랜잭션 4.0+  | ✅ 싱글 스레드    |
| SWR                 | ⚠️ 앱 로직        | ⚠️ 앱 로직        | ⚠️ 앱 로직        |
| **기능 충족률**     | **7/8 (87.5%)**   | **7/8 (87.5%)**   | **5/8 (62.5%)**   |

**분석:**
- PostgreSQL: TTL 배치 워커만 추가 구현 필요, 나머지 우수
- MongoDB: TTL 내장으로 운영 간편, 스키마 유연성 우수
- Redis: 복잡한 쿼리 제한적, 핫 캐시 용도로 적합

### 하이브리드 아키텍처

**권장 조합 A: PostgreSQL + Redis**

```
[Request]
  → Redis (Hot, 5분 TTL, 최근 접근 환자)
    → PostgreSQL (Warm, 영구 저장, 전체 메타데이터)
```

**장점:**
- PostgreSQL로 복잡한 쿼리 및 영구 저장
- Redis로 핫 데이터 초고속 응답
- 기존 PostgreSQL 인프라 활용

**단점:**
- TTL 배치 워커 필요
- 두 저장소 운영 필요

**권장 조합 B: MongoDB + Redis**

```
[Request]
  → Redis (Hot, 5분 TTL)
    → MongoDB (Warm, 영구 저장, TTL 자동 관리)
```

**장점:**
- MongoDB TTL 인덱스로 자동 만료
- 스키마 유연성 (메타데이터 진화)
- 샤딩으로 대형 클리닉 대응

**단점:**
- 신규 저장소 (학습 곡선)
- 기존 PostgreSQL 미활용
