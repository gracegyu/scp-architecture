# Supabase 도입 검토

- 작성일: 2026-09-15 (개정 2회 — "기반 + 예외 개발" 구성 추가 · 생애주기 기준 비교 프레임 도입)
- 상태: 검토 완료 · **결론 = 코어 미채택, 코어 바깥 부분 채택 여지 있음**
- 관련 문서: [SPC Cloud Server 연구](SPC%20Cloud%20Server%20연구.md) · [메타데이터 연구](../데이터%20저장%20관리%20연구/메타데이터%20연구.md) · [스토리지 클래스 및 라이프사이클 전략](../데이터%20저장%20관리%20연구/스토리지%20클래스%20및%20라이프사이클%20전략.md)

## 목적/범위

Supabase를 SCP Cloud Server의 기반으로 삼는 것이 이득인지를 판정한다. 두 가지 구성을 각각 검토한다.

- **구성 A — 전면 전환**: 기존 연구에서 요구사항과 개념만 가져오고 구체 기술은 백지로 되돌린 뒤, 전 계층을 Supabase로 구성한다.
- **구성 B — 기반 + 예외 개발**: Supabase를 기본 기반으로 깔고, Supabase에서 불가능한 부분만 따로 개발해 연동한다.

판정 대상이 아닌 것: Supabase 제품 자체의 우열, 다른 BaaS(Firebase, Appwrite 등)와의 비교.

## 결론 요약

| 구성 | 판정 | 결정적 근거 |
| --- | --- | --- |
| A. 전면 전환 | **미채택** | 이미지 처리·전송 계층을 대체할 수 없다. 대체 불가 시 AWS가 남아 이중 인프라가 되므로 전환 목적이 소멸한다 |
| B. 기반 + 예외 개발 | **미채택** (조건부 예외 있음) | 개발비 절감은 실재하나 그 양이 전체의 10~15%에 그치고, 클라우드 경계라는 반복 비용이 새로 생긴다. 무엇보다 **같은 절감을 Supabase 없이 AWS 안에서 얻을 수 있다** |
| 코어 바깥 부분 채택 | **조건부 가능** | 내부 콘솔·권한 PoC는 이득이 실재하고 이음매가 뜨거운 경로에 없다 |

이 검토에서 구성과 무관한 수확이 하나 나왔다. 메타데이터 저장소를 DynamoDB와 Aurora로 이원화한 기존 결론은 재검토 가치가 있으며, **개발비 관점에서 특히 그렇다**(§"취할 통찰").

> **비교 기준에 관한 주의.** 본 문서 초판은 "초기 개발 속도"를 단일 항목으로 두고 Supabase에 우위를 부여했다. 이는 두 가지 이유로 부적절했다. ① 생애주기의 첫 구간만 본 비교였고, ② AI 보조 개발 환경에서 그 구간의 격차 자체가 크게 줄었다. §"비교 프레임"에서 이를 바로잡았다.

## 구성 A — 전면 전환

### 전제

전면 전환이 성립하려면 아래가 모두 Supabase로 대체되어야 한다. 하나라도 AWS에 남으면 인프라가 두 벌이 되어 전환의 목적(단순화)이 사라진다.

| 계층 | 현재 설계 | 전면 전환 시 |
| --- | --- | --- |
| 메타데이터 정본 | Aurora PostgreSQL + DynamoDB | Supabase Postgres |
| 인증 | OneID(Keycloak) OAuth2 | Supabase Auth |
| 인가 | 백엔드 검증 + Authorization 서비스(옵션) | RLS |
| 이미지 저장 | S3(원본/프리뷰/썸네일/아카이브) | Supabase Storage |
| 이미지 처리 | Lambda(JPEG2000, binning, 3D 스냅샷) | Edge Functions |
| 전송 | CloudFront + 서명 URL + Lambda@Edge | Supabase Storage CDN |
| 실시간 | 직접 구현(진행률/상태 알림) | Realtime |

### 판정 근거 — 심각도순

#### A-1. 프리뷰·썸네일 파이프라인을 실행할 곳이 없다 (치명)

[SPC Cloud Server 연구](SPC%20Cloud%20Server%20연구.md)에 정의된 파이프라인은 JPEG2000 손실 압축, Rate10 + binning, 3D 볼륨 렌더링 스냅샷이다. 수백 MB 볼륨을 메모리에 적재해 네이티브 코드로 처리하는 작업이며, Lambda의 메모리·실행시간 한계 안에서 가능한지를 PoC로 검증하는 것이 현재 오픈 이슈로 남아 있다.

Supabase Edge Functions는 Deno 런타임이고 메모리·실행시간 여유가 Lambda보다 좁으며, 네이티브 바이너리 실행 전제가 다르다. **CT 볼륨 처리를 이 위에서 돌릴 수 없다.**

결과적으로 이 파이프라인은 어떤 경우에도 Lambda 또는 컨테이너에 남는다. 파이프라인이 남으면 그 입력인 S3와 이벤트 트리거도 함께 남는다. 이 한 항목만으로 구성 A의 전제가 깨진다.

#### A-2. 전송 계층의 통제권을 잃는다 (치명)

현재 설계는 CloudFront 위에 서명 URL, Lambda@Edge 실시간 인증, 캐시 키 정규화, Origin Shield, 썸네일/프리뷰 TTL 분리, 권한 변경 시 무효화까지 규정하고 있다. 서비스의 승부처가 전송 성능이므로 이 통제력이 곧 제품 경쟁력이다.

Supabase Storage에도 CDN이 붙지만 **캐시 키 설계나 엣지 인증 실행 같은 제어를 노출하지 않는다.** 대용량 egress 비용 구조도 S3 + CloudFront 조합이 유리하다.

#### A-3. 데이터 레지던시 (치명 — 단, 자체 호스팅 시 해소)

PHI 자체는 막다른 길이 아니다. Supabase는 상위 플랜에서 HIPAA 대응과 BAA를 제공하는 것으로 파악된다(**미확인 — §"확인이 필요한 사항" 참조**).

실질적 장벽은 **리전**이다. 본 서비스는 국가별 배포와 지역 규제 대응을 요구사항으로 두고 있는데, Supabase는 리전 선택지가 AWS보다 좁고 프로젝트 단위로 리전이 고정된다. 한국은 의료기관 진료기록의 국외 이전이 민감해 국내 리전이 사실상 필수이고, 베트남·브라질 등도 각자 요건이 발생할 수 있다.

자체 호스팅하면 리전 제약은 해소된다. 그러나 Postgres·GoTrue·PostgREST·Realtime·Storage·Kong을 직접 운영해야 하므로 **AWS 관리형 서비스를 직접 쓰는 것보다 운영 부담이 커진다.** 관리형의 이점을 얻으려는 도입 동기와 정면으로 어긋난다.

#### A-4. 인증 체계가 둘이 된다 (중대 — 우회 가능)

OneID(Keycloak)는 전사 자산이므로 대체 대상이 아니다. Supabase가 외부 JWT를 신뢰하도록 구성하는 것은 가능하나, 그 경우 `auth.uid()` 연동을 직접 구현해야 하고 Supabase Auth의 이점이 대부분 소멸한다. **Supabase의 가장 큰 가치를 쓰지 못하는 상태로 도입하게 된다.**

#### A-5. 테넌트 격리를 RLS로만 보증해야 한다 (중대)

요구사항은 "테넌트별 시스템/데이터 격리 방침"을 명시한다. RLS는 논리적 격리이며 물리적 격리가 아니다. 정책 한 건의 누락이 곧 해당 테이블 전체 노출로 이어지며, 이 유형의 사고는 실제로 반복 보고된다.

"치과 A와 치과 B의 환자 영상이 동일 테이블에 있고 정책으로만 분리된다"는 구조는 의료 분야 감사에서 입증 부담이 크다. 불가능하지는 않으나 설명 비용을 지속적으로 지불해야 한다.

#### A-6. 규모와 운영 성숙도 (중대)

Supabase는 단일 Postgres 인스턴스를 중심으로 한다. 읽기 복제·커넥션 풀링·PITR이 제공되나 Aurora 수준의 운영 도구와 장애 대응 실적과는 차이가 있다. 다중 리전 운영 시 리전마다 별도 프로젝트가 되며, 그 사이의 정합성과 운영 도구를 직접 구축해야 한다.

## 구성 B — 기반 + 예외 개발

### 전제

구성 A가 "전 계층 대체"를 전제하므로, 대체 불가 항목(A-1·A-2)만으로 부정된다. 그러나 **애초에 전면 대체를 노리지 않는다면 그 논리는 반론이 되지 않는다.** 따라서 구성 B는 별도로 판정해야 한다.

구성 B의 경계는 다음과 같이 그어진다.

| 담당 | 항목 |
| --- | --- |
| Supabase | 메타데이터 DB, 자동 REST API, RLS 기반 인가, 실시간 알림, 관리 UI |
| AWS(직접 개발) | S3 저장, 이미지 처리 파이프라인, CloudFront 전송, 스트림 zip 업·다운로드 |
| 외부 | OneID(인증), Stripe·Bootpay(결제) |

판정 질문은 하나다. **Supabase가 걷어내는 일의 양이, 인프라를 갈라놓는 비용보다 큰가.**

### B-1. 걷어내는 양 — 연구 범위로 계산

그동안 수행한 연구를 주제별로 놓고 Supabase가 실제로 담당하는 영역을 표시하면 다음과 같다.

| 연구 주제 | 문서 수 | Supabase가 덜어주는가 |
| --- | --- | --- |
| 리포트 연구 | 32 | 아니오 |
| 뷰어 관련 연구 | 27 | 아니오 |
| Image Download/Upload 속도 개선 | 24 | 아니오 |
| 캐시 서버 연구 | 15 | 아니오 |
| 결제 시스템 연구 | 10 | 아니오 |
| 동시 편집 연구 | 9 | 부분(Realtime을 프로바이더로) |
| SCP 분석 설계 | 5 | 부분 |
| 데이터 저장 관리 | 2 | **예** |
| 과금 시스템 | 1 | 아니오 |

Supabase가 실질적으로 걷어내는 것은 **메타데이터 CRUD 계층과 실시간 알림**이며, 연구한 문제 공간의 **10~15% 수준**이다.

반대로 걷어내지 못하는 목록은 이렇다 — 스트림 zip 업로드 API, 슬라이스 범위 다운로드, 프리뷰·썸네일 파이프라인, 서명 URL 발급, Mini CT 크롭, 결제 연동, Share·Order·판독 비즈니스 로직, 캐시 서버 동기화. **SCP를 SCP답게 만드는 요소가 전부 이쪽에 있다.**

절감은 실재하나 "기반을 깔았다"고 부를 만한 비중은 아니며, 덜어내는 대상은 어느 프로젝트에나 있는 CRUD 보일러플레이트다.

### B-2. 갈라놓는 비용 — 업로드 경로 추적

메타데이터를 Supabase에, 이미지를 AWS에 둔 상태로 업로드 한 건을 따라가면 비용이 드러난다.

스트림 unzip이 필요하므로 업로드는 AWS 측 API가 받는다. S3 저장 후 Put 이벤트로 Lambda가 기동하고, **이 Lambda가 메타데이터를 쓰려면 인터넷을 건너 Supabase에 접속해야 한다.** 여기서 다음이 파생된다.

- **키 관리**: Lambda가 RLS를 우회하는 서비스 키를 보유해야 한다. 유출 시 전 데이터가 열리므로 보관·로테이션 체계가 하나 더 생긴다.
- **원자성 부재**: S3 쓰기와 메타데이터 쓰기가 서로 다른 클라우드에 있어 트랜잭션이 성립하지 않는다. 메타데이터 쓰기 실패 시 고아 객체가 남고, 정합성 보정 배치가 필요하다.
- **경계 왕복**: 프리뷰 완료 알림을 클라이언트에 전달하려면 Lambda가 다시 Supabase Realtime을 호출한다. 업로드 한 건에 클라우드 경계를 두 번 넘는다.
- **키 소재 결정**: 서명 URL 발급에 필요한 CloudFront 개인키를 어느 쪽에 둘지 정해야 하며, 어디에 두든 한쪽이 다른 쪽을 호출한다.
- **관측 분산**: 장애 시 로그가 두 곳에 흩어져, 업로드 실패 추적에 CloudWatch와 Supabase 로그의 수동 대조가 필요하다.
- **레지던시 이중화**: 영상은 AWS 리전에, 메타데이터는 Supabase 리전에 놓인다. 국가별 규제를 만족시키려면 **두 곳을 모두 맞춰야 한다**(A-3의 부담이 두 배가 된다).

이 비용은 초기 1회가 아니라 **운영 기간 내내 반복**된다.

### B-3. 결정적 반론 — 같은 절감을 AWS 안에서 얻을 수 있다

Supabase는 오픈소스이며 구성 요소가 각각 독립 제품이다. 따라서 B-1에서 확인한 절감 항목은 대부분 Supabase 없이도 획득 가능하다.

| Supabase가 주는 것 | AWS 안에서의 대안 |
| --- | --- |
| 스키마 기반 REST API 자동 생성 | **PostgREST**(오픈소스)를 Aurora 앞에 배치 |
| 실시간 구독 | Supabase Realtime 서버(오픈소스) 또는 AWS 네이티브 수단 |
| RLS 기반 인가 | **PostgreSQL 기본 기능** — Supabase 고유 기능이 아니다 |
| 관리 UI | 내부 콘솔은 어차피 별도 구축 대상 |

즉 **메타데이터를 Aurora PostgreSQL 하나로 통합하는 것만으로** 구성 B가 노리는 개발비 절감의 대부분을 가져올 수 있다. 그것도 클라우드 경계 없이, 동일 계정·동일 리전·동일 IAM·동일 로그 안에서다. B-2의 비용이 통째로 사라진다.

### B-4. 구성 B가 성립하는 조건

공정하게, 아래 조건에서는 구성 B가 합리적이다.

- **기간이 승부인 초기 검증**: 수개월 내 데모로 투자·내부 승인을 받아야 하고, 그 산출물을 버릴 각오가 되어 있다면 이음매 비용은 후순위다. 단 §"AI 보조 개발이 바꾸는 것"에 따라 이 조건의 설득력도 예전만 못하다 — 자체 구성으로도 같은 기간에 도달할 여지가 생겼기 때문이다.
- **팀이 매우 작아 인프라 담당이 없는 경우**: 관리형에 기대는 편이 낫다. 다만 Aurora·S3 역시 관리형이므로, 이 조건이 Supabase를 특정해 가리키지는 않는다.
- **코어 바깥 과제**: 내부 콘솔 등은 이음매가 뜨거운 경로에 없다(§"코어 바깥 부분 채택").

반대로 **수명이 길고, AWS 표준이 이미 서 있고, 의료 규제를 받으며, 도메인 특수 기능이 계속 추가되는 제품**에서는 초기 절감보다 반복 비용이 크다. SCP는 네 조건을 모두 충족한다. §"생애주기 비교"의 종합표가 이를 구간별로 보인다.

## 비교 프레임 — 무엇을 비교해야 하는가

### 초기 개발 속도만 비교하면 안 되는 이유

소프트웨어의 비용은 최초 구축에서 끝나지 않는다. SCP는 요구사항 문서에 "Sharing, Order, 판독, Cloud AI 서비스"를 후속 과제로 열어 두었고, 국가별 배포와 규제 대응을 전제하며, 데스크톱 뷰어·캐시 서버·EzServer와의 연동을 예정하고 있다. **최초 구축보다 그 이후의 고도화·운영·규제 대응 구간이 길고 무겁다.**

따라서 비교는 생애주기 전 구간에서 이루어져야 한다. 구축 구간 하나만 놓고 우열을 가리면, 가장 짧은 구간의 이점으로 가장 긴 구간의 부담을 사는 결정이 된다.

### AI 보조 개발이 바꾸는 것

Supabase의 구축 속도 우위는 대부분 "쓰지 않아도 되는 코드"에서 나온다 — 스키마에서 자동 생성되는 CRUD API, 인증 연동 코드, 관리 화면 골격이다.

**그런데 이것들은 AI 보조 개발이 가장 잘 압축하는 종류의 작업이다.** 설계가 서 있으면 CRUD 계층·마이그레이션·API 스캐폴딩·테스트·IaC 작성은 짧은 시간에 생성된다. 즉 Supabase가 덜어주는 일과 AI가 덜어주는 일이 **상당 부분 겹친다.**

반대로 AI가 압축하지 못하는 것은 아키텍처 결정, 도메인 고유 알고리즘(JPEG2000 파라미터 조정, 볼륨 처리), 분산 장애 디버깅, 실부하 성능 프로파일링, 규제 검토다. 이쪽은 어느 구성을 택하든 사람이 해야 한다.

여기서 따라 나오는 결론이 있다. **AI 보조 환경은 자체 설계의 상대적 가치를 높인다.** 직접 만드는 비용은 내려가는데 직접 만들어서 얻는 통제력은 그대로이기 때문이다. 관리형 기반의 전통적 논거("만들 시간이 없다")가 약해진다.

그러므로 아래 비교표에서 구축 구간의 격차는 **"Supabase 빠름 / 기존 느림"이 아니라 "차이가 좁혀짐"으로 평가한다.**

## 취할 통찰 — 메타데이터 저장소 재검토

Supabase를 채택하지 않더라도 이 검토에서 얻을 것이 있다. [메타데이터 연구](../데이터%20저장%20관리%20연구/메타데이터%20연구.md)의 결론은 다음과 같다.

> 환자/클리닉/유저 등 마스터 데이터 → Aurora PostgreSQL
> 이미지 메타데이터 → DynamoDB 단일 테이블

그리고 같은 문서의 오픈 이슈에 **"정밀 키 설계 선택(Aurora 병용 필요성?)"**이 남아 있다. 이 물음은 타당하다.

DynamoDB 채택 근거는 고동시성·낮은 지연·조건부 업데이트·유연 스키마였다. 그러나 같은 문서가 제시한 요구사항과 대조하면 다음과 같다.

| 요구사항 | PostgreSQL | DynamoDB |
| --- | --- | --- |
| Clinic·Study·Tag·날짜·공유상태 검색 | 인덱스로 자유롭게 대응 | GSI를 사전 설계, 패턴 이탈 시 불가 |
| 동시편집 충돌 방지 | `UPDATE … WHERE version = ?` | 조건부 표현식 |
| 유연 스키마 | JSONB | 네이티브 |
| 마스터 데이터와 조인 | 가능 | 불가 |
| 공유 권한 모델 | 정책·조인으로 표현 | 애플리케이션이 전부 조합 |

요구사항 목록의 첫 항목이 "빠른 조회/검색(Clinic, Study/Series/Instance, Tag, 날짜, 공유 상태 등)"인데, 이는 DynamoDB의 구조적 약점에 정면으로 해당한다. 조회 축이 다섯 개면 GSI 설계가 조기에 포화하고, 축이 하나 추가되면 테이블 재설계가 필요하다.

더구나 Aurora는 마스터 데이터용으로 이미 도입이 확정되어 있다. 따라서 **저장소가 둘이 되고, 그 사이에 조인과 트랜잭션 경계가 없다.** "이 환자의 공유 중인 스터디 목록"과 같이 두 저장소를 걸치는 질의가 전부 애플리케이션 조합이 된다.

**개발비 관점에서 이 논거는 더 강해진다.** DynamoDB를 유지하면 GSI 설계와 애플리케이션 조합 코드를 직접 작성해야 한다. Aurora로 통합하면 그 작업이 사라지는 동시에 PostgREST 같은 기성 도구를 얹을 수 있게 되어, 구성 B가 노리던 절감을 이음매 없이 획득한다. **즉 "Supabase를 쓸 것인가"보다 "메타데이터를 Postgres로 모을 것인가"가 실질적인 개발비 의사결정이다.**

**제안**: Supabase 채택 여부와 분리해, 이미지 메타데이터를 Aurora PostgreSQL로 통합하는 안을 재검토한다. 판단에 필요한 입력은 규모 수치다 — 예상 클리닉 수, 클리닉당 연간 스터디 수, 피크 동시 조회 수. 현재 이 수치가 어느 문서에도 없으며, 그것이 없는 상태에서 DynamoDB를 선택한 근거는 정성적 판단에 머문다.

## 코어 바깥 부분 채택

전면 전환과 기반 채택을 모두 부정하되, 아래 두 곳은 별도로 검토할 가치가 있다. 공통 조건은 **PHI 정본을 담지 않고 코어 경로에 개입하지 않는 것**이다.

**운영자·고객지원(SA) 내부 콘솔.** 코어와 분리되어 있고 구축 속도가 중요하다. RLS와 자동 생성 API의 이점을 그대로 받으며, §B-2의 이음매 비용이 뜨거운 경로에 발생하지 않는다.

**Share 권한 모델 PoC.** 현재 인가(Authorization)는 [SPC Cloud Server 연구](SPC%20Cloud%20Server%20연구.md)에서 "[논의 필요]"로 열려 있다. RLS로 정책을 수 건 작성해 보면 설계한 권한 모델이 데이터 계층에서 표현 가능한지를 단기간에 확인할 수 있다. **결론만 회수하고 본 구현은 자체 수행**하는 용도다.

## 재검토 조건

아래 중 하나라도 발생하면 이 문서의 결론을 다시 본다.

- 이미지 처리 파이프라인을 Lambda가 아닌 컨테이너(ECS/EKS 등)로 옮기기로 결정한 경우 — A-1의 전제가 바뀐다
- Supabase가 필요한 리전(최소 한국)을 제공하고 BAA 범위가 확인된 경우 — A-3이 해소된다
- **프로젝트 성격이 "기간 승부의 초기 검증"으로 재정의된 경우** — §B-4의 조건에 해당하므로 구성 B를 다시 계산한다
- 메타데이터 재검토 결과 Postgres 단일화로 결론난 경우 — 부분 채택 범위를 다시 계산할 가치가 있다
- 내부 콘솔 구축이 실제 과제로 착수되는 경우 — 부분 채택 검토를 개시한다
