## 1. 목적

소프트웨어 스펙 문서(SRS·기능명세·설계문서 등)를 **어디에 저장하고(개발 단계별), 어떻게 리뷰하며, 이후 어떻게 참조·보관**할지에 대한 **전사 표준**을 정한다. 아래 세 가지를 동시에 만족하는 것이 목표다.

1. **Baseline 준수** — 승인된 문서는 소스코드와 **하나의 base**로 관리한다.
2. **리뷰 편의** — 개발자 외 기획·PM·(때론) 외주도 코멘트·합의할 수 있어야 한다.
3. **접근성** — 권한·소속에 관계없이 필요한 사람이 **열람**할 수 있어야 한다.

## 2. 적용 범위

- **대상 문서:** SRS, 기능·기술 명세, 설계문서(아키텍처/모듈), OnePager 형태의 스펙 등 **제품 요구·설계 정본이 되는 문서**.
- **제외:** WBS·일정(별도 관리, 본 표준은 링크/참조만 규정), 회의록·아이디어 노트 등 비정본 산출물.
- **형식:** 원칙적으로 **Markdown(.md)** 로 작성한다(diff·리뷰·게시에 유리).

## 3. 용어 정의

| 용어 | 정의 |
|---|---|
| **정본(Source of Truth)** | 승인된 문서의 **단일 원본**. 항상 소스코드와 같은 Git(Azure DevOps) 저장소에 둔다. |
| **리뷰 표면(Review Surface)** | 코멘트·합의를 위한 **한시적** 작업 공간. 승인되면 폐기하거나 정본을 가리키는 포인터로 전환한다. |
| **게시본(Publish/Reference)** | 정본을 렌더한 **읽기전용** 뷰. 권한 없는 사람의 "읽기"를 Git 접근과 분리한다. |

## 4. 기본 원칙

1. **정본은 항상 Git(코드와 동일 repo).** baseline 대원칙. 예외 없음.
2. **3개 표면을 분리한다:** 정본 / 리뷰 표면 / 게시본. **리뷰·위키 도구를 "정본"으로 쓰지 않는다**(= baseline 파괴 = 과거 편법의 원인).
3. **승인 후 정본은 하나로 단일화한다.** 리뷰용 사본을 살아있는 복사본으로 방치하지 않는다(drift 방지).
4. **리뷰 표면은 한시적이다.** 대상(내부/외주)에 맞게 선택하고, 승인되면 코멘트를 정본에 반영 후 정리한다.
5. **도구는 VN 정식 도입 서비스로 한정·통일한다**(§5).

## 5. 허용 도구 (VN 보안 정책)

VN은 하드웨어 업체 특성상 **정보 유출 방지가 최우선**이며, **VN이 정식 도입한 서비스만** 사용한다.

| 구분 | 도구 | 용도 |
|---|---|---|
| **허용** | **Azure(DevOps)** | 정본 저장(Git repo), PR 리뷰, Wiki 게시 |
| | **MS365(SharePoint·OneDrive, Word/Excel Online)** | 문서 협업·코멘트 리뷰, 내부/외주 공유 |
| | **VKS(Confluence)** | 표준·전사 프로세스 게시, 인라인 코멘트 리뷰(보조) |
| | **VTS(Jira)** | 이슈·리뷰 지적사항·버그 트래킹 |
| **금지** | Gmail·Google Docs·Notion 등 외부 SaaS | 차단(사용 금지) |
| | Netlify·Vercel 등 임의 외부 SaaS 호스팅 | 🔄 불가 — 게시는 **회사 관리 인프라**(Azure DevOps·자사 SCP 클라우드) 내에서 |

> 같은 목적에 여러 도구를 혼용하지 않는다. "Google Docs 대체재"는 **MS365 Word Online**이다.

## 6. 개발 단계별 저장·리뷰 표준 (핵심)

| 단계 | 활동 | 저장 위치(작업본) | 리뷰 표면 | 산출물/상태 |
|---|---|---|---|---|
| **① 작성(Draft)** | 초안 작성 | **Git repo 작업 브랜치**(MD) | — | 브랜치 상의 MD |
| **② 리뷰(Review)** | 코멘트·합의 | 브랜치(MD) + 리뷰 표면 | **대상별**(§7) | 코멘트·수정 반영 |
| **③ 승인·기준화(Approved/Baseline)** | 승인·병합 | **Git repo main = 정본** | — | 정본 확정, 리뷰 사본 정리 |
| **④ 게시·참조(Publish)** | 상시 열람 | 정본(Git) | — | **읽기전용 게시본**(§9) |
| **⑤ 개정(Revision)** | 변경 | 새 작업 브랜치 | ②와 동일 | Git 이력에 버전 누적 |

**요지:** 문서는 **처음부터 Git 브랜치에 MD로 작성**해 이력을 확보하고, 리뷰만 대상에 맞는 표면에서 진행한 뒤 **승인되면 main에 병합해 정본화**한다. 열람은 정본을 게시본으로 렌더해 분리한다.

## 7. 리뷰 절차 (대상별)

리뷰 대상 범위에 따라 표면을 선택한다.

### 7.1 VN(계열사) 내부만 리뷰

| 리뷰어 유형 | 리뷰 표면 |
|---|---|
| 개발·기술 중심 | **Azure DevOps Pull Request** — MD diff 인라인 코멘트·스레드·resolve (baseline-native) |
| 기획·PM 등 비개발 | **VKS(Confluence) 인라인 코멘트** 또는 **SharePoint Word Online**(코멘트·변경내용 추적)에 리뷰 라운드 미러 → 코멘트 반영 후 MD로 회수 |

### 7.2 외주(외부) 포함 리뷰

- 외부 인력은 Azure DevOps·VKS 접근 불가 → **OneDrive 공유 Word Online**(코멘트/suggest) 또는 **PDF**로 리뷰 라운드 진행.
- 외부에는 **스냅샷만 공유**(정본·Git 접근 금지). 코멘트는 내부에서 정본 MD에 반영한다.

### 7.3 리뷰 지적사항 관리

- 리뷰 중 발견된 버그·누락·개선은 **VTS(Jira) 이슈/Sub-Task**로 등록해 추적한다(1건 = 1 이슈).
- 각 이슈에 **재현 절차·기대 결과(스펙 근거)·실제 결과·스크린샷**을 포함한다.

## 8. 승인·기준화(Baseline)

- 리뷰 합의가 끝난 문서는 **Git repo main에 병합**하여 정본으로 확정한다.
- 리뷰용 사본(VKS·SharePoint/OneDrive Word·PDF)은 **"리뷰 아티팩트 — Git 정본으로 대체됨"** 표기 후 정본 링크로 포인터화하거나 보관한다. **살아있는 복사본을 남기지 않는다.**
- 문서가 여러 repo에 걸치는 제품은 정본 위치를 **그때그때 합의**해 명시한다(대원칙은 코드와 동일 base 유지).

## 9. 게시·참조·보관

권한·소속에 관계없이 열람할 수 있도록 정본을 **읽기전용 게시본**으로 렌더한다. **개발자는 Git 저장소의 `/docs` 정본을 직접 열람**하면 되고, **게시본(wiki)은 Git 접근이 없거나 라이선스가 제한된 비개발자(기획·PM 등)** 를 위한 것이다.

| 구분 | 게시 방법 | 대상 |
|---|---|---|
| **기본** | 🔄 **Azure DevOps Project wiki 자동 미러** — 파이프라인이 main의 정본 MD를 프로젝트 wiki repo(`<project>.wiki`) 하위 폴더로 push(정본은 Git 유지, 완전 자동). **Stakeholder(무료) 열람 가능** | VN 내부(**비개발 포함**) |
| **보조** | **PDF 스냅샷을 OneDrive 공유** | 외주(외부) — 스냅샷만 |

> ⚠️ **code wiki는 쓰지 않는다:** Azure DevOps의 **"Publish code as wiki"(code wiki)** 는 소스 repo에 물려 있어 **Basic 이상만 열람**되고 **Stakeholder(무료)는 못 본다**. 비개발자(기획·PM 등) 열람 보장을 위해 게시본은 **반드시 project wiki(기본)** 로 만든다. 정본과의 drift는 **파이프라인 자동 미러**(main 병합 시 `/docs` MD → wiki repo push)로 없앤다 — wiki는 게시본일 뿐 정본은 Git이다.

### 9.1 Project wiki 자동 미러 파이프라인 (구현 가이드) 🆕

정본(Git `/docs`)을 project wiki에 **단방향 자동 미러**해, 매번 수동 복사 없이 게시본을 최신으로 유지한다. project wiki 뒤에는 전용 git repo(`<project>.wiki`)가 있으므로 CI가 여기에 push하면 wiki가 갱신된다(Microsoft 공식 지원 패턴).

**사전 준비(1회):**

1. **Project wiki 생성(없을 때만)** — 프로젝트 → **Overview → Wiki** → **Create project wiki**.
   - 처음 생성하면 **첫 페이지(홈 랜딩 페이지) 제목을 묻는다** → 관례상 **`Home`** 입력. 내용은 한 줄 소개면 충분(예: `프로젝트 문서 게시본. 정본은 각 repo의 /docs.`).
   - 이 홈 페이지는 랜딩용일 뿐이고, **자동 미러는 별도 하위 폴더 페이지**로 들어가므로 홈 제목은 무엇이든 무방하다.
   - 생성되면 backing repo `<project>.wiki`(기본 브랜치 `wikiMaster`)가 만들어진다.
   - ⚠️ **code wiki가 아니라 project wiki** 여야 Stakeholder 무료 열람 가능(§9 상단 노트). 상단 wiki 드롭다운에 이미 `<project>.wiki`(Project wiki)가 있으면 이 단계는 건너뛴다.
2. **인증 준비(§9.2 A안 = PAT):**
   - **PAT 발급** — 우측 상단 프로필 → *Personal Access Tokens* → *New Token* → 스코프 **Code: Read & Write**, 만료일 지정 → 토큰 문자열 복사(생성 직후 1회만 표시됨).
   - **파이프라인 secret 변수 등록** — Pipelines → 해당 파이프라인 → *Edit → Variables → New variable* → 이름 **`WIKI_PAT`**, 값 = PAT, **"Keep this value secret" 반드시 체크**(저장 후 `🔒 ***` 로 보이는지 확인).
   - ⚠️ secret 체크를 빠뜨리면 PAT가 **평문 노출**된다(변수 UI·로그). 노출됐다면 즉시 해당 PAT **Revoke** 후 재발급.
   - 개인 계정 종속(발급자 퇴사·만료 시 중단)을 피하려면 **전용 서비스 계정 PAT** 권장.

**파이프라인 스텝(검증 완료 · `scp-section-poc/azure-pipelines.yml`):** `main` 빌드 성공 후 실행.

```yaml
- script: |
    set -e
    if [ -z "$WIKI_PAT" ]; then echo "ERROR: secret 변수 WIKI_PAT 미설정"; exit 1; fi
    WIKI_URL="https://dev.azure.com/{org}/{project}/_git/{project}.wiki"
    # PAT basic 인증(사용자명 공백 + PAT). URL/원격설정·로그에 토큰을 노출하지 않도록 extraheader 사용.
    B64=$(printf ":%s" "$WIKI_PAT" | base64 | tr -d '\n')
    AUTH="AUTHORIZATION: basic $B64"
    rm -rf .wikisync
    git clone -c http.extraheader="$AUTH" "$WIKI_URL" .wikisync
    mkdir -p .wikisync/{product}                                # 공유 wiki 보호: 제품별 하위 폴더에만 기록
    rm -f .wikisync/{product}/*.md
    cp docs/*.md .wikisync/{product}/                           # 정본 MD → wiki 미러
    cd .wikisync
    git config user.email "build@company"; git config user.name "Docs Pipeline"
    git add -A
    if git diff --cached --quiet; then echo "no changes"; else
      git commit -m "docs: sync /docs from main [skip ci]"
      git -c http.extraheader="$AUTH" push origin HEAD:wikiMaster   # project wiki 기본 브랜치 = wikiMaster
    fi
  displayName: Publish /docs to Project wiki
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  env:
    WIKI_PAT: $(WIKI_PAT)
```

**결과(검증 완료 2026-07-28):** `scp-section-poc`의 `/docs` → `prototypes` project wiki의 `scp-section-poc/` 하위로 자동 미러 성공. 게시본 URL 예:

```
https://dev.azure.com/ewoosoft/prototypes/_wiki/wikis/prototypes.wiki/541/Section-Module-Spec-v1.3.2-OnePager
```

(치환값: `{org}`=`ewoosoft` · `{project}`=`prototypes` · `{product}`=`scp-section-poc`. 경로의 `541`은 wiki 페이지 ID로 자동 부여됨.)

**규칙·주의:**

- **단방향·읽기전용:** wiki에서 직접 편집하지 않는다. 편집은 Git 정본에서만 → 미러로 반영(양방향 금지 = baseline 보호).
- **공유 wiki 격리:** `<project>.wiki`가 여러 산출물에 공유되면 **제품별 하위 폴더**에만 기록해 타 콘텐츠를 보존한다.
- **인증:** **§9.2 A안(PAT) 채택.** 조직 정책 "Protect access…"(On) 하에서 `System.AccessToken`은 wiki repo 접근 불가(`TF401019`)였고, **PAT(`WIKI_PAT`)로 해결**함.
- **표기:** 파일명의 `-`는 wiki 페이지 제목에서 **공백**으로 표시된다(예: `A-B.md` → "A B"). mermaid 다이어그램도 wiki에서 렌더된다.
- **트리거:** `main` 한정. 커밋 메시지 `[skip ci]`로 미러 push가 불필요한 재실행을 유발하지 않게 한다.

### 9.2 인증 방식 — 조직 정책과 A(PAT) 채택 🆕

**배경:** 조직 설정 **"Protect access to repositories in YAML pipelines"** 가 **On**이면, 파이프라인 기본 토큰(`System.AccessToken`)은 **파이프라인이 명시적으로 선언한 repo에만** 접근 가능하다. project wiki backing repo(`<project>.wiki`)는 보통 미선언 시스템 repo이므로, **Repos 권한(Read/Contribute)을 부여해도** clone/push가 `TF401019`로 실패한다. 따라서 인증 방식을 아래 둘 중 하나로 정해야 한다.

| 방안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. PAT 인증 (권장)** | 개인(또는 **전용 서비스 계정**) PAT(`Code: Read & Write`)를 secret 변수로 clone/push에 사용 | **조직 보안 정책 유지** · 영향 범위 = **이 파이프라인 하나** · 즉시 동작 | secret 등록·**만료 갱신** 관리 · 개인 계정 PAT는 발급자 퇴사/만료 시 중단 → **서비스 계정 PAT 권장** |
| B. 조직 정책 Off (미채택·대안) | "Protect access…" 해제 후 `System.AccessToken` 사용 | secret·만료 불필요 · YAML 단순 | **전사 모든 파이프라인**의 repo 접근 보호가 풀림 = **조직 전체 보안 완화**(거버넌스 결정 필요) |

**결정: A(PAT) 채택·검증 완료(2026-07-28).** `scp-section-poc` 파이프라인에 PAT(`WIKI_PAT`, secret) 적용 → project wiki 미러 **성공**. 개인 계정 종속(발급자 퇴사·만료)을 피하려면 **전용 서비스 계정 PAT**로 발급한다.

> **B(정책 Off)를 안 쓴 이유:** 한 파이프라인 편의를 위해 **전사 모든 파이프라인의 보안**을 낮추는 트레이드오프라 미채택. 정책 변경이 필요하면 **팀·보안 담당 합의(거버넌스)** 로만 다룬다. (표에 대안으로만 남김.)

**A(PAT) 적용 시 인증 스텝 예:**

```yaml
# secret 변수: WIKI_PAT (Code: Read & Write 스코프)
env:
  WIKI_PAT: $(WIKI_PAT)
```

### 9.3 비개발자(기획·PM 등) 열람 온보딩 — Stakeholder + Reader 🆕

Azure DevOps 계정이 없는 비개발자도 **무료(Stakeholder)** 로 project wiki 게시본을 볼 수 있다. code wiki·Repos는 못 보지만 **project wiki는 Stakeholder도 열람 가능**하다(§9 상단 노트).

**관리자(조직 소유자)가 1회 설정:**

1. **사용자 초대 + Stakeholder 부여** — Organization Settings → **Users → Add users**:
   - 사용자 = 대상자의 **회사 Entra(MS365) 계정** 이메일.
   - **Access level = `Stakeholder`**(무료). ← Basic 아님(과금 회피).
   - Add to project = 해당 프로젝트(예: `prototypes`).
2. **프로젝트 Reader 권한 부여** — Project Settings → **Permissions → `Readers` 그룹**에 대상자 추가.
   - 대상자가 이미 **Readers에 포함된 Entra 그룹**의 멤버라면, 별도 추가 없이 **Access level만 Stakeholder**면 된다(그룹으로 권한 상속).

**대상자(열람자)가 할 일:**

3. 초대 메일 수락 → **회사 계정으로 로그인**.
4. 공유받은 **project wiki 게시본 URL** 열람(예: §9.1 결과 URL).

**주의·확인:**

- **반드시 project wiki URL을 공유**한다. code wiki URL은 Stakeholder가 못 본다(`Basic 이상` 필요).
- 열람이 안 되면: ① Access level이 **Stakeholder로 실제 부여**됐는지(Organization → Users), ② **Readers 소속**인지 확인.
- Stakeholder는 Boards 일부만 쓰고 **Repos·code wiki는 제한**되지만 **project wiki 열람은 정상**이다.

- **참조 규칙:** 다른 문서·이슈·코드에서 스펙을 참조할 때는 **정본(Git 경로) 또는 게시본 URL**을 링크한다. 리뷰용 사본을 참조 대상으로 삼지 않는다.
- **보관:** 리뷰가 끝난 문서는 **반드시 소스코드와 함께 Git에 보관**한다(baseline). 과거 이력은 Git 히스토리로 관리하며 별도 "old" 폴더 관행은 지양한다.

## 10. 개정 관리

- 변경은 **새 작업 브랜치 → PR/리뷰 → main 병합** 절차를 반복한다(§6-⑤).
- 버전·변경 이력은 **Git 이력**을 정본 이력으로 삼는다(문서 내 changelog는 보조).
- 게시본은 정본 병합 시 자동/수동으로 갱신한다.

## 11. 역할·권한

| 역할 | 책임 |
|---|---|
| **작성자(개발/PM)** | 브랜치 작성, 리뷰 요청, 코멘트 반영, 병합(정본화) |
| **리뷰어(기획/PM/QA/외주)** | 스펙 기준 검토, 코멘트·이슈 등록 |
| **승인자** | 리뷰 합의 확인 후 병합 승인 |
| **게시 담당** | 정본 → 게시본 발행·갱신, 접근권한 관리 |

> 🔄 **선결 확인 [해결 2026-07-28]:** Azure DevOps Stakeholder(무료) 열람 범위 확정 결과 — private 프로젝트에서 Stakeholder는 **Repos·code wiki 열람 불가**, **project wiki는 열람 가능**. 따라서 비개발 열람은 **project wiki 자동 미러(§9-1)** 로 보장한다. 기획(Stakeholder)의 실제 열람도 확인 완료. (담당: 전규현/Raymond)

## 12. 한 줄 요약

**정본은 무조건 Git(코드와 동일 repo). 리뷰는 대상에 맞는 한시 표면(VN=PR / VKS·SharePoint, 외주=OneDrive Word Online)에서 하고, 승인되면 Git으로 회수한다. 열람은 정본을 게시한 읽기전용 표면(Azure DevOps Wiki / Azure 정적 사이트)으로 분리한다. 모든 도구는 VN 정식 도입 서비스(Azure·MS365·VKS·VTS)로 한정·통일한다.**
